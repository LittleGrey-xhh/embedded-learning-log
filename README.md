## 二、知识点

### 1. ★★★ SCARA 平面二连杆逆解就是余弦定理，不需要 DH 参数

平面两连杆，末端坐标 (x, y)，臂长 L1、L2：

```
r² = x² + y²

cos(θ2) = (r² − L1² − L2²) / (2·L1·L2)
θ2 = ±acos(cos θ2)                    ← 正负号 = 两组解

θ1 = atan2(y, x) − atan2(L2·sin θ2, L1 + L2·cos θ2)
```

**就这三行。** 六个自由度才需要 DH 参数和雅可比矩阵，平面两连杆用不着。

正解（验证用）：

```
x = L1·cos θ1 + L2·cos(θ1 + θ2)
y = L1·sin θ1 + L2·sin(θ1 + θ2)
```

**验证方法：正解 → 逆解 → 正解，闭环比对。** 14400 个姿态跑下来，最大往返误差 0.000121mm，说明公式和符号全对。这是装机械之前唯一能确认的事。

**`acos` 之前必须夹住输入：**

```c
c2 = clampf(c2, -1.0f, 1.0f);   // 浮点误差会让 cos 略微超 1，进 acos 就是 NaN
```

边界上（两臂刚好伸直）几乎每次都会超一点点，不夹住就得到一个 NaN 角度，后面全崩。

**两组解怎么选：** 等长臂时两组解是镜像对称，抓取效果一样。但舵机行程只覆盖一侧，所以实际只能用一组。舍掉一组只损失"多一条绕行路径"，不影响能不能抓到。

### 2. ★★★ 末端方位角 = 大臂角 + 半个小臂角，这条决定了工作区长什么样

**我一开始把"大臂舵机能转 ±82°"直接当成"末端方位角只有 ±82°"，这是错的。** 实际单圈能扫 164°，但扫出来的不是一片正扇形，是一片"扭过的扇形"。

**推导（等长臂 L1 = L2 = L）：**

```
正解：x = L[cos θ1 + cos(θ1+θ2)]
      y = L[sin θ1 + sin(θ1+θ2)]

和差化积：cos A + cos B = 2·cos((A+B)/2)·cos((A−B)/2)
          sin A + sin B = 2·sin((A+B)/2)·cos((A−B)/2)

代入 A = θ1、B = θ1+θ2：

  r = 2L·cos(θ2/2)          ← 半径只由小臂角决定，和大臂角无关
  φ = θ1 + θ2/2             ← ★ 末端方位角 = 大臂角 + 半个小臂角
```

**两条结论同时成立：**

1. **φ 的跨度 = θ1 的跨度 = 164°**（因为 θ2/2 只是平移，不改变宽度）
2. **但整个 164° 的区间被 θ2/2 推着走**，而 θ2 随半径变（近处大、远处小）

**实测数据：**

| r (mm) | θ2 (°) | φ 中心 (°) | φ 范围 (°) |
|---|---|---|---|
| 20 | 171.6 | 85.8 | 3.8 ~ 167.8 |
| 100 | 137.2 | 68.6 | 346.6 ~ 150.6 |
| 200 | 86.2 | 43.1 | 321.1 ~ 125.1 |
| 270 | 19.6 | 9.8 | 287.8 ~ 91.8 |

**每条弧跨度都是 164°，但中心从 85.8° 漂到 9.8°，漂了 76°。**

所以：

| 项目 | 真值 |
|---|---|
| 单半径方位覆盖 | **164°** |
| φ 中心漂移 | **76°**（内圈偏左，外圈偏前） |
| 全半径公共方位（r 120~260） | **118°**，φ ∈ [−18°, 100°] |
| 形状 | **斜扇环**，不是圆盘也不是正扇形 |

**164° 的来源：** 大臂舵机 `SERVO1_MIN_DEG=8 / SERVO1_MAX_DEG=172`，180° 行程两头各留 8° 安全余量。**这 8° 不能省**，顶到 0°/180° 的后果是嗡嗡响、发热、烧掉。

**★ 装配时要考虑 φ 的偏置。** 大臂中位对准 +X（`THETA1_HOME = 0`）时，工作区整体偏向 +Y（左侧），因为 θ2/2 恒为正。想让工作区居中，`THETA1_HOME` 要设成 −40° ~ −50°，或者把底座整体转个角度。

**中位选在哪，还决定能覆盖多大的半径：**

| 小臂中位 | θ2 可取值范围 | 对应半径 | 解的组数 |
|---|---|---|---|
| 90°（折成直角） | 0 ~ 180° | 20 ~ 274mm | **只有一组** |
| 0°（直臂） | −82 ~ +82° | 207 ~ 274mm | 两组 |

**所以小臂舵机必须装在"折 90°"的位置，不是"伸直"的位置。** 这是装配时就要定下来的，装错了半径范围直接砍掉三分之二。

### 3. ★★ 细分和电流是两个独立参数：一个管分辨率，一个管扭矩

驱动器上 6 个拨码，前三个管细分，后三个管电流，**互不影响**。

```
脉冲当量 = 丝杆导程 ÷ (200 × 细分)
         = 4mm ÷ 1600 = 0.0025mm/脉冲

转速 = 脉冲频率 ÷ (200 × 细分) × 60
     = 8000 ÷ 1600 × 60 = 300 RPM
```

**细分不是越高越好：**

| 细分 | 脉冲当量 | 20mm/s 所需频率 | 问题 |
|---|---|---|---|
| 8 | 0.0025mm | 8 kHz | 正常 |
| 16 | 0.00125mm | 16 kHz | 光耦和中断压力翻倍 |
| 32 | 0.000625mm | 32 kHz | 3.3V 驱动光耦开始丢脉冲 |

**判据：细分精度只需要做到机械精度的一半。** T8 丝杆的重复精度只有 0.02~0.05mm，把细分做到 0.0006mm 纯属浪费，代价是频率翻倍。

**电流决定扭矩，但和细分无关：**

```
驱动器设 1.0A → 电机出约 3.2 kg·cm
驱动器设 0.5A → 电机出约 1.6 kg·cm（和电流近似线性）
```

**电机型号里通常编码了参数。** 这只 `42SHDC1067Z` 的后四位 `1067` 就是 **1.0A / 6.7Ω**。查不到手册时，先看型号编码。

### 4. ★★ 舵机受力要分两笔账：转动扭矩和悬臂弯矩

很多人把"转得动"和"撑得住"混成一件事，其实是两个独立的力，量纲都不一样。

**第一笔：绕 Z 轴的转动扭矩（决定转不转得动）**

```
转动惯量 J = Σ m·r² ≈ 0.0205 kg·m²
0.2s 加速到 90°/s → α = 7.85 rad/s²
所需扭矩 = J × α = 0.161 N·m = 1.64 kg·cm
加摩擦算 3 kg·cm
```

**MG996R 有 9.4 kg·cm，3 倍余量，够。**

关键洞察：**SCARA 是水平构型，臂在水平面内摆动，重力垂直向下，转动时根本不用对抗重力。** 所以转动这一笔账特别轻松。

**第二笔：压在输出轴上的悬臂弯矩（决定会不会耷拉）**

```
各部件重量 × 到回转轴的距离：
  大臂      200g × 6.8cm  = 1.36 kg·cm
  小臂舵机   55g × 13.7cm = 0.75
  小臂      200g × 20.5cm = 4.10
  夹爪舵机   55g × 27.4cm = 1.51
  夹爪       80g × 27.4cm = 2.19
  ─────────────────────────────
  合计 ≈ 9.9 kg·cm
```

**9.9 kg·cm 压在 5mm 输出轴上，超载 2~3 倍。**

**表现（装好立刻能看出来）：** 臂在水平位下垂、舵机持续嗡嗡响、松手回不到原位。

**缓解手段：** 降压到 6V（扭矩 9.4→11，但对弯矩没用）、缩短臂长（弯矩按距离平方衰减）、减重。

**教训：算舵机选型时，弯矩和扭矩要分开算。** 只算扭矩会得出"3 倍余量很安全"的错误结论。

### 5. ★★ 3.3V 的 MCU 和 5V 的光耦打交道，进出两个方向都有坑

**方向一：MCU 驱动驱动器（输出）**

驱动器输入端是光耦 LED + 内部限流电阻。共阳接法下，MCU 输出高电平时两端压差是：

| 共阳接 | MCU 输出高时压差 | 后果 |
|---|---|---|
| **3.3V** | 3.3 − 3.3 = **0V** | 光耦完全关断 ✔ |
| 5V | 5 − 3.3 = **1.7V** | 光耦半导通，脉冲乱发 ✘ |

**所以 3.3V 单片机的共阳一定要接 3.3V，不能接 5V。** 接 5V 时电压"看起来对"，实际光耦一直微微导通，表现为电机乱走、方向乱跳，极难排查。

代价是灌电流只有 (3.3−1.2)/270 ≈ 7.8mA，比 5V 时小，所以**高速时要拉满测一遍**，低速能转不代表高速能转。

**方向二：编码器/传感器进 MCU（输入）**

NPN 集电极开路输出 = **开漏**：输出低时把线拉到 0V，输出高时**线是悬空的**。

```
不加上拉 → MCU 永远读不到高电平
上拉接 5V → 高电平 5V 直接灌进 3.3V 的 IO
上拉接 3.3V → 正确
```

标准接法（上拉放器件侧，不是 MCU 侧）：

```
器件输出 ──┬── 4.7kΩ ── 3.3V
           └── 1kΩ ──── MCU 引脚
```

上拉放 MCU 侧会出问题：器件拉低时，3.3V 经 4.7k + 1k 分压，MCU 脚只有 0.58V，虽然勉强算低电平但余量很小。上拉放器件侧，MCU 脚能干净地到 0V。

**串 1k 是保险**：万一器件其实是推挽输出（5V 推挽），1k 把灌进 MCU 的电流限到 1mA，不会烧。

### 6. ★ 24V 电源端子和信号端子挨在一起，接线前必须量电压

驱动器从上看 12 个端子：

```
ENA− / ENA+ / DIR− / DIR+ / PUL− / PUL+   ← 信号（上面 6 个）
B− / B+ / A− / A+                          ← 电机（中间 4 个）
GND / VCC                                  ← 24V（最下面 2 个）
```

**`VCC` 在最底下，`ENA−` 在最顶上。** 顺着数接错，24V 直接进 STM32，整块板报废。

**规矩：上电前用万用表量一遍**——VCC 对 GND 是 24V，PUL+ 对 GND 是 3.3V，都对了再接 MCU。

另外 `B−/B+/A−/A+` 是 **B 在上、A 在下**，不是习惯的 A 在上。两相接反电机会反转（不影响），单相反了会原地抖不转。

## 三、踩的坑

1. **买滑台只看行程和价格，没看滑块尺寸。** 到货才发现滑块只有 1cm 宽，带 300g 外伸 150mm 的机械臂超载两倍。进度不受影响，但精度和寿命要打折。
2. **没预留夹板空间就选了"传感器贴着滑块"的滑台。** 传感器和滑块间隙几乎为 0，导致"上下夹板"方案全部作废，被迫改成"附加触发体"。
3. **工作空间的描述错了两回。** 第一回在交接文档里写"工作半径 0~274mm"，把数学上限当成了实际范围，没考虑舵机行程。第二回纠正时又走了另一个极端，把"大臂舵机能转 ±82°"直接当成"末端方位角只有 ±82°"——实际单圈能扫 164°。错因是没意识到 θ1 和末端方位角 φ 不是一回事。
4. **引脚规划时把步进 ENA 分给了 PC13，没查驱动能力。** F103 的 PC13/14/15 挂在 VBAT 电源域，数据手册明确最大只能灌/拉 3mA，而驱动器光耦要 8~15mA。这种错的麻烦之处是万用表量电压还是对的，只是带不动负载，查起来很绕。
5. **一开始把末端只规划成"夹爪开合"一个舵机，等于把 4 轴 SCARA 做成了 3 轴。** 看参照机型 WS-04 的参数（4 轴：立柱升降 / 腰部回转 / 大臂回转 / 腕部回转）才反应过来——它的第 4 轴就是腕转，我们买的 4 个舵机正好够用，不用额外买。**构型数错了轴数，机械和引脚都得返工。**

## 二、知识点

### 1. ★★★ ESP-IDF 工程分四层，别人的包里永远缺第三层

| 层 | 是什么 | 别人的包里 | 换机器要动吗 |
|---|---|---|---|
| 源码层 | `main/*.c`、`main/*.h`、`CMakeLists.txt` | 有 | 不用 |
| 芯片层 | `sdkconfig`（里面是 `CONFIG_IDF_TARGET`） | 有 | 换芯片要重配 |
| **本机层** | **`.vscode/`**（IDF 装在哪、串口号、target） | **通常没有** | **必换** |
| 产物层 | `build/` | 有时被打包进来 | **必删** |

`.vscode/` 不是工程的一部分，是"这台电脑的身份证"。ESP-IDF 插件靠它里面的 `idf.currentSetup` 判断"这是个 IDF 工程"，缺了就**不注入 include path**，C/C++ 满屏红线；同时 CMake Tools 插件会自己拿本机 mingw64 的 gcc 去 configure，多出一个错的 `build/`。

所以正确做法是：**每台电脑维护一份 `.vscode` 母版，所有工程共用，新工程直接复制**。只有三个字段可能变：`idf.currentSetup`（IDF 路径）、`idf.customExtraVars.IDF_TARGET`（芯片型号）、`idf.port`（串口号）。

`build/` 必须删的理由：里面的 `CMakeCache.txt` 和 `compile_commands.json` 全是别人机器的绝对路径。CMake 看到路径没变就认为"不用重新配置"，继续用错工具链。

### 2. ★★ I2C 只需要 4 个函数，读和写的区别就一句话

```
写： S | 地址+W | 寄存器号 | 数据 | P
读： S | 地址+W | 寄存器号 | Sr | 地址+R | 数据 | P
```

| 函数 | 干什么 |
|---|---|
| `i2c_new_master_bus()` | 铺一根线（配 SCL/SDA 引脚 + 时钟） |
| `i2c_master_bus_add_device()` | 往线上挂一台设备，登记地址，拿到 `dev` 句柄 |
| `i2c_master_transmit(dev, buf, len, to)` | 只发不收（写） |
| `i2c_master_transmit_receive(dev, &reg,1, data,1, to)` | 先发寄存器号再收数据（读） |

**总线是总线，设备是设备。** 建完总线只拿到总线句柄；挂完设备才拿到设备句柄。以后所有读写都用设备句柄，不再用总线句柄。

**一条总线可以挂多个从机，靠 7 位地址区分。** 这块板上：

- `PCA9557` = `0x19`，I2C 转 8 个 GPIO 的扩展芯片，管 `LCD_CS` / `PA_EN` / `DVP_PWDN` 这类开关脚
- `FT6336` = `0x38`，触摸控制 IC

PCA9557 就三个寄存器：`0x00` 输入（只读）、`0x01` 输出、`0x03` 配置（**写 1 = 输入，写 0 = 输出**，容易记反）。

**主机的真身是 ESP32 内部的 I2C 控制器外设**，不是 CPU 核心直接怼。所以配置时要指定 `i2c_port`（用 I2C0 还是 I2C1）。

### 3. ★★ 触摸屏：FT6336 和 gslX680 差的是"一整层内核驱动"

| | ESP32 / FT6336 | GEC6818 / gslX680 |
|---|---|---|
| 数据怎么来 | 自己的代码调 `i2c_master_transmit_receive()` 读寄存器 | `read()` 读 `/dev/input/event0` 的 `struct input_event` |
| 读什么 | `0x02` 触摸点数，`0x03~0x06` 四字节坐标 | `EV_ABS/ABS_X`、`EV_ABS/ABS_Y`、`EV_KEY/BTN_TOUCH` |
| 数据形态 | **一次拿到完整快照** `{state,x,y}` | **事件流**，一个动作拆成好几条 |
| 谁驱动 | 自己 `while(1)` 轮询 | LVGL 定时器回调 `read_cb`，被动被拉 |
| 芯片校验 | 读 4 个 ID 寄存器验明正身 | 不用管，内核验过了 |
| 输出 | 自定义 `tp_data_t` | `lv_indev_data_t`，直接喂 LVGL |

分层看就一句话：

```
GEC6818：芯片 → [内核驱动] → evdev 事件队列 → 你的 touch_input.c → LVGL
ESP32  ：芯片 → 你的 tp.c → 自定义结构体
```

**ESP32 上做的事，等于把"内核驱动 + evdev"两层的活自己干了。** 换算下来，`tp.c` 那 200 行里跟 LVGL 有关的只有最后几行，其余 150 行都在当驱动用。

接 LVGL 只差一个回调：

```c
static void tp_read_cb(lv_indev_t *indev, lv_indev_data_t *data)  // LVGL 每次刷新会调这个
{
    tp_data_t s;                                    // 装一次读到的快照
    tp_read_xy(&s);                                 // 调自己的驱动拿坐标
    data->point.x = s.x;                            // 填 X
    data->point.y = s.y;                            // 填 Y
    data->state = (s.state == TP_STATE_PRESS)       // 按下还是松开
                  ? LV_INDEV_STATE_PRESSED : LV_INDEV_STATE_RELEASED;
}
```

### 4. ★★★ PWM 的 `duty` 是"高电平占比"，亮度方向由 LED 极性决定

这是今天最容易搞混的一点，两层要分开算：

1. `duty` 是**高电平占整个周期的比例**（官方示例：13 位下 `duty = 4096` 就是 50%）
2. LED 亮不亮看**引脚是低电平还是高电平**（本板低电平点亮）

所以对这块板：

| duty（10 位 0~1023） | 引脚输出 | 灯 |
|---|---|---|
| `0` | 恒低 | **全亮** |
| `1023` | 恒高（实际约 99.9%） | **全灭** |

**STM32 那边反而是 CCR 越大越亮**，因为 `OCPolarity = LOW` 把"有效电平"定义成了低电平，`CCR` 越大低电平越长。两边数值含义相反，照抄代码会得到反方向的呼吸。

解法：ESP32 用 `ledc_channel_config_t` 里的 `.flags = { .output_invert = 1 }` 把输出反相，之后就是"数值大 = 引脚低 = 亮"，跟 STM32 的直觉一致。

### 5. ★★ LEDC 配置三步，第三步不能省

```c
// 1. 定时器：定频率和分辨率，可被多个通道共用
ledc_timer_config_t timer_cfg = {
    .speed_mode      = LEDC_LOW_SPEED_MODE,   // 低速模式
    .timer_num       = LEDC_TIMER_0,          // 定时器 0
    .duty_resolution = LEDC_TIMER_10_BIT,     // 10 位 → 占空比 0~1023
    .freq_hz         = 5000,                  // 5kHz
    .clk_cfg         = LEDC_AUTO_CLK,         // 时钟源自动选
};
ledc_timer_config(&timer_cfg);

// 2. 通道：绑定时器 + 绑定引脚
ledc_channel_config_t ch_cfg = {
    .speed_mode = LEDC_LOW_SPEED_MODE,        // 必须跟定时器一致
    .channel    = LEDC_CHANNEL_0,             // 通道 0
    .timer_sel  = LEDC_TIMER_0,               // 用哪个定时器（决定频率）
    .gpio_num   = GPIO_NUM_10,                // 输出引脚
    .duty       = 1023,                       // 初始占空比
    .hpoint     = 0,                          // 相位起点
    .flags      = { .output_invert = 1 },     // 输出反相
};
ledc_channel_config(&ch_cfg);                 // 配完就自动输出，没有单独的 Start

// 3. 改占空比：两句必须成对
ledc_set_duty(LEDC_LOW_SPEED_MODE, LEDC_CHANNEL_0, 500);  // 只写影子寄存器
ledc_update_duty(LEDC_LOW_SPEED_MODE, LEDC_CHANNEL_0);    // 这一句才推到引脚
```

**`ledc_update_duty()` 忘了写，现象是"代码在跑但灯一动不动"。** STM32 写 CCR 是立即生效的，ESP32 不是。

还有一个细节：10 位分辨率下最大只能写 `1023`，而 `1023/1024 ≈ 99.9%`，所以**永远到不了真正的 100%**，灯不会完全灭（或完全亮），差一丝。

### 6. ★ STM32 的 TIM 和 ESP32 的 LEDC 对照

| 维度 | STM32（TIM1） | ESP32（LEDC） |
|---|---|---|
| 外设性质 | 通用定时器，PWM 是它的一种模式 | 专用 PWM 外设 |
| 频率怎么定 | `Prescaler` + `Period` 两个数算出来 | 直接写 `freq_hz` |
| 分辨率 | 由 `Period` 隐含（999 → 10 位） | 显式声明 `duty_resolution` |
| 改占空比 | `__HAL_TIM_SET_COMPARE()`，立即生效 | `ledc_set_duty()` + `ledc_update_duty()` |
| 启动 | `HAL_TIM_PWM_Start()` | 通道配置完自动跑 |
| 引脚绑定 | CubeMX 选引脚 → 配复用 | 通道配置时直接写 `gpio_num` |
| 互补输出/死区 | 硬件自带（CH1/CH1N、BDTR） | 没有 |

RTOS 下两边还有两个差异：

1. **入口身份**：STM32 要 `main()` → `osKernelStart()`，业务代码必须放进任务；ESP32 的 `app_main()` **本身就是 FreeRTOS 任务**，可以直接写 `while(1)`。
2. **tick 频率会影响 `pdMS_TO_TICKS()`**：ESP-IDF 默认 `CONFIG_FREERTOS_HZ=100`，1 tick = 10ms，`pdMS_TO_TICKS(2)` 算出来是 **0**，`vTaskDelay(0)` 只是让出 CPU 不延时。要精确到毫秒级得把 tick 改成 1000，或者不用延时计时、改用 `esp_timer_get_time()` 读时间戳判断。

## 二、知识点

### 1. ★★★ `idf_component_register` 三个参数各管什么

```cmake
idf_component_register(SRCS "main.c" "led.c"
                       INCLUDE_DIRS "."
                       PRIV_REQUIRES esp_driver_gpio esp_timer)
```

| 参数 | 填什么 | 路径相对谁 |
|---|---|---|
| `SRCS` | **自己写的** `.c` 文件 | 组件目录（`main/`） |
| `INCLUDE_DIRS` | **自己写的**头文件所在目录 | 组件目录（`main/`） |
| `PRIV_REQUIRES` | **别人的**组件名，不是文件名 | —— |

口诀：**前两个说"我有什么"，后两个说"我要谁的"**。

`SRCS` 是白名单，不列进去的文件压根不参与编译，也不会出现在 `compile_commands.json` 里。ESP-IDF 没有"自动收集目录下所有 .c"这回事。

`SRC_DIRS` 能扫目录，但源码里写的是 `file(GLOB "${abs_dir}/*.c")`：**只扫一层不递归**，且不带 `CONFIGURE_DEPENDS`，新增文件后必须 `idf.py reconfigure` 才生效。所以文件少时老老实实列 `SRCS`。

`REQUIRES` 和 `PRIV_REQUIRES` 的区别：判据是**你的 `.h` 里 include 了谁**。只在 `.c` 里 include 的写 `PRIV_REQUIRES`；写在公开头文件里的写 `REQUIRES`（因为依赖你的人也得看得见）。`main` 是顶层组件没人依赖它，一律 `PRIV` 就够。

### 2. ★★★ `xxx.h: No such file` = 组件没声明，不是路径问题

ESP-IDF 里能不能 include 成功，只看**该文件的编译命令里有没有对应的 `-I` 目录**，跟文件在不在硬盘上无关。而 `-I` 目录是构建系统按 `PRIV_REQUIRES` 算出来的。

三步自查：

```bash
# 1. 这个头属于哪个组件
cd /e/a2_QianRuShi/ESP/v5.5.5/esp-idf/components
ls */include/esp_timer.h
# → esp_timer/include/esp_timer.h   → include 前面那层就是组件名

# 2. 看现在写了什么
cat main/CMakeLists.txt

# 3. 加上再 build（CMakeLists 变了会自动 reconfigure，不用删 build）
```

通配符只替换组件名那一层，`include/` 后面的路径要原样带上：`#include "driver/gpio.h"` 就查 `ls */include/driver/gpio.h`。

常用对照：

| 头文件 | 组件名 |
|---|---|
| `driver/gpio.h` | `esp_driver_gpio` |
| `driver/i2c_master.h` | `esp_driver_i2c`（5.x 老名字 `driver/i2c.h` 已删） |
| `driver/spi_master.h` | `esp_driver_spi` |
| `nvs_flash.h` | `nvs_flash` |
| `esp_timer.h` | `esp_timer` |
| `esp_log.h` / `freertos/*` | 公共依赖，**不用写** |

### 3. ★★★ ESP32 的 GPIO 中断是"查表"，STM32 是"向量表"

| | STM32 | ESP32 |
|---|---|---|
| 硬件中断源 | 每个引脚组一个（`EXTI15_10` 等） | **所有 GPIO 共用一个** |
| 入口绑定 | 编译期写死，链接器填向量表 | **运行期**查数组 `gpio_isr_func[]` |
| 怎么知道是哪个脚 | 自己在回调里比 `GPIO_Pin` | 驱动读状态寄存器拿位图 |
| 清中断标志 | 软件写 `EXTI->PR`（写 1 清零） | **驱动替你清** |
| 使能 | `EXTI->IMR` + `NVIC_EnableIRQ` | `gpio_intr_enable()` |

ESP32 的驱动里，`gpio_isr_func` 是一张**按引脚号索引的数组**，每项存 `fn` 和 `args`。中断来时读状态寄存器拿到位图，位号直接当数组下标取，所以虽然是"查表"但仍是 O(1)，没有遍历开销。

STM32 里中断标志**不清会死循环**：ISR 退出后 `EXTI->PR` 还是 1，NVIC 看到挂起标志立刻再次进同一个中断，程序卡死在中断里，主循环一行都不跑（"中断风暴"）。ESP32 没这个坑，驱动在你回调返回后统一清。

### 4. ★★★ "关 → 填 → 开" 只发生在注册阶段

`gpio_isr_handler_add()` 内部三步：

```c
gpio_intr_disable(gpio_num);                                 // 关这个脚的中断
gpio_isr_func[gpio_num].fn   = isr_handler;                  // 填函数地址
gpio_isr_func[gpio_num].args = args;                         // 填原样保存的参数
gpio_intr_enable_on_core(gpio_num, ...);                     // 开
```

**为什么必须先关**：填表是两条语句，中间可能被中断打断。如果那时中断来了，驱动会读到"`fn` 已经是我的函数、`args` 还是 NULL"的半成品，直接崩。

中断真正触发时**只查表不填表**，整个程序寿命里"填"只做一次。

`args` 存的意义：驱动只知道"0 号脚触发了"，不知道你管它叫 KEY1。把当初登记的参数原样传回去，两个键才能共用同一个回调、靠 `arg` 区分。

### 5. ★★ ISR 的三条铁律

1. **不能 `printf`**。ISR 借的是被打断任务的栈，没有任务控制块，而 `printf` 内部要拿锁、要动态分配——这些在中断上下文里没有意义甚至崩。
2. **只能用 `FromISR` 版 API**。`xQueueSendFromISR` 而不是 `xQueueSend`，因为前者不会阻塞。
3. **结尾要 `portYIELD_FROM_ISR(hp)`**。不写也能工作，但任务要等到下一个 tick 才被唤醒，默认 tick 100Hz 就是最多延迟 10ms。

`hp` 是**局部变量**，每次进中断都重新初始化为 `pdFALSE`，**不需要用完清零**。写成 `static` 才是错的——它会一直保留上次的 `pdTRUE`，导致每次中断都强制切任务。

`IRAM_ATTR` 的真正原因：ESP32 的代码默认在**外部 Flash**，靠 Cache 映射执行。写 Flash（NVS 保存、OTA）时 Cache 必须关闭，Flash 里的代码全都取不出来，此时来中断就崩。放 IRAM 等于给个安全屋。**但只有中断用 `ESP_INTR_FLAG_IRAM` 分配时才必须**；默认标志（`gpio_install_isr_service(0)`）时 Flash 操作期间中断本来就被屏蔽了，加不加都行，属于好习惯。

### 6. ★★ 事件驱动 vs 轮询

```c
// 轮询：每 500ms 主动问一次"按了吗"
vTaskDelay(pdMS_TO_TICKS(500));
if (gpio_get_level(KEY1_PIN) == 0) ...

// 事件驱动：按键那一刻才被叫醒
xQueueReceive(g_queue_key_handle, &key_state, portMAX_DELAY);
```

轮询的根本问题是**采样间隔决定漏检**——按住的时长小于 500ms 就完全抓不到。而按 500ms 以内采样，CPU 又全耗在空转上。

`portMAX_DELAY` 让任务在队列空时彻底挂起，一个指令都不执行，CPU 拿去跑别的任务。有数据时调度器唤醒它，把数据**拷贝**进缓冲区。

队列深度 5 意味着最多缓存 5 个事件，满了 `xQueueSendFromISR` 返回 `errQUEUE_FULL`，事件就丢了。

### 7. ★★ 消抖必须做在 ISR 里，时间戳必须 `static`

机械触点在闭合瞬间会弹跳，产生好几个下降沿。一次按键就能把深度 5 的队列灌满。

```c
static int64_t last_ms = 0;
int64_t now = esp_timer_get_time() / 1000;   // 微秒转毫秒
if (now - last_ms < 20) return;
last_ms = now;
```

`static` 是这里的关键：把变量放进 `.bss`，函数退出不销毁，下次进中断还是上次的值。不加就变成每次都是 0，消抖完全失效。

`esp_timer_get_time()` 返回上电以来的微秒数，它是 ISR 安全的（实现在 IRAM，只读硬件计数器）。

**两个键共用同一个 `last_ms` 会互相吞**：KEY1 触发后 20ms 内按 KEY2，KEY2 被当抖动丢掉。严格做法是按引脚分开存：`static int64_t s_last_ms[GPIO_NUM_MAX]`。

### 8. ★★ 对着原理图核对：GPIO0 是 BOOT 键，不是用户键

| 网络标号 | 芯片引脚 | 按键 | 外部上拉 |
|---|---|---|---|
| `IO0_BOOT` | 27（GPIO0） | SW2 | **R2 10kΩ → 3V3** |
| `IO11` | 20（GPIO11） | SW3 | **R111 10kΩ → 3V3** |
| `RESET` | EN | SW1 | —— |

板上就三颗键：复位、BOOT、用户键。**用户键是 GPIO11，GPIO0 是 BOOT 键。**

由此得三个结论：

1. `key.c` 里 `.pull_up_en = GPIO_PULLUP_DISABLE` 是**对的**。外部已经有 10k 上拉，再开内部上拉属于重复。
2. 下降沿触发也对：松开 = 3V3（高），按下 = GND（低）。
3. GPIO0 是 strapping 脚（启动模式选择），但**有 10k 上拉**，正常上电不按键就是高电平，能正常启动。只有上电/复位那一瞬间正好按着，才会进下载模式。所以风险没想象中大，但这颗键本来就设计成 BOOT 用，拿它做普通按键容易在调试时误触。

## 二、知识点

### 1. ★★★ 脉冲当量：从"导程"和"细分"一路算到"每毫米多少脉冲"

这条链路每一步都不能跳，跳一步后面全错。

```
丝杆导程 L = 4mm        （丝杆转一圈，螺母走多远）
步距角 1.8°             → 电机一圈 200 步
驱动器细分 1600 脉冲/转  → 实际 8 细分（200 × 8 = 1600）
每转位移 = 4mm
────────────────────────────────────
脉冲当量 = 4 ÷ 1600 = 0.0025mm/脉冲
```

反过来用：

```
走 10mm   → 4000 个脉冲
走 100mm  → 40000 个脉冲
```

**注意"螺距"和"导程"不是一回事。** 说明书上写"螺距 2，导程 4"——螺距是相邻两条螺纹的距离，导程是转一圈轴向走的距离。多线螺纹的导程 = 螺距 × 线数，这里是 2 线。**计算一律用导程。**

### 2. ★★★ "地"有三个，共地和接大地是两件事

| 名词 | 是什么 | 需不需要 |
|---|---|---|
| 大地（Earth / PE） | 埋在地里的那根线，220V 的保护地 | **适配器两脚插头就没有** |
| GND / 0V | 直流电源负极，电路的参考点 | **必须共** |
| 信号地 | 信号回流路径，本质就是 GND | 跟着 GND 走 |

**共地 = 把所有电路的直流负极连成一个点，跟接不接大地完全无关。**

为什么必须共地：信号是**电压差**。STM32 输出"高电平"是相对 STM32 的 GND 3.3V，驱动器读"高电平"是相对驱动器的 GND。两边 GND 不连，就没有共同参考点，驱动器读到的是随机值。

打个比方：两个人比身高，必须站在同一块地板上。这块地板是 GND，它不需要是地球。

**为什么两脚插头就够**：24V 是安全特低电压（SELV），适配器内部有隔离变压器，220V 侧和 24V 侧没有电气连接，输出侧是"浮地"。**浮地照样可以共地**，因为共的是各器件之间，不是对大地。

### 3. ★★★ 电容补不了堵转电流，只能补瞬态缺口

先算清楚电容到底能提供多少：

```
I = C × ΔV / t

2200μF，允许压降 0.5V，撑 1ms：
I = 2200×10⁻⁶ × 0.5 / 0.001 = 1.1A
```

**2200μF 在 1 毫秒内只能补 1.1A。** 而舵机堵转是 7.5A（三个 MG996R）。

真要补 7.5A 持续 5ms，需要：

```
C = I × t / ΔV = 7.5 × 0.005 / 0.5 = 0.075F = 75000μF
```

这么大的电容，上电瞬间充电电流会直接触发模块限流保护。

**所以电容的真实作用是这四条，不是"让模块带得动"：**

| 作用 | 说明 |
|---|---|
| 抑制纹波 | 开关电源输出有几十 mV 纹波 |
| 补偿线阻线感 | 舵机线 20cm 有 0.1Ω，7A 时压降 0.7V，就近的电容顶上 |
| 稳定反馈环路 | DC-DC 模块本身需要输出电容才不振荡 |
| 吸收换相尖峰 | 舵机内部 H 桥换向产生的高频尖峰 |

**真正解决供电的是"分路 + 时序"，不是电容：**

1. 双路模块分开带（每路 1~2 个舵机，负载降到 30%）
2. 软件错开动作（大臂转到位→停→小臂转→停→夹爪动，不要同时启动）
3. 夹爪动作加超时（夹住后一直堵转 2.5A，必须 500ms 后停止输出）

**电容要装在负载端，不是模块端** —— 它补的是线阻造成的压降，装在模块那头没意义。

### 4. ★★★ 槽配方滑块，绝不能配圆销

机械配合有一条基本规则：

| 配合 | 作用 |
|---|---|
| 圆孔配圆销 | **定位**（限制两个方向） |
| 长槽配方滑块 | **导向**（限制一个方向，允许另一个方向滑动） |
| **圆销配长槽** | **错误**，会滚 |

直码上是 6.5mm 宽的长槽。如果塞一个外径 6 的圆柱衬套进去：

- 横向只有 0.5mm 间隙（看着很好）
- **纵向能沿着槽滚 59mm**（废了）
- 而且垫片压圆柱端面是**切点接触**，不是面接触，3mm 冷轧钢反复受力会压出月牙凹坑

**正确做法：M3 螺丝直接穿过槽，用外径 10mm 的大垫片压住槽两侧的钢面。**

有人会担心"M3 螺丝在 6.5mm 槽里有 3.5mm 旷量"。但这里有个概念要分清：

| | 含义 |
|---|---|
| **可移动范围** | 螺丝松开时能在槽里滑多远 |
| **定位误差** | 锁紧后实际位置与期望位置的偏差 |

**松开时能滑 3.5mm 是"调节范围"，不是"误差"。** 锁紧后螺丝被约 200N 的摩擦力固定（M3 预紧力 500N × 摩擦系数 0.2 × 两侧），而臂的负载只有几牛，余量上百倍。

### 5. ★★ 步进驱动器的电源端必须并大电容

```
电机是感性负载
→ 每次换相，绕组电流方向反转
→ 电源线上产生尖峰，幅值可达供电电压的 2~3 倍（24V 系统能到 50~70V）
→ 没有电容吸收，驱动器 MOS 可能击穿

电机减速时，转子惯性带着电机发电
→ 能量倒灌回母线（"泵升电压"）
→ 母线电压被抬高
```

**所以在驱动器 VCC–GND 之间并 470μF/50V 电解电容，越靠近驱动器端子越好。**

耐压要按 24V 系统的 2 倍以上选，**50V 不是 16V**。

### 6. ★★ 地环路是怎么来的，怎么避免

错误接法：

```
适配器 → 驱动器 ─→ STM32 ─→ 模块 ─→ 适配器
         ↑________电流绕一圈________↓
```

电机换相的脉冲电流会在这个环路上流动，在地线上产生压降，叠加到信号上。

**症状：串口乱码、编码器丢脉冲、ADC 读数跳。**

正确做法：**星型接地**——所有 GND 从一个汇流点分出去，不要互相串联成环。洞洞板上用一条粗铜线当 GND 母线，所有器件的地都接到这条线，**只在一个点连到适配器的 24V−**。

### 7. ★★ ESP32 强在算力和无线，不强在实时控制

| | STM32F103 | ESP32 |
|---|---|---|
| 主频 | 72MHz | 240MHz 双核 |
| RAM | 20KB | 320~512KB |
| **脉冲抖动** | 定时器硬件输出，**< 1μs** | WiFi/BT 中断会打断，**可达几十 μs** |
| 无线 | 无 | 自带 |

**工业控制看"确定性"，不看"算力"。**

步进要发 40000 个脉冲走 100mm。脉冲间隔抖几十微秒就会丢步，表现是"偶尔走不准"，极难排查。

ESP32 也能发精确脉冲（用 RMT 外设，硬件不依赖 CPU），但那等于把无线功能关掉不用，只剩一个更贵的 MCU。

**架构上 PC 已经承担了视觉和语音，MCU 不需要联网，ESP32 的无线优势用不上。**

### 8. ★★ 舵机三线：中间那根永远是 VCC

| 颜色 | 功能 |
|---|---|
| 棕 / 黑 | GND |
| **红（中间）** | **VCC +5V** |
| 橙 / 黄 / 白 | 信号 PWM |

**"中间线是正极"是所有舵机的通用约定。**

但**插头顺序不一定一样**：有的是"信号-电源-地"，有的是"电源-信号-地"。接之前看线的颜色，别按排针位置硬插——信号线接到 5V 上，舵机瞬间烧。

另外 MG996R 工作电压 **4.8~6.6V**，接 12V 直接烧。24V 系统必须经降压模块转 5V。

### 9. ★★ "5A 降压模块"的 5A 是芯片能力，不是持续输出

XL4015 的 5A 是芯片手册的最大值，模块这么小的 PCB 没有散热，**持续能力大概只有 3A**。

判断一个模块能带多少，看三个东西：

1. 有没有散热片（有散热片的 3A 模块，可能比无散热片的 5A 模块更凉快）
2. 输出的电解电容容量（220μF 和 470μF 不是一个档次）
3. 卖家有没有写"建议持续 XX A"（肯写这句的通常比较实在）

**而且 DC-DC 只能降压不能升压**，24V 输入输出最高就是 24V。要给步进供 24V，只能从**模块的输入端**并联取，不能走输出。

## 二、知识点

### 1. ★★★ 有源蜂鸣器的音量下限，由工作电压决定，不由占空比决定

HNB09A05 的参数：`Driver Circuitry = 有源(内含驱动线路)`、`Voltage - Supply = 3V ~ 7V`。

```
4.8% 占空比（Pulse=6/125）   → 5V × 4.8%  = 0.24V   ← 差 12 倍
50%  占空比（Pulse=62/125）  → 5V × 50%   = 2.5V    ← 仍低于 3V 下限
NPN 低边驱动 Q2 的 Vce(sat) 再吃 0.6V → 蜂鸣器实际只拿到 4.4V
```

**结论：靠 PWM 调音量的可用区间只有 68%~100%，这个硬件上等于没有调音能力。**

要小声就串电阻或降到 3V3 供电，别指望压占空比。而且**"完全不响"和"声音小"是两种故障**，前者是电压不够起振，后者才是音量问题。

### 2. ★★★ STM32F1 在复用开漏（AF_OD）模式下，内部上拉是失效的

```c
GPIO_InitStruct.Mode = GPIO_Mode_AF_OD;
GPIO_InitStruct.Pull = GPIO_PULLUP;   // ← 这一行在 F1 上没有用
```

`Pull` 字段**只在输入模式下生效**。AF_OD 输出时引脚由外设驱动，内部上下拉电路不参与。

所以 I2C 的 SCL/SDA **只能靠外部上拉电阻**，软件救不了。拔掉 OLED 模块后 PB6/PB7 悬空实测 0V，就是这个缺陷的直接体现。

### 3. ★★★ I2C 总线悬空的连锁反应：从机状态机错位 → HAL_BUSY

```
排针接触一松 → 失去上拉 → PB6/PB7 悬空
  → 悬空的开漏线被人体电容 / 50Hz 工频拉低
  → SSD1306 收到乱码时钟+数据，内部状态机错位
  → 主机发 START 时检测到 SDA 低 → HAL_BUSY，连从机地址都发不出去
  → 之后所有传输立即失败 → 屏冻在旧画面
```

**实测铁证：手指碰一下 PB7（或测量时手碰到表笔金属头），屏立刻卡死。** 有上拉的话最多丢一帧，不会卡死 —— 差别就是总线上有没有那 0.7mA 在把它拉回高电平。

两个状态码指向不同硬件问题，别混：

| 返回码 | 含义 | 指向 |
|---|---|---|
| `st=2` HAL_BUSY | 总线被拉低 | 没上拉 / 短路 / 从机把线拽住 |
| `st=3` HAL_TIMEOUT | 地址发出去了没人应答 | 从机没供电 / 地址错 / 器件坏 |

### 4. ★★ 间歇性故障要用漏桶判定，不能用"连续 N 次失败"

原逻辑：

```c
if (失败) fail_count++;
else      fail_count = 0;        // ← 一成功就清零
if (fail_count >= 16) 判离线;
```

间歇性故障时，攒到第 15 次突然成功一次，计数清零，**永远攒不满 16**。表现是 `s_online` 一直为真，屏冻在 74 秒的画面却跑了四十多分钟。

改成漏桶：

```c
if (失败) err_score += 4;
else      err_score -= 1;        // 成功只减 1，不清零
if (err_score >= 16) 判离线;
```

**判据：能衰减、但不轻易归零的计数器，才认得出"大部分时候失败"这种状态。**

### 5. ★★★ 垂直轴丝杠会不会自己滑下去，取决于螺旋升角，不取决于电机

先分清两件事：

- **通电时**：步进电机有保持力矩（42 步进约 3.5 kg·cm），T8 导程 8mm 效率 0.6 → 推力约 16 kgf，扛得住整条臂。
- **断电时**：步进电机**没有保持力矩**，只剩 3~5% 的磁阻。这时能不能停住，纯看丝杠自锁。

自锁条件：**螺旋升角 λ < 摩擦角 φ**（钢-铜约 4~6°）。

```
λ = atan(导程 / (π × 中径))     T8 中径约 7mm
```

| T8 规格 | 导程 | λ | 自锁 |
|---|---|---|---|
| 1 线（螺距 2） | 2mm | 5.2° | 勉强自锁 |
| 2 线 | 4mm | 10.3° | 不自锁 |
| 4 线 | 8mm | 20° | 完全不自锁 |

工业上垂直轴用滚珠丝杠也不自锁，标准做法是**抱闸电机或配重块**。DIY 最便宜的办法是一根拉簧做配重（5 元），顺便减小电机负载。

### 6. ★★★ 机械臂构型决定逆运动学难度，差三个量级

| 构型 | 逆运动学 | 需要的数学 |
|---|---|---|
| **SCARA**（水平二连杆+升降） | 余弦定理求肘角，atan2 求肩角，两解取一 | **高中三角函数** |
| 圆柱坐标（旋转+直线伸缩） | 三轴完全解耦，各算各的 | 加减乘除 |
| 6 轴关节型 | DH 参数 + 齐次变换矩阵 + 雅可比 + 多解筛选 | 线性代数、矩阵 |

SCARA 的全部公式：

```
r = sqrt(x² + y²)
cos(θ2) = (r² - L1² - L2²) / (2·L1·L2)      → θ2 = ±acos(...)  两解
θ1 = atan2(y, x) - atan2(L2·sin θ2, L1 + L2·cos θ2)
```

**"画圆"不是单独写的算法**，是给定圆周上一串点、逐点代入上面公式的自然结果。

选构型时这条比"看起来简不简单"重要得多 —— 6 轴的机械看着差不多，数学门槛高一个数量级。

### 7. ★★ SCARA 构型下重力不产生关节转矩，但会产生径向负载

臂在**水平面**内旋转时，重力方向与舵机输出轴平行，**不产生绕轴的力矩**：

```
臂总重约 185g，重心半径 150mm
转动惯量 I ≈ 0.0042 kg·m²
加速时需要扭矩 ≈ 0.04 kg·cm
```

MG996R 有 9.4 kg·cm，余量三个数量级。这也是它跟 MeArm 的本质区别 —— MeArm 的臂是竖着举起来的，重力全压在舵机转矩上，2.2 kg·cm 的 MG90S 连 50g 都费劲。

**但径向负载是另一回事**：臂重垂直压在输出轴上，全靠舵机内部轴套扛，跑久了会松。工业做法是关节用轴承承重、电机只输出扭矩；DIY 短期可以直接扛，但要知道精度衰减是从这儿来的。

### 8. ★★ 舵机 180° 和 360° 不是"范围大小"的区别

| | 180° 角度舵机 | 360° 连续旋转舵机 |
|---|---|---|
| 1500μs | 停在 90° | **停止不动** |
| 2000μs | 转到 135° | **正转，速度与偏差成正比** |
| 输入含义 | **目标角度** | **转速 + 方向** |

360° 拆掉了角度反馈电位器，只知道"转多快"，不知道"转到哪"。**凡是要定位的关节，必须 180°。**

另外 180° 舵机在 0°/180° 附近会顶到机械限位，堵转电流 2.5A，几分钟就烧。软件限到 10°~170°，超范围直接拒绝执行。

## 三、踩的坑

1. **蜂鸣器一直以为是占空比压太低**（4.8%），改到 50% 才发现还是 2.5V，低于 3V 工作下限。**先查器件的工作电压范围，再调 PWM**，顺序反了白折腾半天。
2. **OLED 卡死查了很久都往软件上找**，根因是硬件缺上拉电阻。判据是"手指碰一下 I2C 线就卡死" —— 有上拉的话干扰最多丢一帧，不会锁死。
3. **"连续 16 次失败才判离线"这个设计在间歇故障下完全失效**，一成功就清零，永远攒不满，导致 `s_online` 假在线。
4. **选滑台只看行程，没看导程**。75 元那个是导程 8mm（4 线丝杠），立起来断电会自己滑下去；而且行程只有 23mm，抓 20mm 高的方块抬起来就会撞到旁边的。
5. **一开始把立柱码垛机理解成"旋转 + 直线伸缩"的圆柱坐标**，实际看视频里是"两个水平旋转关节 + 立柱升降"，属于 SCARA。构型认错了，逆运动学的难度判断和结构方案全得重来。

# 11.2 笔记

## 一、干了什么

1. 把中控板从裸机重构成 FreeRTOS：拆出 LoRa 接收、MQTT、OLED 三个任务，全链路（小程序 → 巴法云 → MQTT → LoRa → 终端板 → 闭环确认）跑通，行为和裸机版一致。
2. 用二值信号量替掉 `while(!rx_done) HAL_Delay(1)` 的轮询，接收零丢帧。
3. 终端板加光照采集（ADC + DMA）和蜂鸣器（TIM4_CH4 PWM），并把两者联动。
4. 巴法云新建蜂鸣器主题 `krzIenwb5006`，接通 MQTT 手动控制蜂鸣器。
5. 蜂鸣器始终不响，用 ACK 帧 + GPIO 自检把问题从"整条链路"缩到"PWM 或硬件"，最终定位到蜂鸣器本体，明天继续。

## 二、知识点

### 1. ★★★ `osKernelStart()` 之前不许有任何阻塞或死循环

CubeMX 保留 `USER CODE BEGIN 2` 区，老工程那句 `app_main();` 留在原地。而 `app_main()` 内部是 `while(1)`，永远不返回：

```c
MX_FREERTOS_Init();
osKernelStart();     // ← 永远执行不到
```

**后果不是报错，是"板子照常跑裸机逻辑，你完全看不出 RTOS 没启动"。**

这是移植最容易踩的一脚，因为所有外设初始化都正常，串口也正常打印，只有调度器没起来。

**铁律：`main()` 里 `osKernelStart()` 之前只允许配外设，不许有任何业务逻辑。**

### 2. ★★★ `delay_ms` 改 `vTaskDelay`，一行解决 12 秒调度器停摆

```c
void delay_ms(int nms) { HAL_Delay(nms); }              // 改前
void delay_ms(int nms) { vTaskDelay(pdMS_TO_TICKS(nms)); }  // 改后
```

`HAL_Delay()` 是"读 uwTick 死等到够数"，**全程占着 CPU 不让出**。而 `esp_mqtt_init()` 里有 6 个 `delay_ms(2000)`，合计 12 秒。

改之前的串口是**完全静默 12 秒**（LoRa 那 6 帧全丢）；改之后两个任务交错输出：

```
[21:29:10.836] [init] 7/10 connect_server     ← MQTT 在连服务器
[21:29:11.304] [lora] #9  type=1 v1=252 v2=590   ← LoRa 同时收数据
[21:29:13.003] [init] 8/10 entry_transparent
[21:29:13.309] [lora] #10 type=1 v1=251 v2=589
```

**只改底层一个函数，上层几十处调用全部自动生效。**这比逐个替换调用点可靠得多。

### 3. ★★★ 中断 → 信号量 → 任务，替掉轮询

```c
// 裸机：等的时候 CPU 原地空转
while (!rx_done && !rx_timeout) {
    if (HAL_GetTick() - start > 60) break;
    HAL_Delay(1);
}

// RTOS：等的时候任务挂起，CPU 让给别人
xSemaphoreTake(g_lora_rx_sem, pdMS_TO_TICKS(60));
```

**驱动写成双模式最划算**：信号量为 NULL 时自动退回轮询，这样同一份 `llcc68_p2p.c` 在裸机工程和 RTOS 工程都能用，不用维护两份。

两个细节：
- 中断里 `xSemaphoreGiveFromISR(sem, &woken)` 之后必须 `portYIELD_FROM_ISR(woken)`，否则要等下一个 tick 才切任务
- `Take` 之前先清一遍残留（`while (xSemaphoreTake(sem, 0) == pdTRUE) {}`），否则上一轮的 give 会让这次立刻返回，表现为"收得特别快但全是垃圾数据"

### 4. ★★★ 能在中断里调 FreeRTOS API 的优先级，必须 ≥ `configMAX_SYSCALL_INTERRUPT_PRIORITY`

CubeMX 给 EXTI15_10 配的是 **3**，而 `configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY` 是 **5**。

STM32 的 NVIC 是**数值越小优先级越高**，所以 3 比 5 更"高"，属于 FreeRTOS 管不着的层级。在里面调 `xSemaphoreGiveFromISR` 会命中 `vPortValidateInterruptPriority()` 的断言。

**现象是"一收到 LoRa 就死机"**，而且不会告诉你是优先级的问题。

改法：`HAL_NVIC_SetPriority(EXTI15_10_IRQn, 6, 0);` 写在 `MX_FREERTOS_Init()` 里，别改 `Core/Src/gpio.c`（Generate 会冲掉）。

### 5. ★★ 队列的两个参数决定语义，别乱配

| 用途 | 深度 | API | 理由 |
|---|---|---|---|
| 环境数据（LoRa → MQTT） | **1** | `xQueueOverwrite` | 上报只要最新值，旧的覆盖掉，慢的一方不会积压 |
| 控制指令（MQTT → LoRa） | **4** | `xQueueSend` | 连点几下不能丢 |

深度 1 + `Overwrite` 是"永远保留最新"的标准写法；深度 1 + `Send` 会变成"满了就丢新数据"，语义正好相反。

### 6. ★★ 两个触发源控制同一个执行器，必须先用标志合成再执行

蜂鸣器有两个触发源：光照太暗、巴法云下发 `on`。

**错误写法**（两边各自调 `BEEP_Alarm`）：

```c
if (太暗)     BEEP_Alarm(1);
if (变亮了)   BEEP_Alarm(0);
if (远端 on)  BEEP_Alarm(1);
```

MQTT 刚让它响，200ms 后光照判断"不够暗"立刻把它关掉，**互相打架**。

**正确写法**：各自只改自己的标志，在固定节拍里统一合成。

```c
static uint8_t beep_by_light, beep_by_remote;

每 20ms：BEEP_Alarm(beep_by_light || beep_by_remote);
```

这条对任何"多来源控制一个设备"的场景都成立（比如以后的电机、继电器）。

### 7. ★★ 没有串口时的调试手段：让对端回一帧 ACK

终端板的 CH340 接触不良，看不到它的打印，"指令发到了没"完全抓瞎。

解法：**让终端板收到控制帧后立刻回一帧 ACK**，借中控板的串口打出来。

```c
// 终端板
frame_build(frame, TYPE_ACK, CMD_BEEP, beep_by_remote, s_led_state);
llcc68_lora_send(&llcc68_ctx, frame, FRAME_LEN, 1000);
```

```
[lora] *** ACK from terminal: cmd=0x03 val=1
```

`val=1` 这一条就把"指令到了、进对了分支、变量置对了"全部证明掉，**问题范围立刻从"整条链路"缩到"PWM 或硬件"**。

**这是"链路分段验证"思路的具体实现**：哪一段看不到，就让它的对端帮你把结果带出来。

### 8. ★★ J-Link ARM-OB 的速度，两块板不一样

| 板 | 可用速度 | 现象 |
|---|---|---|
| 中控板 | 400kHz | 正常 |
| 终端板 | **100kHz** | 400kHz 报 `Verification of RAMCode failed` |

`RAMCode` 是 J-Link 下载算法（跑在目标 RAM 里），写进去读回来不一致就是速度太快。**看到这个错误先降速，别怀疑接线。**

这块 J-Link 是 2012 年固件的克隆 OB，对速度很挑。

### 9. ★ 阻塞式接收会把"20ms 节拍"拖成 1 秒

终端板主循环：

```c
while (1) {
    20ms 节拍块           // 想每 20ms 跑一次
    ...
    receive_data(1000);   // 但这里阻塞 1000ms
}
```

节拍块实际每 1 秒才执行一次。**凡是在主循环里塞"高频节拍"的，先检查循环里有没有阻塞调用。**

修法：把接收超时降到 20ms，让循环真正转起来（代价是每圈多几次 `receive_mode` 的 SPI 配置开销）。

### 10. ★ 有源蜂鸣器的 PWM 占空比不能太低

8kHz × 4.8% = 每个周期只通电 **6 微秒**。

有源蜂鸣器的机械响应时间是几十微秒量级，**6us 根本来不及让它动**。表现是"完全不响"，而不是"声音小"。

**降音量要靠占空比，但下限大约在 20~30%**，再低就起不了振。真要更小声，串电阻比压占空比可靠。

## 三、RTOS 概念速查（附本项目实际用法）

下面这张表按"通用概念 / 本项目用了没"对照着记。**只看概念容易飘，标上实际状态才知道自己真正掌握了什么。**

| 概念 | 本质 | 本项目实际状态 |
|---|---|---|
| **Task** | 拥有独立栈的无限循环函数 | ✅ 4 个任务。没有进程隔离，所以全局变量是共享的 |
| **NVIC 优先级** | 中断的抢占等级，数值越小越高 | ⚠️ EXTI15_10 从 CubeMX 的 3 **改成 6**。必须 ≥ `configMAX_SYSCALL_INTERRUPT_PRIORITY`(5) |
| **EXTI** | 外部中断，感知突发事件 | ✅ DIO1(PB10) 用上升沿。⚠️ **PB12 按键中断里还有 `delay_nms(15)` 空转，RTOS 下要删** |
| **DMA** | 硬件搬运数据，不占 CPU | ✅ 终端板 ADC1 用它搬 `adc1_value[]`，**连续模式，没开 DMA 中断**（用不上信号量） |
| **二值信号量** | 0/1 标志，做同步通知 | ✅ `g_lora_rx_sem`。中断 give、任务 take，替代了 `while(!rx_done)` 轮询 |
| **队列** | 任务间传数据，自带同步 | ✅ 两个，方向相反：`env_queue`（深度1+Overwrite）和 `cmd_queue`（深度4+Send） |
| **互斥量 Mutex** | 带所有权的二值信号量，支持优先级继承 | ❌ **一个都没用**。`configUSE_MUTEXES=1` 只是开了编译开关 |
| **SPI** | 4 线高速总线（SCK/MOSI/MISO/CS） | ✅ 驱动 LLCC68。**只有 `loraTask` 用，单任务独占所以不需要锁** |
| **I2C** | 2 线低速总线（SCL/SDA），开漏+上拉 | ✅ 驱动 OLED。**只有 `oledTask` 用，也不需要锁** |
| **UART** | 点对点串口 | ✅ 中控板 USART2 接 ESP12-F。⚠️ 它是 `HAL_UARTEx_ReceiveToIdle_IT` 空闲中断收整包，**不是 DMA 方式** |
| **CS 片选** | 告诉 SPI 从机"在跟你说话" | ⚠️ LLCC68 的 NSS 在 `llcc68_hal.c` 里手动拉。**将来如果多个任务用 SPI，拉 CS 和发数据必须是一个原子段，在锁里面做** |
| **delay_us()** | 忙等待，占着 CPU 不让出 | ⚠️ 终端板 DHT22 还在用，而它**借 SysTick 当定时器**。RTOS 下要么换 DWT，要么用 `vTaskSuspendAll` 包住 |
| **vTaskDelay()** | 挂起任务，让出 CPU | ✅ `osDelay` 全是它。**关键收益：`esp_mqtt_init()` 那 12 秒不再卡死 LoRa 收数** |
| **portYIELD_FROM_ISR** | 中断里触发立即切换 | ✅ `DIO1_EXTI_Callback` 里调了。不调的话要等下一个 tick 才切任务，延迟 1ms |

**一句话总结这张表**：真正在用的只有 **Task、信号量、队列、vTaskDelay、EXTI→信号量** 这五样；Mutex、DMA 中断、事件组、任务通知都还没碰。**"学过"和"用过"是两件事，别混。**

### 本项目实际的完整数据流

```
                     ┌──────────── 中断层（只做"短平快"）────────────┐
  终端板发帧 ──空中──> DIO1(PB10) 上升沿 → EXTI15_10_IRQn
                     → HAL_GPIO_EXTI_Callback()
                     → DIO1_EXTI_Callback()   读 IRQ 状态+清除
                     → rx_done = true
                     → xSemaphoreGiveFromISR(g_lora_rx_sem)
                     → portYIELD_FROM_ISR()
                     └───────────────────┬───────────────────────────┘
                                         │ 唤醒
                     ┌───────────────────▼───────────────────────────┐
                     │ loraTask（AboveNormal / 1KB）                  │
                     │ 1. receive_mode(0)     进连续接收              │
                     │ 2. receive_data(50)    → xSemaphoreTake(50ms)  │
                     │ 3. 四查：长度/帧头/设备ID/校验和               │
                     │ 4. 更新 g_disp 快照（给 OLED 用）              │
                     │ 5. env_queue ← xQueueOverwrite(温度湿度)       │
                     │ 6. cmd_queue → 取指令，搭车发控制帧             │
                     └───────┬───────────────────────┬───────────────┘
                             │ env_queue(深度1)      ▲ cmd_queue(深度4)
                             ▼                       │
                     ┌───────────────────────────────┴───────────────┐
                     │ mqttTask（Normal / 1.5KB）                     │
                     │ 1. xQueueReceive(env) → esp_mqtt_set_env()     │
                     │ 2. esp_mqtt_poll()：收指令/心跳/10秒上报        │
                     │ 3. esp_mqtt_take_cmd/beep → cmd_queue          │
                     │ 4. osDelay(20)    ← 主动交出 CPU               │
                     └───────────────────────────────────────────────┘

                     ┌───────────────────────────────────────────────┐
                     │ oledTask（BelowNormal / 1KB）                  │
                     │ 拷 g_disp 快照 → 刷 4 行 → osDelay(1000)      │
                     └───────────────────────────────────────────────┘

   SysTick（FreeRTOS 独占）每 1ms 一跳 → 决定谁上 CPU、谁去睡觉
   TIM2（HAL 时基）每 1ms 一次     → HAL_GetTick() 靠它递增
```

**和通用架构图的区别，正是本项目最该记住的地方**：

1. **没有 Mutex** —— 每个外设只有一个任务碰，用不着锁。将来加第二个 SPI 设备才需要。
2. **没有 DMA 中断** —— ADC 连续转换，任务随时读最新值，比"搬完发信号量"更简单。
3. **有两条独立队列，方向相反** —— 这是双板架构决定的：环境数据往上传（只要最新），控制指令往下传（不能丢）。
4. **两个 1ms 时基分开** —— SysTick 归 FreeRTOS，TIM2 归 HAL。混用一个就是死锁。

## 四、踩的坑

1. **`app_main()` 挡在 `osKernelStart()` 前面**，RTOS 压根没启动，而所有外设看起来都正常。这个坑不报错、不报警，只能靠"任务里加心跳打印"发现。
2. **任务启动那两行打印只出现一次**，串口抓晚了就错过，差点误判成"任务没创建"。判据：看 `heap_free` 掉了多少 —— 掉了约 1200 字节就说明任务和信号量都建成功了。
3. **通过 bash 传给 `python -c` 的字符串会被两层转义**，`printf("...\r\n")` 里的 `\r\n` 变成真实换行，字符串字面量跨行，编译报 `missing closing quote`。以后这种改动用脚本文件，别用 `-c`。
4. **CubeMX 生成的是 `Template.uvprojx`，不是覆盖 `Terminal.uvprojx`**。两个 `.ioc` 的 ProjectName 都是 `Template`，所以每次 Generate 都新生成一个工程文件，原来的分组一个都不继承。

## 五、遗留

1. **蜂鸣器不响**（明天第一件事）。已排除：MQTT 链路、LoRa 下行（有 ACK）、TIM4 时钟和 PB9 复用配置、占空比过低。待验证：GPIO 直推能不能响、蜂鸣器是有源还是无源/三脚（**三脚是低电平触发，和现在的代码极性相反**）。
2. **终端板节拍被 1 秒阻塞拖慢**，蜂鸣器节奏会是"响 1 秒停 1 秒"，不是要求的 200/300ms。
3. **OLED 字库曾被链接器裁掉**（`RO-data` 只有 352 字节），现在 OLED 任务已经用上了，下次编译要留意 RO-data 应该回升到 15KB 左右。
4. **调试打印要收拾**：`esp_mqtt.c` 里那句 `[MQTT] rx topic=[..] payload=[..]` 是诊断用的，稳定后删掉。
5. **终端板还没移植 RTOS**，按计划压后，先解决蜂鸣器硬件。
6. **中控板按键中断里的 `delay_nms(15)` 还留着**：`ISR_callback.c` 的 `HAL_GPIO_EXTI_Callback()` 里，`GPIO_Pin == GPIO_PIN_12` 分支空转 15ms 做"软件去抖"。PB12 和 LoRa 的 DIO1(PB10) 同属 `EXTI15_10_IRQn`，按一下键就把 LoRa 中断堵住 15ms —— 正好可能错过终端板那一帧。RTOS 下的正确做法：中断里只置标志发信号量，去抖交给任务用 `vTaskDelay` 做。
