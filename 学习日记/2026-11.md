# 11.24 笔记

> 今天两件事：机械臂三层堆叠跑通（顶层偏移 ≤5mm），ROS2 装好并跑通 demo。
> 一句话：从「能动」到「能叠」—— 堆叠把平面搬运时被掩盖的三个耦合问题全暴露出来了。

## 一、干了什么

1. 木块到货，三层堆叠从手动逐条试改成脚本，最终**顶层相对底层累计偏移 ≤5mm**，第 3 次时前两块直接重合。
2. 试出同步下降的安全判据（Z 耗时 ≥ M 耗时），把整条序列从 130 秒压到 115 秒。
3. ROS2 在虚拟机装好，跑通 talker / listener，用 `topic list / echo / hz` 验证了整条链路。

## 二、知识点

### 1. ★★★ 堆叠时 Z 值不能固定递减 —— 塔高在变，夹持位置也在变

直觉做法是「每叠一层，Z 减一个块高（15mm）」。**实测不行。**

原因是有两个变量同时在动：

| 变量 | 方向 | 后果 |
|---|---|---|
| 塔顶变高 | Z 要**加** 15 | 不加就压穿前一块 |
| 抓取夹持位置 | 抓底块只能夹偏上沿 | 块底相对爪尖的距离变大，落点要**减** |

所以第三块不是 `17 + 15 + 15 = 47`，而是 **46**。

**判据**：抓取时如果夹爪已经下不去（块贴地），必然是夹偏上沿，那一次的放置 Z 就要比理论值低 1~2mm。

### 2. ★★★ 改水平坐标会连带改 Z —— 三个量是耦合的

落点从 `M 190` 改到 `M 211`（补足 10cm 位移）后，**所有放置 Z 都要 +4**。

因为臂伸得更远 → 下垂更大 → 同一个 Z 指令的实际高度更低。实测同一块木块：
- `M 190` 处 `Z 15` 刚贴地
- `M 211` 处要 `Z 17` 才贴地

**教训**：改坐标不能只改坐标。**水平位置、下垂量、Z 高度三者绑在一起，动一个必须重算另外两个。**

### 3. ★★ 同时动两轴的安全判据：Z 的耗时 ≥ M 的耗时

去程想「边走边降」省时间，但不能一刀切。

| 情况 | 谁先到位 | 末端动作 | 安全 |
|---|---|---|---|
| Z 慢 | M 先到位 | 到位后**竖直下降** | ✔ |
| Z 快 | Z 先到位 | 在低高度**水平扫** | ✘ 撞到塔 |

实测：第 3 块 Z 只降 4mm（0.4 秒），M 要 1.8 秒 → Z 先到位，块底以 30mm 高度水平飞 121mm 撞向塔顶。**必须串行。**

### 4. ★★ 背隙 ≠ 回程误差

| 术语 | 是什么 | 能不能单独测 |
|---|---|---|
| **背隙**（backlash） | 纯机械间隙，齿轮咬合有缝，反向先走空程 | 不能，和弹性变形混在一起 |
| **回程误差**（hysteresis） | 正反两个方向接近同一点，落点的差值 | 能，就是实测到的那个数 |

**所以应该说「我测的是回程误差」，不是「我测了背隙」。** 面试官追问「怎么把弹性变形分离出去」，答案是「分不开，软臂的变形和齿隙外观一样」。

★ 夹爪其实早就做过背隙补偿：两段式「先过冲到 1000/1600 再退 20μs」，本质就是吃干净齿隙。

### 5. ★★ ROS2 的最小验证链路：list → echo → hz

| 命令 | 看什么 |
|---|---|
| `ros2 topic list` | 现在有哪些话题在跑 |
| `ros2 topic echo /chatter` | 话题里流的是什么数据 |
| `ros2 topic hz /chatter` | 数据实际多快来、抖不抖 |

实测 `/chatter` 上是 `Hello World: 73 → 74 → 75...` 逐条递增，说明 talker 是持续发布、不是只发一条。
`ros2 topic hz` 读出 **average rate 1.000，std dev 0.0003s**（窗口 4）——
talker 默认 1 秒发一次，抖动只有零点几毫秒。**这个 std dev 就是「通信是否确定性」的第一个可量化指标。**

## 三、踩的坑

1. **堆叠脚本第一次跑忘了做位移补偿。** `M 90 → M 190` 以为走了 10cm，实际只有 8.4cm。
   原因和平面搬运那次一样：**指令距离 ≠ 实际距离，远端下垂让行程按比例缩水。**
   **教训**：换个工作点就得重新标定，旧点的补偿值不能直接搬。

2. **放置 Z 一次给太高，木块落地会「飘」。** 依次试了 19 → 18 → 17 才对。
   飘的原因是块底离台面还有 1~2mm，张开夹爪时它自由落体，落地瞬间被自己的重心带偏。
   **判据：块落下时有轻微的「落定感」而不是「飘一下」才对。**

3. **ROS2 卡在自己写 Python pub/sub。** demo 跑通了但自己从零写节点写不出来，时间也花没了。

## 四、遗留

1. **回程误差没测**：`M 224→200` 与 `M 176→200` 的落点差，决定了 ±4mm 这个数到底算不算「双向」。
2. **堆叠顶层偏移的具体数值没量**：只确认了 ≤5mm，x / y 两个分量没有分开记。
3. **ROS2 Python pub/sub 没写出来**：这是 D1 的目标，顺延。

# 11.23 笔记

> 今天全天在机械臂：本来是去测重复性的，结果挖出一个藏得很深的系统性偏差。
> 一句话：从"落点差 15mm 查不出原因"到"根因是夹爪倾斜，补偿后 ±4mm"。

## 一、干了什么

1. 用标定板逐点实测行程，确认 `M 100 0` → `M 200 0` 指令走 100mm、实际只走 85mm。
2. 用 `S` 回显排除固件问题：`M 80/160/60` 三个位置回的都是 `POS 79/160/60`，逆解正解完全自洽。
3. 两点标定出补偿关系（目标 130 要发 137、目标 180 要发 198），放置点从 `M 200 0` 改到 `M 224 0`。
4. 实测"物体底部刚碰台面"的 Z 指令值（`M 100` 处约 16、`M 158` 处 25、`M 224` 处 35），把序列 Z 从 5/10 重定成 15/34。
5. 连跑 5 遍，落点偏差做到 ±4mm。

## 二、知识点

### 1. ★★★ `S` 回显自洽 ≠ 物理位置正确

`S` 打印的 `POS` 是拿 `s_st[].cur_deg`（软件跟踪值）做正解算出来的，而正解用的又是和逆解同一套 L1/L2。
**逆解和正解互为反函数，永远自洽**，跟舵机实际转了多少度零关系。

所以"发 `M 80` 回 `POS 79`"只能证明固件算得对，**证明不了机械臂真的走到了 80mm**。

**判据**：想知道真实位置，只能靠外部测量（标定板、钢尺、铅垂线），不能靠回显。

### 2. ★★★ 末端下垂让夹爪朝里倾斜，行程按比例缩水

下垂不只是"末端变低"，它会让**夹爪不再竖直向下，而是朝回转中心倾斜**。

夹爪是根约 120mm 的杠杆，倾斜 β 时爪尖横向偏移 `120 · sin β`。
r 越大 → 臂越直 → 下垂越狠 → β 越大 → 偏移越多，于是行程看起来按比例缩短。

| 区间 | 指令行程 | 实际行程 | 系数 |
|---|---|---|---|
| 50～100mm | 61mm | 50mm | 0.82 |
| 100～120mm | 27mm | 20mm | 0.74 |

**系数递减，是非线性的**，不能拿一个固定比例套全行程。

★ 指纹判据：**用手托一下末端，位移立刻恢复** —— 这个现象一出现，就是倾斜，不是臂长标定错了。

### 3. ★★★ 倾斜补偿和"物体接触台面"互斥

补偿是在**悬空状态**下标定的。物体一接触台面，地面反力从末端传回舵机，抵消一部分下垂，
倾斜变小，实际需要的补偿量就比标定值小。

**但完全悬空又不行**：实测 `Z 25` 张开夹爪纸巾直接翻倒，`Z 24`（压下 1mm）姿态就稳。

| 状态 | 落点稳定 | 补偿有效 |
|---|---|---|
| 完全悬空 | 会翻 | 完整 |
| 轻压 1～2mm | 稳 | 被削弱 |

**鱼与熊掌，取"轻压 1mm"** —— 演示里没人看得出差几毫米，但物体翻了就穿帮。

### 4. ★★ Z 值必须按"触地点"实测，不能沿用旧值

物体底部刚碰台面的那个 Z 指令值就是触地点，**它随位置变**：

| 位置 | 触地点 Z |
|---|---|
| `M 100` | ≈16 |
| `M 158` | 25 |
| `M 224` | 35 |

每往外 66mm 半径，触地点抬高 10mm（下垂斜率 0.15mm/mm，与水平偏移斜率 0.18 同量级，
说明是同一个物理机制）。所以取 `Z = 触地点 − 1`（压下 1mm）。

原来那套 `Z 5`/`Z 10` 在 `M 224` 处会**把物体往地里压 25mm**。

## 三、踩的坑

1. **直接沿用了 11-21 的 Z 值（`Z 5` / `Z 10`）**，没意识到下垂让触地点整体抬高了一截。
   结果放置时物体被压进台面 25mm，地面反力把下垂顶回去，倾斜补偿全废。
   **教训**：Z 值不是绝对量，它跟着姿态走，换工作点就得重测触地点。

2. **用圆弧边的纸巾当被测物体**，读数噪声有 ±3mm，比钢尺还不准。
   **教训**：测精度要用直角边的硬物，软的东西一压就变形，边缘还会飘。

## 四、遗留

1. 木方块到了重测触地点（现在这套 Z 值只对约 60mm 高的纸巾包有效）。
2. 堆叠测试：第二层接触面变成方块顶面，Z 值又要重来，而且更需要轻压（悬空释放会滑）。
3. 用直角边方块重做一次干净的重复性验收，把 ±3mm 的读数噪声压掉。
4. 补拍横向整机照、夹爪抓取特写、落点俯视图。

## 二、知识点

### 1. ★★★ GitHub 把成对的半角 `~` 当删除线语法

写 `工作半径 35~305mm；建议 120~280mm`，本地编辑器看着正常，GitHub 上渲染成
「35305mm；建议 120280mm」中间带一条删除线。

原因是 GFM（GitHub Flavored Markdown）支持用 `~文字~` 表示删除线。两个 `~` 之间的内容
被整段划掉，首尾的数字留在外面拼到了一起。

| 写法 | 结果 |
|---|---|
| `35~305mm` | 两个 `~` 配对 → 中间被划掉 |
| `35～305mm`（全角 U+FF5E） | 正常显示 |
| `` `35~305mm` ``（行内代码） | 正常显示，不解析 |

**改法**：正文和表格里的范围符号一律用全角 `～` 或 `–`（en dash）。
代码块和行内代码里的 `~` 不用改（如 `` `W <0~180>` ``、`` `us_min~us_max` ``）。

★ 数学表达密集的文档最容易踩这个坑，一次能中几十处。

### 2. ★★ 视频转循环动图用 WebP，不用 GIF

同样画质下 WebP 动图体积只有 GIF 的三分之一到一半，而且 GitHub 的 `<img>` 标签原生支持
循环播放。2MB 的 mp4 转 GIF 会破 10MB，转 WebP 只有 1.65MB。

生成方法（Python + OpenCV 读帧，PIL 存动图）：

```python
frames[0].save("demo.webp", "WEBP", save_all=True, append_images=frames[1:],
               duration=100, loop=0, quality=55, method=6)
```

降低体积的三个旋钮：**帧率**（15 → 10 fps）、**尺寸**（限宽 360）、**quality**（62 → 55）。

### 3. ★★ 抽帧网格法：一分钟看清一段长视频的内容

65 秒的演示视频，不知道哪一段有完整动作。做法是每 5~6 秒抽一帧，缩成 180×320 的缩略图，
拼成 4×3 的网格图，每格左上角标上时间戳。**一张图就能定位动作区间**，比拖进度条快十倍。

对视频剪辑、录屏整理都适用。

### 4. ★★ 示教-复现的等待时间必须按实际耗时算

示教脚本给每条命令固定等 3 秒，但实际耗时差异很大：

| 命令 | 实际耗时 | 该给多少 |
|---|---|---|
| `HM` 舵机回位 | 3 秒斜坡 | `!4` |
| `M` 平移 65mm | 约 1.5 秒 | `!3` |
| `C` 夹爪开合 | 约 1 秒（两段式） | `!3` |
| `Z` 升降 45mm | **4.5 秒**（10mm/s） | `!6` |
| `H` 回零 | 1~5 秒（看起点高度） | `!8`，且必须排第一条 |

**等待时间不够的后果不是"报错"，是下一条命令把上一条的目标覆盖掉**——机械臂半路改方向，
回放出来的轨迹和录的时候完全两样，而且不报任何错。

★ `H` 回零必须在所有 `Z` 命令之前，因为"已回零"这个标志要等 `HOME_DONE` 才置位，
早发 `Z` 会直接报"没回零"。

### 5. ★ 开源仓库的体积清理：删什么、留什么

一个 112MB 的开发目录，清理到 8MB 的原则：

| 处理 | 内容 |
|---|---|
| **删** | Keil 编译产物（`Arm/` 目录 30MB）、`.7z/.rar/.mp4/.stp`、别人的完整工程、数据手册 PDF |
| **留** | 自己写的业务代码（1KB 级）、HAL 库（3.8MB，别人 clone 下来要能直接编译） |
| **外置** | 演示视频压到 2MB 放仓库，或者传 B 站只放链接 |

★ **`.gitignore` 必须在第一次 `git add` 之前写好**。一旦编译产物进了提交历史，
后面只能用 `git filter-repo` 洗，很麻烦。

### 6. ★ README 是门面，正文必须外置

学习日记仓库原来的 README 是把整月笔记原样复制进去，结果 2834 行 160KB。
陌生人点进来第一屏看到的是「11.20 笔记」，完全不知道这是谁的仓库、在学什么。

改成：**README 只放「一句话定位 + 技能索引 + 项目表 + 目录」，正文放 `学习日记/YYYY-MM.md`**。
门面 68 行，读完只要 30 秒。

同步脚本相应改成只替换 README 里 `<!-- RECENT:BEGIN -->` 和 `<!-- RECENT:END -->`
之间的内容，其余部分手改不会被冲掉。

## 三、踩的坑

1. **文档里的 `~` 在 GitHub 上全变成了删除线** —— 本地 Markdown 预览看不出来，推到 GitHub 才发现数字被拼到一起。两个仓库一共 534 处。以后范围符号统一用全角 `～`。

## 二、知识点

### 1. ★★★ 验证执行机构，距离和方向必须分开验

步进第一次跑时验的是「`T 50` 走 50mm，尺子量误差为零」——**距离对，方向反了也照样是零误差**。所以 DIR 极性反了一整个月没人发现，直到 `T 30` 一头撞下去。

| 只验距离 | 距离 + 方向一起验 |
|---|---|
| 反了也通过 | 立刻暴露 |
| 埋一个月 | 第一次就修 |

**教训**：任何执行机构，至少要一个"往哪走"的判据。走 50mm 准，不代表往上走对。

### 2. ★★★ 限位分压：串联电阻要远大于分压网络，电压上限才锁得住

两级分压公式 `V = 24 × R2 / (Ru + R1 + R2)`，其中 `Ru` 是传感器内部上拉（这颗实测 ≈10.3k），**它是串在回路里的，不能只算 R1/R2 的比例**。

| 方案 | Ru=8k | Ru=10k | Ru 掉到 0 |
|---|---|---|---|
| 75k 串 + 10k | 2.55V | 2.53V | **2.82V**（安全） |
| 2.4k 串 + 1.2k | 2.56V | 2.23V | **8.0V**（烧脚） |

75k 方案里 R1 远大于整个分压网络，**即使 Ru 短路到 0V，输出也永远 ≤2.82V**，天生接不坏。1.2k 方案没有这个性质，所以必须"先量后接"。

**判据**：分压电阻的串联项至少是分压网络的 5～10 倍，才有天然的电压上限。

### 3. ★★★ 三颗等阻值串联，压降相等 = 最好的自检

焊完洞洞板量电压，测出「黑线→第一个电阻后 2.08V、→分压点 4.16V、→GND 6.26V」。

三个压降分别是 **2.08 / 2.08 / 2.10** —— 完全相等。等阻值串联电流处处相同，压降必然相等。

| 读数 | 含义 |
|---|---|
| 三段压降相等 | 三颗都在位、都焊通了 |
| 某段 24V | 那颗断路 |
| 某段 0V | 那颗短路 |

**一个自检就能替代"挨个查焊点"。**

### 4. ★★★ 腕转舵机不跟小臂解耦，夹爪朝向会随位置漂

腕转装在小臂末端，所以：

```
夹爪绝对朝向 A = (θ1 + θ2) − 腕转角 + 265
```

★ **是减号**：腕转脉宽变大、夹爪绝对角反而变小（方向标定和直觉相反）。

`M` 只动大臂小臂、不动腕转 → 小臂绝对角一变，夹爪朝向跟着变：

| 位置 | θ1+θ2 | 腕转仍 85° | 夹爪绝对朝向 |
|---|---|---|---|
| HM 收拢 | −180° | 85° | 0° 平行 X |
| M 100 0 | −91.5° | 85° | 88° 垂直 X |
| M 200 0 | −57.1° | 85° | 123° 歪 33° |

**解法不是"试出一个角度"，是给出目标朝向让代码反解**：

```c
腕转角 = (θ1 + θ2) + 265 − 目标朝向     // 目标 90° = 垂直 X 轴
```

265 是四个实测点拟合的（每个位置手动调到垂直、记下脉宽）：

| 位置 | 手调脉宽 | 反推偏置 |
|---|---|---|
| M 100 0 | 1472μs | 268.1 |
| M 150 0 | 1650μs | 265.5 |
| M 200 0 | 1800μs | 263.0 |
| M 250 0 | 2000μs | 263.5 |

取 265，残差 ±3°。代回 HM 那点算出 85.0°，和 11-17 标定的 85° 完全一致。

**判据：绝对朝向是不是正 90° 不重要，各半径一致才重要。** 平行爪夹方块，一致就抓得住。

### 5. ★★★ 单点标定定不了方向，至少两个点

第一次只用 `HM` 一个点反推，公式写成 `+腕转角 + 95`。原因是 **θ1+θ2 = −180° 时，正号和负号两种公式都能凑出 175°**，一个点看不出符号反了。

多测的 `M 150 / 200 / 250` 三个点才把符号钉死：腕转从 85° 一路涨到 134°，而夹爪要保持 90°，说明是负相关。

**方法论**：标定任何"两个量之间的线性关系"，**至少取两个点定符号，三个点以上定偏置**。一个点只能定"某个状态对不对"，定不了"关系怎么走"。

### 6. ★★ 平行爪有 180° 对称，负角度不是无解

反解出来的腕转角可能是负数或超过 180，但**平行爪转 180° 形状完全一样**（只是开口朝向反过来）。所以结果一律 `+180` 折回 `[0,180)`，永远不会因为算出来是负的就判"无解"。

`M 35 0` 收拢位算出来是 −5°，折成 **175°**（脉宽 2464μs），照样是垂直 X 轴。

### 7. ★★ 所有写执行器的路径都要同步回读状态，漏一条就必炸

调斜坡要拿「当前脉宽」当起点，但有两条写 CCR 的路：

| 路径 | 谁在用 | 同步了当前值吗 |
|---|---|---|
| 斜坡分支 | `K` / `HM` / 夹爪两段式 | ✔ |
| 角度分支 | `M` / `W` / `C` / `P` | ✘ **漏了** |

所以 `W 30` 把腕转甩到 836μs 后，"当前值"还停在 1500。再发 `HM`，斜坡从 1500 起算 → 第一拍就把脉宽写成 1500 附近 → **舵机从真实位置猛窜过去**，之后才慢慢爬。现象是"设了 3 秒的 HM 一秒就到位，还抽一下"。

**所有能改执行器状态的路径，都要顺手更新那份"当前值"缓存。** 漏一条就是个定时炸弹。

### 8. ★★ 串口一打开就复位 MCU，回零结果存不住

这块底板的 CH340 带自动下载电路（DTR/RTS 经三极管接 NRST），**上位机 open 串口的那一瞬间就会拉低复位脚**。

后果：每次重开脚本 → MCU 重启 → `s_homed` 归 0 → 所有 `Z` 命令回 `ERR 5`，同时四路舵机重走一遍 3 秒回正斜坡。

**验证**：打开串口后屏幕上有没有 `=== Arm Controller v0.1 ===` 启动横幅，有就说明复位了。

**对策**：把 `H` 当成每次开脚本的固定第一步，别指望上一次的回零结果能留下来。

### 9. ★ STM32F103 的 VIH 是 2.0V，不是 0.45×VDD+0.3

手册 I/O 静态特性保证值：**`VIH min = 2.0V`、`VIL max = 0.8V`**。

分压点实测：接上 PB12 后未触发 2.2V、触发 0.5V。

| | 实际 | 门限 | 余量 |
|---|---|---|---|
| 高电平 | 2.2V | 2.0V | 0.2V（薄） |
| 低电平 | 0.5V | 0.8V | 0.3V（够） |

高电平余量只有 0.2V，所以这根线**不能和舵机线、电机线捆一起走**。真要抖，把串联电阻从 2.4k 改成 1.2k，电压能升到 2.39V。

### 10. ★ 大电容上电打火是浪涌，断电要拔墙插不能拔圆头

470μF 对 24V 就是瞬间短路，充电能量 `E = ½CV² = 135mJ` 全砸在 DC 圆头那几个平方毫米的触点上。断电时电容放电 + 驱动器输入电感反电动势，一样打。

**真正的风险不是火花，是接触电阻变大 → 带载压降 → 步进丢步**（这种故障最难查）。

规矩：
1. 上电：线全接好，最后**合插排开关**
2. 断电：**关插排 / 拔墙插**，永远不动 DC 圆头和驱动器端子
3. 必须动 DC 侧，先断电等 10 秒放完电容

## 二、知识点

### 机械臂线

### 1. ★★ 电容是"本地储能"，必须贴着负载端子并联

步进驱动器每拍从电源抽 1A 级脉冲电流，这个脉冲要由**紧贴端子的电容**就地供出来。电容隔着一段导线，导线的电阻电感会让脉冲瞬间在端子处形成电压凹陷——470μF 跨在**驱动器 VCC/GND 端子**上才能填平这个坑，留在降压模块输入端等于白装。**电压凹陷的直接后果是高速段丢步。**

电解电容接完上电前必看极性（反接鼓包/炸）；50V 耐压用在 24V 上余量充足；电容腿剪短贴着端子。

### 2. ★★ 杜邦线不能当动力线

从降压模块输入端子引杜邦线给驱动器，意味着驱动器的 1A 脉冲电流和降压模块的输入电流**共用一段细线**：脉冲在共用段产生周期性压降 → 降压模块输入跟着抖 → 输出 6V 跟着抖 → **舵机被连带**。杜邦单根 22AWG 只有 1～1.5A 上限。动力线用粗线，或者两根杜邦并成一根。

### 3. ★★★ 静态拉线救不了舵机轴（内力），锚到外面才有用

臂末端拉线回**同一个基座/塔身** = 系统内力，舵机轴照样承受全部重力矩，一根线的张力通过臂传回轴——**一根线都救不了，这是力的闭合回路**。只有锚到**基座之外**（滑台立柱、底板）才真正分走力矩。而且线是固定长度：臂扫过工作区时要么干涉要么失效——只适合"静态展示位"，运动前解开。尼龙线还有弹性，越拉越长。

### 4. ★★ 舵机下坠是确定性的，不破坏示教-复现

MG996R 内部闭环：相同指令 = 相同角度 = 相同下垂 = 相同实际位置。折拢 4 指 → 伸直 2 指的下坠差**可复现**，所以 V1 示教-复现不受伤——抓取平面是示教时实测的，下垂自带补偿，绝对精度牺牲但复现性保住。`Z` 基准以后以示教实测为准，别按几何算。

### 5. ★ 前倾是结构问题，必须解决，放任会基准漂移

前倾（臂伸出时基座/夹板往前栽）和下坠不同：它不在舵机闭环里，量不稳定就破坏复现，还会越用越松。对策按优先级：**前撑杆**（基座前方斜撑到底板，把前倾力矩直接传进底板，零成本）> **配重**（滑块背面挂重物平衡重心）> 收紧夹板 M4。拉线只配当静态展示位的辅助保险。

### 小智语音终端线

### 6. ★★★ "跑一会儿就挂"，第一件事是加内存打点，不是改逻辑

11-18 八次改动七次烧录全不中，每次都在"改一个假设"。11-19 翻盘靠的是**在两个 AFE 创建前后各打一次 `heap_caps_get_free_size(MALLOC_CAP_INTERNAL)`**——一行日志把 80KB 的去向锁到 66KB 的 AEC 上。指标先行，假设后行。

### 7. ★★ `errno=11 (EAGAIN)` + free sram 个位数 = 内存耗尽，别查网络

症状链全是一次生现象：内存耗尽 → lwip 分不出 pbuf → send 失败 → 发送队列灌满 → 编码队列不消费 → 主循环阻塞 → 按键任务饿死 → xTaskCreate 失败弹"无法连接服务"。**串口看到 errno=11 + free sram 掉个位数，直接查内存，别沿着网络查。**

### 8. ★★ 关功能前先想它的前提还在不在

ManualStop 模式下播报时 `EnableVoiceProcessing(false)`——**麦克风是关的，喇叭声音根本没有进麦的路径**，设备端 AEC 在这个模式下除了占内存没有任何作用。功能"该不该开"取决于它的使用前提，前提不在就纯是包袱。同理：VAD 服务端做了、NS 实测关掉识别正常，一并关。

### 9. ★ 87KB 内部 RAM 的板子，AEC VOIP_HIGH_PERF 66KB = 必死

实测打点：AFE(唤醒) 17.5KB、语音处理不开 AEC 只 872B、**开 AEC 一次 67556B**。要恢复 AEC 前提是内部 RAM 余量 >75KB，或换 `AEC_MODE_SR_HIGH_PERF`（比 VOIP 省）。另外双 AFE 实例（唤醒+处理分开）是结构隐患，原版只有一个，以后内存再紧张第一选择是合并成单 AFE。

## 二、知识点

### 1. ★★★ Kconfig 的 depends 不满足时，配置会被静默丢弃

板级 `config.json` 里写了 `sdkconfig_append: CONFIG_USE_DEVICE_AEC=y`，看着天经地义，实际上一次都没生效过——因为 `USE_DEVICE_AEC` 的 `depends` 白名单里**没有 GEC 这块板**。Kconfig 遇到依赖不满足的符号，直接把整行丢掉，**不报错、不警告、不提示**。

所以"配置写了但没效果"这类问题，判据不能是"我改过配置文件"，而是：

```bash
grep CONFIG_XXX build/config/sdkconfig.h
```

宏真的出现在生成的头文件里才算生效。**中间任何一层（Kconfig depends、sdkconfig 优先级、board config 应用步骤）都可能把你写的配置吃掉。**

### 2. ★★★ I2S 全双工在 slot 配置不同时根本不能并发

这块板 tx 和 rx 挂在同一个 I2S0：

| 通道 | 模式 | 18bit 位宽 |
|---|---|---|
| tx（喇叭） | STD | 16bit data / **16bit slot** × 2 |
| rx（麦克风） | TDM | 16bit data / **AUTO slot** × 4 槽 |

BCLK/WS 是共用的，一套时钟不可能同时满足两种 slot 宽度。

一直没暴露，是因为 ManualStop 模式下收发**天然互斥**（播报时关麦、聆听时关喇叭）。一旦让两者同时跑（Realtime 模式、或"播完自动续听"），立刻出事：播放断流、主循环卡死。

官方日志里有一句直接证据：

```
I I2S_IF: Pending out channel for in channel running
```

意思是"输入通道还在跑，输出通道得排队等"。**硬件层面就不允许收支同时活跃**，这不是软件调参能绕过的。

### 3. ★★★ 服务端的 `tts stop` 不代表设备播完了

服务端发 `tts stop` 只说明它那边**这一句合成完了**，设备喇叭里可能还有几秒音频没放。

如果这时切到 listening，`EnableVoiceProcessing(true)` 立刻开麦，而输出通道还在放音——直接撞上第 2 条。表现是"话没说完就跳聆听，然后卡死"。

正确做法：`tts stop` 一律回 idle（关麦），让剩余音频安静播完。

### 4. ★★★ 一张 128px GIF 能吃掉 82KB 内部 RAM

实测数据：

```
正常           free sram: 87787
收一张 78855 字节 GIF 后  free sram: 7587      ← 掉了 80KB
再来一张                   free sram: 5827 → 崩
```

内部 RAM 总共就 88KB 可用，一张表情就吃掉九成。`gif_buf` 本身走了 PSRAM，真正吃内部 RAM 的是 `lv_gif` 的解码画布（128×128×4 ≈ 65KB）+ LVGL 对象。

**最坑的地方在于它的伪装**：内存耗尽之后报的是 `wifi:m f null`、`TCP receive failed`、`AFE Ringbuffer is full`、主循环卡死——每一条都指向网络或音频，害我一晚上在 WiFi 和 WS 里找。**内存不足不会说"我没内存了"，它会让别的子系统一个接一个地莫名其妙失败。**

以后看 `SystemInfo: free sram` 要放在第一顺位，比任何错误日志都优先。

### 5. ★★ `reset_buffer` 不能在有 fetch 活着的时候调

`AfeAudioProcessor::Stop()` 里调 `afe_iface_->reset_buffer()`，看起来是在"清理现场"，实际上是在跟阻塞在 `fetch_with_delay()` 里的 fetch 任务抢 AFE 内部 ringbuffer。

关键特征：**第一次安全，第二次必炸**。因为第一次 fetch 任务刚从 `Initialize` 出来、还没进 `while` 循环；从第二次起它已经阻塞在那儿了。

这个"第一次好、第二次坏"的规律，本身就是"资源释放/复位类操作撞上了并发"的典型信号。

### 6. ★★ 阻塞式队列不要在音频回调里调用

`PushTaskToEncodeQueue` 里一句 `audio_queue_cv_.wait(...)`，队列满就无限等。而它是从 AFE 的 fetch 回调里调用的，于是：

```
WS 发送卡住 → send 队列满 → 编码队列堵满 → wait 永久阻塞
  → fetch 停摆 → 但 feed 还在继续 → 刷 Ringbuffer FEED is full
  → 主循环卡在同一把锁 → 黑屏、按键无响应
```

**一个下游环节的慢，能顺着回调链把整个系统拖死。** 实时音频链路里，"丢帧"永远优于"等待"。

### 7. ★★ 判断通道接错，有比实测更硬的判据

我搭探针测 ES7210 四通道，得出 `ch0=回采、ch1/ch3=麦克风`，据此改了固件的通道顺序——**结果把好好的链路改坏了**。因为探针走 32bit 槽、固件走 TDM 16bit×4 槽，两条通路的通道排列并不一致。

真正的硬判据是：**唤醒词一直能触发**。如果喂给 AFE 的"麦克风"通道里是回采，WakeNet 根本不可能被"你好小智"唤醒。能唤醒，就说明通道是对的。

**能用系统既有行为反推的结论，比临时搭台子测出来的更可信**——因为前者是整条链路在真实条件下跑出来的。

### 8. ★★ .bat 文件必须存 GBK，否则中文会被拆成命令

中文 Windows 的 cmd 按当前代码页逐行解析 bat。UTF-8 编码的中文会被按 936 拆成畸形字节，**凭空劈出 `&`、`|` 这类命令分隔符**，现象是"注释里的句子被当成命令执行"。配套要 `chcp 936`。

同理，循环里当 sleep 用 `ping -n N 127.0.0.1 >nul` 而不是 `timeout`——`timeout` 在输入被重定向时会直接报错退出，循环就废了。

## 二、知识点

### 1. ★★★ 固件手写媒体解析器写死参数，素材必须按它的规格来

小智固件的 `PlaySound` 是手写 OGG 解析：帧时长写死 60ms、采样率从 OpusHead 读。系统自带提示音全是 60ms 帧 + 16000Hz，所以能播；自己转的 20ms 帧 + 48kHz 就解不出声、队列瞬间空、`IsIdle()` 立刻为真——表现为"没声音但流程正常"。**给固件喂媒体素材，先看它的解析代码假定什么规格。**

### 2. ★★★ prompt 注入决定 agent 的"聪明程度"

同一个模型、同一套工具：QQ 私聊知道当前时间、有记忆、有工具引导，所以"问几点"答得又准又机灵；板子链路的 prompt 是裸的，啥上下文都没有，连时间都不知道。差异不在模型，在喂料——把私聊的上下文注入（时间/身份/记忆/工具引导）搬过来，板子立刻同水平。

### 3. ★★ 大文件下发嵌入式的预处理三板斧 + md5 缓存

库里的 GIF 中位数 1.1MB、最大 5.7MB，直接下发 WS 和内存都扛不住。但显示区只有 128px：**缩尺寸（128px）+ 降帧率（8fps）+ 降色板（64 色）**，1.1MB → 112KB（10 倍），动图效果保留。服务端按文件 md5 缓存转码结果，每张图只转一次。

### 4. ★★ LVGL 9.3 播 GIF 动图的要点

`lv_gif_set_src` 支持内存模式：构造 `lv_img_dsc_t`，`header.magic = LV_IMAGE_HEADER_MAGIC`、`cf = LV_COLOR_FORMAT_RAW`（**9.3 没有 LV_IMG_CF_RAW 这个旧名**）、data 指向 GIF 原始字节流。gifdec 逐帧解码时会**回读原始 GIF 数据**——所以缓冲必须持续存活，提前释放直接崩；一张压完 50～300KB，PSRAM 能扛几十张。

### 5. ★★ C++ 虚函数基类声明必须给定义

基类里 `virtual void f();` 只声明不定义，所有派生类都 override 了它也不行——**vtable 会引用基类的槽**，链接时报 `undefined reference to Display::f`。给个空函数体就好。ESP-IDF 链接错误看到 vtable 字样先查这个。

### 6. ★★ 流式协议里"标记被 chunk 切断"的通用解法

LLM 流式输出里要剥 `[表情:xxx]` 这类标记，标记常被 chunk 从中间切断。解法：尾部疑似标记前缀（`[表情` 开头且无闭合）先扣进 hold buffer，下一块拼上再剥；**冲刷必须在循环外**——放循环体内每轮都冲，扣住的碎片永远拼不完整。这个模式适用于所有流式协议解析。

### 7. ★ 触摸轴映射：swap_xy 之后镜像轴也跟着换

触摸方向反了，改 `mirror_y` 没用——因为 `swap_xy=1` 时原始 X 轴变成显示的垂直轴，**管垂直的是 `mirror_x`**。调触摸方向别按直觉改，先想清楚轴交换的映射关系再动那一位。

## 二、知识点

### 1. ★★★ 光耦隔离不等于可以不共地

不共地时电机左右左右地摆、原地抖、完全不转，而软件脉冲计数一切正常（`S` 的 Z 照常累加），极易误判成驱动器坏了。

**根因**：24V 适配器是隔离输出，它对 PC 的 USB 地是浮空的。浮空地通过 Y 电容、变压器分布电容漂移几十伏，共模电压加在光耦隔离电容上，超过共模抑制能力，输出侧乱翻——驱动器把干扰当成脉冲。

**解法**：一根线，24V 负极 → STM32 GND。

```
光耦隔离的是"直流电位"，隔不掉"共模干扰"。
只要两边有信号往来，就必须有一个共同参考点。
```

**判据**：信号发出去、软件计数正常、执行机构乱动 → 先查共地。

### 2. ★★★ 电机线色不能信商家图，必须电阻实测

商家写 `A+红 / A−蓝 / B+绿 / B−黑`，照接 = 两相完全交叉 = 原地抖不转。

断电量驱动器端子（不用拔线）：

| 测量 | 读数 | 结论 |
|---|---|---|
| 红 — 黑 | 3.6Ω | 同相（A） |
| 蓝 — 绿 | 3.6Ω | 同相（B） |
| 其余四组 | OL | 不同相 |

**实际是红黑 = A 相、蓝绿 = B 相。** 同相内对调只是反转，跨相对调也是反转，只有"同相接成不同相"才会抖着不走。

### 3. ★★ 步进：低频扭矩大，但功率峰值在中间

绕组是电感，电流上升有 `τ = L/R`。频率低 → 电流建立充分 → 扭矩接近保持扭矩；频率高 → 电流来不及升到额定值 → 扭矩掉。

但功率 = 扭矩 × 角速度，低频扭矩大而转速低，高频反过来，**功率在中间某频率最高，两头都低**。

实测：4000Hz（10mm/s）声音最扎实，8000Hz（20mm/s）发虚。演示优先 4000Hz，丢步风险减半。

### 4. ★★ "设频率"的函数会顺手改 CCR

`step_set_freq()` 内部把 CCR 设成 `arr/2`（固定 50% 占空比）。所以初始化顺序反了就是"上电电机自己哒哒哒慢爬"（200Hz × 0.0025 = 0.5mm/s）：

```c
// 错：清完 CCR 又被改回 50%
__HAL_TIM_SET_COMPARE(&htim1, TIM_CHANNEL_1, 0);
step_set_freq(STEP_F_MIN);

// 对：先设周期，再清 CCR
step_set_freq(STEP_F_MIN);
__HAL_TIM_SET_COMPARE(&htim1, TIM_CHANNEL_1, 0);
HAL_TIM_PWM_Start(&htim1, TIM_CHANNEL_1);
```

★ 这个 bug 从写代码那天就在，但没接驱动器时 PA8 发着脉冲没人收 —— **硬件没接，软件 bug 是隐形的**。

### 5. ★ ENA 的"有效"是脱机，不是使能

TB6600 规格书原文："ENA 有效时电机转子处于自由状态。"

共阳下 GPIO **低** = 光耦导通 = ENA 有效 = **脱机松轴**。所以锁轴要输出**高**。

三态判据：真脱机 = 和断电一样松；半流锁轴 = 紧但大力能拧动；全流锁轴 = 硬邦邦。

### 6. ★★★ 接近开关的检测面在"正前方"，不是轴向那个"灯泡"

今天最大的乌龙：把传感器尾部那颗 LED 指示灯当成了光电探头，一直对着轴向端面测，不管放什么金属都不触发，差点判成坏件。

实际检测面在**侧面（正前方）**，那颗"灯泡"就是指示灯。

**教训**：拿到陌生传感器先查型号资料确认检测面，别凭外形猜。有 LED 反而好办——**有金属靠近时灯会亮**，比万用表快。

### 7. ★★★ 电感式只认金属，塑料尼龙零响应

原理是涡流：金属导体在交变磁场里产生涡流 → 振荡器振幅下降 → 触发输出。非金属（塑料、尼龙、木头、水）**不产生涡流**，不是"距离短"而是**完全没有响应**，贴死也没用。

| 材料 | 检测距离 |
|---|---|
| 铁 / 碳钢 | 4mm（最好） |
| 铝 / 铜 | 2.4～2.8mm（衰减 60～70%） |
| 不锈钢 304/316 | 更差，可能测不到 |
| 塑料 / 尼龙 / 亚克力 | 零响应 |

所以想用尼龙扎带当触发体是行不通的，扎带只能当"绑带"，绑住的东西必须是金属。

### 8. ★★ 仿制 NPN 的输出端可能带 24V 内部上拉

被测这颗标着 `SN04-N`，未触发时黑线**常驻 24V**、触发时掉到 0.xV。标准 NPN 常开应该是"未触发悬空、触发拉 0V"，所以它内部在输出端**并了一个上拉到电源正的电阻**（实测 Ru ≈ 8～10k）。

后果：**黑线不能直连 3.3V 的 MCU 引脚**，24V 会灌进钳位二极管。

★ 顺便纠正一个常见误解：NPN 开集电极的输出管只连在"输出—GND"之间，**物理上没有通向 24V 的路径**，正常不会输出 24V。真要出 24V，只有两种可能：接错线（棕/黑互换）或者这根本不是标准 NPN。

### 9. ★★ 分压设计要把传感器内部上拉算进去

不能只算 R1、R2 —— **Ru 是串在回路里的**：

```
黑线 ──[R1]──┬── PB12
             │
          [R2]
             │
            GND
```

`V_PB12 = 24 × R2 / (Ru + R1 + R2)`

代入 Ru = 8～10k、R1 = 75k、R2 = 10k → **2.53～2.58V** ✔

STM32F103 标准 IO 的 **VIH min = 0.45×VDD + 0.3 = 1.79V**（不是 0.7×VDD），所以 2.5V 余量足够。

**顺序**：先上电量分压点电压，确认 ≤3.3V 且够高，**断电**再接 PB12。这一步不能省。

### 10. ★★ 电源网络里的电阻不能拆来用

想拆另一块板上的 1.5k 电阻，查原理图发现它挂在 `MT3540-F25`（DC-DC 升压）的 FB/EN 引脚上，是**输出电压设定网络**的一部分。

| 操作 | 后果 |
|---|---|
| 拆掉（断路） | 升压不启动或反馈失控 → 输出跑飞 |
| 换别的阻值 | 输出电压按分压比变，可能烧穿后级 |

**判别**：电阻周围有电感、肖特基二极管、DC-DC 芯片 = 电源电路，一颗都别动。

### 11. ★ 贴片丝印读法

四位：前三位有效数字 + 第四位倍率（10 的幂）；三位：两位有效数字 + 倍率。

| 丝印 | 阻值 |
|---|---|
| 3300 | 330Ω（330 × 10⁰） |
| 1501 | 1.5kΩ（150 × 10¹） |
| 7502 | 75kΩ（750 × 10²） |
| 103（三位） | 10kΩ |

量电流要把红笔插到 **mA 孔**，★ **量完立刻插回 VΩ 孔**，否则下次量电压直接把电源短路。

## 二、知识点

### 1. ★★★ 舵机装反了不是改一个常量，要改三个地方

小臂的实测数据：`550μs → 伸直(θ2=0)`、`1500μs → 垂直右侧(θ2=−90)`、`2460μs → 折到底(θ2=−180)`。

而代码原本假设 θ2 是 **正**的（1500μs 折 +90°）。差一个符号，底下有**三处**必须一起翻过来：

| 位置 | 原来 | 改成 | 管什么 |
|---|---|---|---|
| `THETA2_HOME_DEG` | 90 | **−90** | 1500μs 时的实际关节角 |
| `SERVO2_DIR` | 1 | **−1** | 脉宽增大时关节角是增还是减 |
| `ik_solve(..., elbow, ...)` | +1 | **−1** | 逆解取哪一组解（θ2 正解还是负解） |

**判据公式：** `servo2 = 90 + (θ2 − THETA2_HOME) × SERVO2_DIR`

拿三个实测点代进去解：1500μs 时 θ2 = −90（求 HOME），2460μs 时 θ2 = −180（求 DIR），一次就能定出 (−90, −1)，而且三个点自洽——**这就是"三点定标定"**，比一个个试快得多。

**只改一处的后果**：改 HOME 不改 DIR，小臂会**越指令越往反方向跑**；三个都改对了但 elbow 忘改，逆解算出来的 θ2 符号是错的，实际角度正好镜像。这种"看着能动但位置全歪"的错最难查。

### 2. ★★ 舵机的 9.4 kg·cm 是扭矩，不是“能举 9.4kg”

`kg·cm` 是**力 × 力臂**：在 1cm 处能推 9.4kg，在 10cm 处只能推 0.94kg。

更要紧的是分清两个完全不同的力：

| | 是什么 | 谁在承受 | 我们的数值 |
|---|---|---|---|
| **扭矩** | 绕轴转动方向的力 | 舵机内部电机+齿轮 | 需求约 3 kg·cm，舵机 9.4，**余量 3 倍** ✔ |
| **弯矩（径向力）** | 垂直于轴压在输出轴上的力 | 输出轴 + 上下轴承 + 齿轮箱 | 约 **14 kg·cm**，舵机承载 3～5，**超载 3 倍** ✘ |

SCARA 是水平构型，重力方向垂直于转动平面，**转起来根本不用举重**——所以扭矩一直够用。真正把舵机压坏的是那根 18cm 悬臂产生的弯矩。

**表现不是“转不动”，是：** 臂头明显下垂、停下来持续嗡嗡（在跟重力较劲）、用久了齿轮间隙变大、臂晃动。

### 3. ★★ 缩短臂长是降弯矩最直接的手段，但减重同样重要

弯矩 = Σ(每个部件的重量 × 它到根部轴心的距离)。臂从 21cm 缩到 18cm，末端那堆东西（小臂+腕转+夹爪）的力臂跟着短 3cm，弯矩从 16 掉到 14 kg·cm。

但算下来大头是**重量**：整臂 1.5kg，而按零件清单估只有 660g 左右，多出来的一倍全在结构件上（4 根 3mm 冷轧钢直码就 280g）。

所以两条路要一起走：**缩短**（几何）+ **减重**（材料）。只做一样，弯矩降不下来。

### 4. ★ 让臂“坐在外壳上转”，能把径向力从齿轮上分走

舵机输出轴的径向承载是最弱的一环。工业转台的做法是：**重量由推力轴承/滑动面承担，电机只输出扭矩**。

土办法也能实现：在舵机臂和舵机外壳之间垫一片尼龙/PTFE 垫圈，让臂的重量先压在垫圈→外壳上，剩下的才传给齿轮。

- 尼龙摩擦系数 0.15～0.25，PTFE 只有 0.05～0.1，PTFE 更好
- 摩擦增加的扭矩代价很小（1.5kg 压着转，大约多 0.2 kg·cm），远小于它省下的径向载荷
- **★ 但这只是分走一部分**，臂还是悬在外面，弯矩依然存在

## 二、知识点

### 1. ★★★ 内部 RAM 的瓶颈是「最大连续块」，不是「总空闲」

实测（WiFi 起来之后）：

```
内部RAM 空闲 252 KB, 最大连续 180 KB
```

看着有 252KB，但**最大的一整块只有 180KB**。想要一块 115KB 的刷屏缓冲 + 一块 64KB 的解码工作区（合计 179KB），数字上够、实际装不下——180KB 被 115KB 切走之后，剩下的 68KB 碎成两段，最大一段只有 31KB。

**判据**：`heap_caps_get_free_size()` 和 `heap_caps_get_largest_free_block()` 两个数要一起看，后者才决定能不能分配。分配大块用 `heap_caps_malloc`，失败时它不会告诉你"其实总量还有"。

能腾的地方（都试过）：

| 手段 | 效果 |
|---|---|
| WiFi 收发缓冲 32/32/10 → 16/16/4 | 最大连续块 168 → 180 KB |
| 环形缓冲从内部 RAM 挪到 PSRAM | 空闲 +48KB，但连续块反而更碎 |
| 输出缓冲去掉冗余余量 | 116 → 112 KB |

**内部 RAM 总量 512KB 是焊死的（IRAM + DRAM 分段），不能"配置调大"，只能省。**

### 2. ★★★ PSRAM 的数据不能直接喂给 SPI DMA——会被截断

把 RGB 刷屏缓冲放在 PSRAM 里，现象是**画面只刷出上边一小部分，剩下的行全是背景色**（照片里是一条约 50 行的扁条）。

```
放 PSRAM：刷屏 12~17 ms，画面残缺
放内部 RAM：刷屏 0.4 ms，画面完整
```

12ms 全花在把 PSRAM 数据拷进内部 bounce buffer 上，而且大块数据只拷了一部分。**驱动不报错，就是默默截断**，非常难查。

**结论：刷屏缓冲必须在内部 RAM。** 之前在 GEC6818 上是 `mmap(/dev/fb0)` 直接写内存，根本不存在这个问题，换到 SPI 屏才踩到。

### 3. ★★★ WiFi 省电模式会毁掉实时传输

日志里这一行是元凶：

```
I (3729) wifi:pm start, type: 1
```

默认的 modem sleep 让射频周期性休眠，TCP 收包延迟从毫秒级涨到几百毫秒。实测**视频每帧要 1～3 秒才收齐**，帧率掉到 0.4fps。

加一句就好了：

```c
esp_wifi_set_ps(WIFI_PS_NONE);   // 日志变成 "Set ps type: 0"
```

**以后只要做实时传输（流媒体、远程控制），第一件事就是关它。** 代价是功耗高一点，插 USB 供电无所谓。

### 4. ★★ ESP32-S3 没有 JPEG 硬件解码器

`esp_driver_jpeg` 那个组件是给 **ESP32-P4** 的。判断方法：

```bash
grep -c "SOC_JPEG" components/soc/esp32s3/include/soc/soc_caps.h   # → 0
grep -c "SOC_JPEG" components/soc/esp32p4/include/soc/soc_caps.h   # → 3
```

S3 只能软件解码，速度直接由像素数决定：

| 分辨率 | 解码耗时 |
|---|---|
| 320×180（57,600 像素） | 85 ms |
| 352×198（69,696 像素） | 98 ms |
| 480×270（129,600 像素） | 173 ms |
| 480×320（153,600 像素） | 205 ms |

**大约每像素 1.3 微秒**，可以拿来快速估算任意分辨率的可行性。

### 5. ★★ `swap_xy` 会把 GRAM 的写入方向一起转掉

想让物理竖屏（320×480）当横屏（480×320）用，设 `esp_lcd_panel_swap_xy(true)`。但它置的是 MADCTL 的 **MV 位**，MV 会**同时**交换写入方向：

传进去 480×270 的横排数据 → 硬件按列优先解释 → 画出来是右边一条 270 宽的竖带。

而且 `swap_xy` **必须在 `esp_lcd_panel_init()` 之后调**，因为 init 会发整段初始化序列（含 MADCTL），先设会被覆盖。这两个坑叠在一起，我一开始完全看错方向。

### 6. ★★ 流媒体协议不用自己造，但也省不了多少

现成的有：MJPEG over HTTP、RTSP/RTP、HLS、WebSocket。最省事的一条是让 ffmpeg 直接当服务器：

```
ffmpeg -re -i video.mp4 -f mpjpeg -listen 1 http://0.0.0.0:8080/stream
```

**但客户端那一半省不掉**——MJPEG-over-HTTP 只是把帧用 `--boundary` 字符串隔开，板子照样要逐字节找边界切帧。我把 boundary 换成 `A5A5A5A5 + 4 字节长度`，本质同一件事，只是搜索更快。

**帧同步标记是必须的**：断线重连时缓冲里残留半帧，没有标记的话整条流会永久错位（日志里刷随机大长度）。有了标记，客户端可以逐字节搜索重新对齐。

### 7. ★ 摄像头流畅和网络视频卡顿，是两条完全不同的路

| | 摄像头 | 网络视频 |
|---|---|---|
| 数据形态 | **原始 RGB565，不压缩** | JPEG（压缩） |
| 谁在搬数据 | LCD_CAM 外设 **DMA 直写内存**，CPU 不介入 | CPU 软件解码 |
| 瓶颈 | SPI 带宽（12ms/帧） | **CPU 解码（85～173ms/帧）** |

摄像头能跑 20-30fps，是因为它压根不解码。视频必须压缩传输（WiFi 带宽限制），压缩就要解码，S3 没有硬件解码器——**这是物理限制，不是代码写得好不好的问题**。

### 8. ★★★ 视频文件必须锁帧率：显示帧率高于源帧率 = 快放

这条之前一直理解错了。**"帧率越高越流畅"只对实时画面成立**（游戏、摄像头），对固定帧率的视频文件完全是另一回事：

| 源内容 | 板子显示 | 结果 |
|---|---|---|
| 25fps | 25fps | 1× ，正常 |
| 25fps | 38fps | **1.5× 快放** |
| 25fps | 12fps | 0.5× 慢放 |

视频的"内容时间"是固定的：1 秒的内容就是 1 秒。每秒塞进去的帧数超过源帧率，多出来的只能靠快放消化；少于源帧率就慢放。**所以解码能力富余时，必须主动按源帧率节流，不能让解码能力决定播放速度。**

节流的写法有讲究：不能用"每帧固定延时"，`vTaskDelay` 只有 10ms 粒度，误差会累积。要维护一个**累加的目标时刻** `next += 40ms`，长期平均才准。

### 9. ★★★ JPEG 软解的耗时 = 固定成本 + 数据量成本

实测拟合出来的关系，两个旋钮互不替代：

```
解码时间 = 74.7ms（像素数决定，做 IDCT + 色彩转换） + 1.58ms × 每KB数据量
```

- **前半段跟码率完全无关**，每个像素都要算一遍 IDCT 和 YCbCr→RGB
- **后半段才是 Huffman 解码**，跟压缩后的数据量成正比

实测验证（480×270）：q=15 帧 8.7KB → 88ms；q=31 帧 5.2KB → 83ms。**码率翻到最烂只快 7%，画质却崩了。**

**结论：想提帧率只能减像素（降分辨率），降码率几乎没用。** 反过来想提画质，降 q 只增加那 1.58ms/KB 的部分，代价相对可控——这是晚上提画质的依据。

### 10. ★★ ROM 版和软件版 tjpgd 是两个东西，软件版能多开三个加速开关

ESP32-S3 的 ROM 里自带一份 tjpgd，所以默认 `CONFIG_JD_USE_ROM=y`。但 ROM 版是**编译好固定**的，拿不到这几个参数：

| 开关 | 作用 |
|---|---|
| `JD_FORMAT_RGB565` | tjpgd 内部直接吐 RGB565，省掉外层「RGB888→RGB565」逐像素转换 |
| `JD_FASTDECODE_TABLE` | 表法 Huffman，比逐位读快约 20% |
| `JD_TBLCLIP` | 饱和运算查表 |

关掉 ROM 版换成组件自带的软件版，三个都能开，**实测解码快 25%**（480×270：88ms → 66ms）。代价是工作区从 3100 字节涨到 65472 字节。

★ 但工作区必须待在**内部 RAM**：一旦掉到 PSRAM，解码时会疯狂读 PSRAM 和 WiFi 收包抢带宽，表现为**网络直接断流**（实测丢帧率 86%），而解码时间看起来还挺正常。这个坑极难从现象倒推回来。

### 11. ★★ 内部 RAM 分配顺序必须「先小块后大块」

同一块 184KB 的连续空间，分配顺序不同结果完全不同：

- 先要 112KB 的 RGB → 剩下的连续块被切碎 → 64KB 工作区申请失败 → 掉 PSRAM
- 先要 64KB 工作区 → 再要 112KB 的 RGB → 两个都成功

原因是大块会从连续区中间切走，把剩余空间劈成两半。**判据看启动日志有没有 `work=64KB(PSRAM)`。**

### 12. ★★ WiFi 接收缓冲的块确认窗口会卡住吞吐

`CONFIG_ESP_WIFI_RX_BA_WIN`（块确认窗口）默认只有 6，`STATIC_RX_BUFFER_NUM` 只有 4。低吞吐场景够用，一旦要跑几百 KB/s 就露馅了——实测把它调到 8、静态缓冲调到 16，**吞吐从 105KB/s 涨到 257KB/s，翻倍多**。

代价是这些缓冲吃内部 RAM（16×1600 ≈ 25KB），会挤掉别的缓冲。

## 三、踩的坑

1. **串口日志抓不全**，好几次都在 4～6 秒处截断，白等了好几轮。后来改用服务器端「已发 N 帧」的日志反推板子状态才定位到问题。教训：**调试不能只依赖一条信息通道。**

2. **反复用程序开关 Windows 移动热点把它搞死了**。`StopTetheringAsync` + `StartTetheringAsync` 折腾几次之后，热点卡在 `InTransition`，信号闪一下就没，手机都连不上，最后只能手动去设置里关掉等 10 秒再开。**移动热点不是设计成被程序反复开关的。**

3. **旧服务器进程没杀干净**，3 个旧实例同时抢 8080，板子连的其实是旧的（分辨率不一样的）那个，排查方向全错。而且在 bash 里执行 `Get-Process` 这种 PowerShell 命令会**静默失败**，看着像执行了其实没有。

4. **改 `sdkconfig` 里不存在的选项会被 Kconfig 静默丢弃**。手动往 sdkconfig 追加 `CONFIG_SOC_JPEG_CODEC_SUPPORTED=y`，重新 configure 之后这行直接消失——因为 S3 根本没有这个配置项。

5. **"网络明明能到 1MB/s，但吞吐死活上不去"** —— 我一开始怀疑网络、怀疑板子收得慢，查了半天都不是。真相是 ffmpeg 的 **`-re`** 参数：它让 ffmpeg 按实时速率读源，等于**只准每秒出 25 帧**，25fps × 5KB = 125KB/s，带宽利用率只有 12%。**服务器在给自己设限，却表现成"网络不行"。**

6. **以为降码率能提帧率** —— 实测 q 从 15 调到 31（画质已经不能看），帧率只从 11.3 涨到 12.1fps。后来才想明白：解码的大头是"每个像素都要算一遍"，跟压得多狠无关。

7. **任务不绑核，顺序不同结果不同** —— 两个流媒体任务一开始用 `xTaskCreate` 不指定核心，每次启动跑在哪个核上都不一样。关掉 CPU1 的看门狗检查之后，任务跑到 CPU0，CPU0 的看门狗照样报警。必须 `xTaskCreatePinnedToCore` 绑死。

## 四、遗留

1. **视频疑似"倍速快放"，现象和日志对不上，没定论**。板子日志确实是 25fps（每 1000ms 打印 25 帧），服务器转码输出的帧序列也对（8725 帧 ÷ 25 = 349 秒 = 源时长 5:49），但肉眼感觉比电脑上快。待查的两个嫌疑点：
   - 板子侧每帧前会逐字节搜 4 字节同步标记 `0xA5A5A5A5`，万一 JPEG 数据里恰好出现这个序列就会误判、跳过一段数据重新对齐（症状就是内容跳跃）
   - 服务器侧靠扫 `FF D8`/`FF D9` 切帧边界，JPEG 内部若有假 EOI 会提前截断，之后整条流错位跳数据
   - **验证方法**：视频总长 5:49，掐表看多久循环回开头一次。接近 5:49 就是正常，2～3 分钟就是真快放

2. **音画同步没做**（下一阶段主线）。方案已定：
   - 音频传**裸 PCM s16le 不传 MP3**（省 CPU，且采样数天然就是时间轴）
   - 服务器一个 ffmpeg 双输出，两路都用墙钟打 pts
   - 板子拿 I2S 当主时钟调度视频帧

3. **延迟 30 秒**。4MB 环形缓冲灌满后画面比源晚约 30 秒。点播无所谓，做实时预览必须把缓冲降回几十 KB。

4. **当前分辨率 320×180**。选它不是因为要小画面，而是**内部 RAM 刚好能同时放下 RGB 112KB + 工作区 64KB**（176KB < 184KB 上限）。352×198 是 200KB，装不下，工作区会被挤到 PSRAM 导致网络断流。想上 480×270 满宽得靠 `psram_dma_direct`（RGB 走 PSRAM），帧率约 15fps。

5. **画质还可以再提**。现在 q=10（帧 6～8.7KB，解码 31～42ms，刚好卡在 25fps 的 40ms 预算边缘）。想更好画质需要腾出解码余量，办法是把 WiFi 静态缓冲从 10 再降到 6，让 RGB 缓冲回到内部 RAM。

## 二、知识点

### 1. ★★★ 新增 `.c` 文件后必须重新 configure，否则只在链接阶段报错

`main/CMakeLists.txt` 用的是 `file(GLOB_RECURSE ...)`，这个命令**只在 CMake configure 阶段展开一次**，不是每次编译都重新扫目录。

新建 `tcp.c` 之后直接编译，现象是：

```
undefined reference to `tcp_client_create'
```

编译阶段一切正常（因为 `tcp.h` 是能 include 到的，函数声明有），**只有链接阶段才暴露**——目标文件里压根没有 `tcp_client_create` 这个符号。

**判据：编译零错误，只在链接报某一批函数 undefined，先翻 build 目录有没有对应的 `.obj`。**

```
build/esp-idf/main/CMakeFiles/__idf_main.dir/
    exti.c.obj  i2c.c.obj  key.c.obj  lcd.c.obj  led.c.obj
    main.c.obj  pca9557.c.obj  pwm.c.obj  tp.c.obj  wifi.c.obj
    ← 没有 tcp.c.obj，就是它
```

解法就是重新 configure（`idf.py reconfigure`，或者直接跑一遍 cmake）。**这个工程以后每加一个 `.c` 都要记得做这一步**，或者干脆把 CMakeLists 改成显式列文件、彻底躲开 GLOB。

### 2. ★★★ 一个 `.c` 忘了写 `#include`，报错会连成一片

`mqtt_bafa.c` 开头两个空行，直接从函数开始写，结果一编译十几条错误：

```
unknown type name 'esp_event_base_t'      → 缺 mqtt_client.h
unknown type name 'int32_t'               → 缺 stdint.h
'implicit declaration of snprintf'        → 缺 stdio.h
'implicit declaration of vTaskDelay'      → 缺 freertos/task.h
'BAFA_SERVER' undeclared                  → 缺 mqtt_bafa.h（宏都在里面）
's_client' / 's_connected' undeclared     → 这两个变量从来没定义
```

**看懂这个规律：凡是 `unknown type`、`undeclared`、`implicit declaration` 一起冒出来，基本都是「头文件没包含」，不是每个错误都要单独修。**

C 语言没有"模块自动可见"这回事：`.c` 文件想用别处的宏、类型、函数声明，**必须自己 include**，别的文件 include 过跟它没有任何关系。

顺带一条：**头文件里不要声明 `static` 函数**。`static` 是文件内部链接，写在头文件里毫无意义，谁 include 谁得到一份废声明。对外暴露什么，就在头文件里只写那些。

### 3. ★★ 烧录偏移不能自己算，要从 bootloader 日志里读

手动用 esptool 烧 app 时，偏移写错了会怎样？**烧录照样成功、hash 校验照样通过、板子照样正常启动——只是它跑的还是旧固件。** 因为 app 分区之外的位置写了也没人读。

正确做法是看启动日志：

```
I (74)  boot: 2 factory   factory app   00 00  00010000  00100000
I (234) boot: Loaded app from partition at offset 0x10000
```

**`Loaded app from partition at offset` 后面那个地址就是该烧的位置。** 这台机器上是 `0x10000`（不是 `0x100000`，差一个 0）。

判断依据：如果串口日志里完全看不到自己新加的打印，但编译产物明明是新的，**第一件事就是怀疑烧错位置，而不是怀疑代码**。

### 4. ★★ `printf` 有缓冲，程序一卡住一条日志都看不到

排查 WiFi/MQTT 时用 `printf` 打阶段日志，结果串口一片空白，看着像"卡死在第一步"。换成 `ESP_LOGx` 立刻就出来了。

原因：`printf` 走 stdout，是**带缓冲**的，程序不往下跑或者不正常退出，缓冲区里的内容永远不会刷出去；而 ESP-IDF 的日志系统是**无缓冲直写 UART**。

**结论：所有用来排查的打印一律用 `ESP_LOGI/W/E`，`printf` 只用来输出最终给用户看的结果。**

### 5. ★★ LVGL 的坑：操作要加锁、镜像不能靠负 zoom

**加锁**：`esp_lvgl_port` 会自己起一个 LVGL 任务在跑 `lv_timer_handler`。主线程直接 `lv_img_create()` 是在跟它抢同一份内部状态，轻则界面不刷新，重则卡死。所有 LVGL API 都要包在锁里：

```c
if (lvgl_port_lock(0)) {
    ui_image_button_create();
    lvgl_port_unlock();
}
```

耗时的事（比如逐像素处理 30 万字节的图片）要放在锁**外面**做，别占着锁。

**镜像**：LVGL 8.3 的 `lv_img_set_zoom()` 参数是 `uint16_t`，绘制描述符里也是 `uint16_t`，**源码里没有负值分支**，所以"传负数实现左右翻转"这条路走不通。可行的做法是在内存里翻一份：

```c
for (int y = 0; y < H; y++)
    for (int x = 0; x < W; x++)
        dst[y*W + x] = src[y*W + (W - 1 - x)];   // y 不变 = 只翻左右
```

480x320 一共 15 万像素，翻转一次几毫秒，307KB 放 PSRAM 完全没压力。

**另外**：`lv_img` 默认**不可点击**，必须显式 `lv_obj_add_flag(img, LV_OBJ_FLAG_CLICKABLE)`，否则 `LV_EVENT_CLICKED` 永远不触发。

### 6. ★★ RGB565 往屏里写之前要换字节序

`lcd_set_color(0xF800)` 想刷红色，结果刷出来是青绿色——因为 **ST7796 收数据是高字节在前（大端），而 CPU 是小端**。

```
想发：0xF800（红）
内存里存成：[0x00, 0xF8]      ← uint16_t 小端
屏幕读到：0x00F8（青绿）      ← 高字节在前
```

所以要手动换一下：

```c
uint16_t color_be = (uint16_t)((color >> 8) | (color << 8));
```

**为什么之前一直没发现**：测试时用的是 `0xFFFF`（白）和 `0x0000`（黑），高低字节相不相同都看不出来。**纯色测试一定要用红/绿/蓝这种三通道不对称的颜色。**

顺带记 RGB565 的算法：

```
16 位 = R(5bit) << 11 | G(6bit) << 5 | B(5bit)
红 255,0,0   → 31<<11                = 0xF800
绿 0,255,0   → 63<<5                 = 0x07E0
蓝 0,0,255   → 31                    = 0x001F
```

### 7. ★★ 整屏缓冲不一定更快，反而会拖死触摸

LVGL 的绘制缓冲有两个方向：

| 配置 | 缓冲大小 | 效果 |
|---|---|---|
| 分块 `480 * 80` | 76800 字节，可放**内部 DMA 内存** | 分 4 次 flush，每块约 60ms |
| 整屏 `480 * 320` | 307200 字节，只能放 **PSRAM** | 一次 flush 约 250ms，且要先从 PSRAM 拷进内部内存 |

看起来"一次刷完"更省事，实测反而**显示不全、触摸失灵**——因为一整屏传输期间 LVGL 一直持锁，触摸事件全排在后面。

**结论：这块屏 + 10MHz SPI，`480 * 80` 分块 + 内部 DMA 内存才是对的组合。** `buff_dma = true` 让 SPI 直接搬，省掉每块 memcpy 到 bounce buffer 的开销。

### 8. ★ 收数据的缓冲区一定要自己补 `'\0'`

```c
int len = recv(sockfd, buf, sizeof(buf), 0);
printf("%s", buf);            // 收满 1024 字节时，buf 里没有 '\0'，%s 会一直往后读
```

`recv` 只负责拷字节，**不负责补结束符**。正确写法：

```c
int len = recv(sockfd, buf, sizeof(buf) - 1, 0);   // 留 1 字节
if (len > 0) {
    buf[len] = '\0';                                // 自己补
}
```

### 9. ★★★ 舵机标定只认两个端点脉宽，中间靠线性插值

MG996R 的脉宽—角度关系是严格线性的：`0.5ms → 0°`、`1.5ms → 90°`、`2.5ms → 180°`，增益 **0.09°/μs**（2000μs ÷ 180°）。所以不用逐点测，测两个端点就够：

| 舵机 | −90° | +90° | 跨度 | 实测增益 |
|---|---|---|---|---|
| 大臂 | 520 | 2450 | 1930μs | 0.0933 |
| 小臂 | 550 | 2460 | 1910μs | 0.0942 |
| 腕转 | 500 | 2520 | 2020μs | 0.0891 |

代码里就是一句线性映射：`us = us_min + (us_max − us_min) × deg / 180`，只有这两个端点参与计算。**量角度只是手段，最终写进代码的只有那两对脉宽。**

同批三只舵机跨度差 110μs（1910～2020），增益差 5%，**每只必须单独标，不能拿一只的值套全部**。

还有一点：中途发 1000μs 时只看到转 45°，不是舵机坏了——`1000~2000` 只覆盖全程中间的一半（45°～135°），要看到 180° 得发 500 和 2500。但多数舵机机械限位留了余量，实际能转到 190～200°，用“听嗡嗡声”定边界这套办法可能完全失效（我手上这只 400～2600 全程都不顶死），这时就取实测角度最准的那一对脉宽当端点。

### 10. ★★★ 夹爪：直接发目标脉宽会堵转，必须先过冲再退 20μs

机械爪连杆有两个“顶死位”：全开、全合。直接发目标脉宽，舵机闭环保位时的静差正好压在卡点上，就会持续嗡嗡、轻微堵转（堵转电流约 2.5A，久了烧电机）。

实测有效的做法是**先过冲，再退回**：

| 动作 | 先到 | 再退到 | 效果 |
|---|---|---|---|
| 完全合上并轻微夹紧 | 1600 | **1580** | 安静，且夹得住 |
| 完全打开 | 1000 | **1020** | 安静，开口接近最大 |

原理：先顶到限位把齿隙吃干净，再退 20μs，输出轴落在“有余量”的位置，闭环不会一直较劲。20μs ≈ 1.8°，刚好在死区（4μs）之上、又小到不改变夹持效果。

**★ 反过来直接发 1020 反而会堵转**，必须走“1000 → 1020”这个顺序，别图省事改成一步到位。

### 11. ★★ 慢转不会让舵机扭矩变大

常见误解。舵机是闭环（电位器反馈 + H 桥），**输出扭矩由负载决定**，上限就是堵转扭矩（MG996R 9.4 kg·cm），跟转速无关。慢转真正改变的是**峰值需求**：快速启停要额外对抗惯量（`J×α`），慢慢转加速度小，峰值扭矩反而更低，更不容易过载。

所以标定时把速度降到 2 秒一次，除了安静，本身也更安全。

## 二、知识点

### 1. ★★★ 屏幕横竖屏由 MADCTL 的三个位决定，MV 交换、MX/MY 镜像

ST7796 的方向全压在 `MADCTL`（0x36）这一个寄存器上：

| 位 | 名称 | 作用 |
|---|---|---|
| bit7 | **MY** | 行地址反转 |
| bit6 | **MX** | 列地址反转 |
| bit5 | **MV** | 行列交换（就是 swap_xy） |

ESP-IDF 的两个 API 直接对应这三个位：

```c
esp_lcd_panel_swap_xy(handle, true);      // MV = 1，行列交换
esp_lcd_panel_mirror(handle, x, y);       // 第一个参数写 MX，第二个写 MY
```

**竖屏（320×480）和横屏（480×320）的正确组合：**

| 目标 | MV | MX | MY | 代码 |
|---|---|---|---|---|
| 竖屏 | 0 | 1 | 0 | `mirror(true, false)`，不调 swap_xy |
| 横屏（本板实测可用） | 1 | 1 | 0 | `swap_xy(true)` + `mirror(true, false)` |

**判据（很重要，能一眼定位）：**

- 原点跑到**对角**（左上 → 右下）→ MX 和 MY **两个一起反了**，把 `mirror` 的两个参数同时取反
- 只上下颠倒 → 只反 MY
- 只左右反 → 只反 MX
- 转了 90° → MV 配错了

第一次配成了 `mirror(false, true)`，等于在正确的横屏上又转了 180°，画面原点就跑到了右下角。**记住：交换行列之后，MX/MY 的作用轴也跟着换了**，不能照抄竖屏的参数。

### 2. ★★★ 背光 PWM 调光会在低亮度下引发拍频条纹，必须把频率拉高

现象：100% 亮度完全正常，降到 50% 就出现轻微频闪 + 缓慢横移的束状条纹。

**为什么 100% 不闪？** 满占空比时 PWM 输出是恒定高电平，驱动管常通，**根本没有开关动作**，也就没有电流跳变、没有电源纹波、没有拍频。这是判断"是不是 PWM 引起"的关键特征。

**为什么 50% 会横移？** 两层原因叠加：

1. **电流纹波**：PWM 不是降压，是快速通断。50% 时电流是脉冲式的，每次开关的 di/dt 都会在 3V3 上激起纹波。ST7796 内部的电荷泵和 Gamma 基准靠这条轨供电，纹波进去灰阶就抖。
2. **拍频**：LCD 自己按帧扫描（ST7796 约 70Hz）。PWM 10kHz 时每帧经历的周期数是 `10000 / 70 ≈ 142.857`，**不是整数**。小数部分让每一帧的平均背光亮度都比上一帧差一点，形成低频的明暗调制。因为扫描是逐行从上往下，这条明暗带就沿着垂直方向慢慢移动 —— 看起来就是"横移条纹"。

**解决：把 PWM 频率拉开。** 10kHz → 20kHz 后完全干净：

```c
#define BL_PWM_FREQ_HZ   20000
...
        .clk_cfg         = LEDC_USE_APB_CLK,   // 固定 APB 80MHz
```

频率提高后，拍频周期短到人眼融合，纹波也更容易被电容滤掉。

**坑：时钟源必须固定成 APB。** 20kHz 下 `80M / 20k = 4000` 个计数才够 10 位分辨率（1024 级）；如果让 `LEDC_AUTO_CLK` 挑到 17.5MHz 的 RC 振荡器，只剩 875 个计数，分辨率不满足，配置直接失败。

**频率和分辨率的硬约束：**

```
LEDC 时钟频率 / PWM 频率 ≥ 2^分辨率位数
80MHz / 20kHz = 4000 ≥ 1024   ✓
17.5MHz / 20kHz = 875 < 1024  ✗  配不出来
```

### 3. ★★★ LCD 和 OLED 的根本差异在「显存模型」，不在接口

同样是画一个点，两边对"坐标"的理解完全不同：

| 维度 | STM32 + OLED (SSD1306) | ESP32 + LCD (ST7796) |
|---|---|---|
| 总线 | I2C1，2 根线，400kHz | SPI3，4 根线，**10MHz** |
| 颜色 | 1 bit 单色 | RGB565，**16 bit** |
| 显存组织 | **页寻址**：8 页 × 128 列，1 字节 = 纵向 8 个像素 | **像素寻址**：x/y 就是像素，1 像素 = 2 字节 |
| 片选 | I2C 器件地址 0x78 | PCA9557 的 IO0 拉 CS |
| 背光 | 自发光，靠 `0x81` 对比度命令 | 必须外部背光 PWM |

**页寻址是什么意思：** SSD1306 的显存按"8 行一页"切，一个字节管**纵向 8 个点**。所以 y 坐标不能直接下发，必须换算：

```c
// STM32：y 要先拆成"第几页"和"页内偏移"
uint8_t offset = y % 8;              // 页内偏移，用 0xD3 设
uint8_t page   = (y - offset) / 8;   // 第几页，用 0xB0+page 设
for (i = 0; i < font_size / 8; i++)  // 16x16 汉字占 2 页
    OLED_Set_Pos(x, page + i);
```

**像素寻址是什么意思：** ST7796 的 GRAM 按像素排，给 x/y 就是像素坐标：

```c
// ESP32：没有"页"，y 就是一个像素一行
for (uint32_t y = y_s; y < y_e; y++)
    esp_lcd_panel_draw_bitmap(g_panel_handle, x_s, y, x_e, y + 1, pic + (y - y_s) * width);
```

一句话：**OLED 写的是"第几页第几列的 8 个点"，LCD 写的是"第几行第几个像素"。**

### 4. ★★ 「命令还是数据」告诉屏幕，I2C 和 SPI 用了两种思路

这是两边最容易被忽略、但最本质的差别。

**I2C 只有两根线，没有富余引脚，只能把标志塞进协议本身** —— 先发一个控制字节：

```c
// STM32：第三个参数 0x40 = 数据，0x00 = 命令
HAL_I2C_Mem_Write(&hi2c1, 0x78, 0x40, I2C_MEMADD_SIZE_8BIT, &dat, 1, ...);
//                           ^^^^ 这个就是"命令/数据"标志
```

**SPI 引脚富裕，直接多拉一根 DC 线用高低电平区分：**

```c
// ESP32：框架内部自动翻转 DC 脚
.dc_gpio_num = GPIO_NUM_39,
```

所以 STM32 那边每次写字节都要多传一个 `cmd` 参数，而 LCD 的调用方完全不用关心这件事。

**同一个道理还体现在字库上。** OLED 字库的存储格式**就是屏幕显存格式**（纵向 8 点一字节），可以直接丢给屏幕：

```c
OLED_WR_Data((uint8_t*)&g_font_dot_matrix_16[no][font_size * i], font_size);  // 原样发
```

LCD 要 RGB565，1 bit 必须先**逐位展开成 16 bit**：

```c
// lcd_display_char 里做的事
for (i = 0; i < font_size * font_size / 8; i++) {
    tmp = g_font_dot_matrix_16[index][i];                  // 取 1 字节 = 8 个点
    for (j = 0; j < 8; j++) {
        pixels[pixel_idx] = (tmp & (1 << j)) ? fc : bc;    // 每个点展开成 2 字节
        pixel_idx++;
    }
}
```

一个 16×16 汉字：OLED 是 **32 字节**，LCD 展开后是 **512 字节**，放大 16 倍。这也是为什么 OLED 用 400kHz 的 I2C 就够，而这块屏必须上 10MHz 的 SPI。

### 5. ★ 封装层越厚，越要会往下翻源码

STM32 那边 SSD1306 的初始化是照数据手册一条条写死的，三十多条命令全在 `oled.c` 里，想看什么直接看。

ESP32 这边 `lcd_init()` 只填三个结构体：

```c
spi_bus_config_t        buscfg       = { ... };   // 总线
esp_lcd_panel_io_spi_config_t io_config = { ... };   // DC/时钟
esp_lcd_panel_dev_config_t    panel_config = { ... }; // 位数/字节序
esp_lcd_new_panel_st7796(io_handle, &panel_config, &g_panel_handle);
```

厂商初始化序列、MADCTL、DMA、事务队列全在 `managed_components/espressif__esp_lcd_st7796/` 里。

**好处是代码短，代价是不透明** —— 想知道它到底发了哪些命令、默认 MADCTL 是什么，得进去翻 `esp_lcd_st7796_general.c`，猜不出来。

## 二、知识点

### 1. ★★★ `Verification of RAMCode failed` 不是驱动问题，要先查芯片 RAM

J-Link 烧 Flash 不是它自己写，而是**先往目标芯片的 RAM 里下载一小段"Flash 编程算法"（RAMCode），再让芯片自己的 CPU 去执行这段代码擦写 Flash**。

这段 RAMCode 的存放地址是**固定的 `0x20000010`**（RAM 起始 + 16 字节，前面留给栈和参数）。

所以报这个错，可能的原因只有三种，**排查顺序不能反**：

| 顺序 | 查什么 | 怎么查 |
|---|---|---|
| 1 | **芯片 RAM 有没有坏** | 手动往 `0x20000010` 写几个不同数据，看读回是否一致 |
| 2 | 速度太快 | 400kHz → 100kHz 再试 |
| 3 | 驱动版本 | 换 J-Link 软件版本 |

**我这次反了，先去换驱动版本（V6.86 → V4.92），白折腾了半小时。** 正确的做法是先用两行命令验证 RAM：

```
w4 0x20000010, 0xAAAAAAAA     → 读回 AA AA AA AA？
w4 0x20000010, 0x55555555     → 读回 55 55 55 55？
```

**判据：如果低半字对、高半字错，或者干脆写不进去，就是 RAM 坏点。** 换驱动、降速度都没用，只能换芯片。

**用 `0xAAAAAAAA` 和 `0x55555555` 这种"高低半字相同"的值测不出来**（我当时先用 `A5A5A5A5` 测的，看起来全对，其实是错的）。**必须用高低半字不同的值。**

### 2. ★★★ CubeMX 默认栈 1KB 撑不住 printf + 浮点，会 HardFault

CubeMX 生成工程时默认 `Stack_Size = 0x400`（1KB）。这个项目里根本不够：

| 吃栈的东西 | 大概占用 |
|---|---|
| `printf` 格式化（哪怕只印几个 int） | 300～600 字节 |
| 软浮点运算（`sqrtf` / `acosf` / 浮点除法） | 100～300 字节 |
| 中断嵌套 | 几十字节 |
| 逆解的函数调用链 | 100～200 字节 |

加起来轻松破 1KB。**栈溢出后不会立刻报错，而是悄悄地覆盖变量区**，表现是莫名其妙的 HardFault、数据错乱、或者"程序跑一会儿就不动了"。

**判断方法：** `halt` 之后看 SP，如果 SP 的值落进了 ZI 段（变量区）的地址范围内，就是溢出。

```
编译报告的 ZI-data = 1424 字节 → 变量区占 0x20000000 ~ 0x20000590
halt 后读到的 SP = 0x20000580 → 已经在变量区里面了 ← 溢出
```

**改法（两处都要改，防止 CubeMX 重新生成时冲掉）：**

```
MDK-ARM\startup_stm32f103xb.s  →  Stack_Size EQU 0x400 改成 0x1000
Arm.ioc                        →  ProjectManager.StackSize=0x1000
```

**改完判据：** 编译报告的 `ZI-data` 从 1424 涨到 4496。**如果还是 1400 多，说明没改成功。**

### 3. ★★ 读 CFSR/HFSR 能快速定位 HardFault 的原因

HardFault 只是个"总称"，具体原因藏在两个寄存器里：

| 寄存器 | 地址 | 关键位 |
|---|---|---|
| **CFSR**（可配置故障状态） | `0xE000ED28` | bit0 指令访问违规 / bit1 数据访问违规 / bit9 精确总线错误 / **bit10 不精确总线错误** / bit16 非法指令 / bit24 非对齐访问 / bit25 除零 |
| **HFSR**（硬件故障状态） | `0xE000ED2C` | bit1 向量表错误 / **bit30 FORCED（由其他 fault 升级）** |

```
halt
regs                        → 看 IPSR，003 = HardFault，000 = 正常
mem 0xE000ED28, 4           → CFSR
mem 0xE000ED2C, 4           → HFSR
```

**我这次读到 `CFSR = 0x400`（bit10，不精确总线错误）+ `HFSR = 0x40000000`（FORCED）。**

"不精确"的意思是：CPU 写了非法地址，但因为有写缓冲，错误延迟了几条指令才报出来，所以**无法定位到具体是哪一行代码**。**遇到 IMPRECISERR，第一个怀疑对象就是栈溢出或野指针。**

对比一下：如果读到 bit9（PRECISERR，精确总线错误），说明是当前这条指令访问了非法地址，那就直接查 PC 指向的代码。

### 4. ★★ 核心板上的 Type-C 不是串口

STM32F103C8T6 核心板（Blue Pill 类、立创天空星）的 USB 口只有两个功能：

```
VBUS (5V)  →  给板子供电
D+ (PA12) ┐
D- (PA11) ┘  →  只是把引脚引出来，芯片内部没有 USB 转串口控制器
```

**没有任何 CH340/CP2102/FT232 芯片。** 所以插上电脑：

- 能供电（所以 J-Link 能读到 `VTref = 3.3V`）
- **不会出现 COM 口**（不是坏了，是本来就没有）

要做成虚拟串口，得在 STM32 里跑 USB CDC 设备固件（CubeMX 里配 USB Device + 加中间件），和 USART1 是两套完全不同的东西。

**想和 STM32 通信，只有三条路：**
1. **底板上的 CH340K**（中控板底板自带）→ 插 USB 就有 COM 口
2. 外接 USB-TTL 模块 → 接 PA9/PA10
3. J-Link RTT → 通过 SWD 线在内存里传数据，不用额外硬件

### 5. ★ 两个 AMS1117 不能同时输出

底板和核心板**各有一个 3.3V 稳压器**，而且两边 3V3 网络在板上是连通的：

```
底板 USB-C → 底板 AMS1117 → 3V3 ─┐
                                  ├─ 同一根 3V3 网络
核心板 Type-C → 核心板 AMS1117 → 3V3 ┘
```

**同时插两根 USB，两个稳压器会互相灌电流**，轻则发热，重则烧一个。

**规矩：一次只让一个稳压器工作。**

- 用底板 USB（为了让 CH340 工作）→ **底板 SW1 拨到 ON，核心板 Type-C 不插**
- 用核心板 USB → 底板 SW1 拨到 OFF（这样底板 AMS1117 不输出）

**推荐第一种**，一根线同时解决供电和串口。

### 6. ★ 程序"能烧进去"和"能跑起来"是两件事

烧录成功只说明 Flash 内容写对了。程序跑不跑得动是另一回事。

**验证程序真在跑的三个办法（不需要串口）：**

| 办法 | 命令 | 判据 |
|---|---|---|
| **看 IPSR** | `halt` + `regs` | `IPSR = 000 (NoException)` 才是正常；`003` 就是 HardFault |
| **看 PC/LR** | 同上 | PC 或 LR 落在 `0x08000000~0x08010000`（Flash 区）说明在执行我们的代码 |
| **看 SP** | 同上 | SP 落在 RAM 区且没进变量区 |

**我这次就是靠 `IPSR = 003` 发现程序崩了的**，否则看到 `O.K.` 会误以为一切正常。

## 二、知识点

### 1. ★★★ SCARA 平面二连杆逆解就是余弦定理，不需要 DH 参数

平面两连杆，末端坐标 (x, y)，臂长 L1、L2：

```
r² = x² + y²

cos(θ2) = (r² − L1² − L2²) / (2·L1·L2)
θ2 = ±acos(cos θ2)                    ← 正负号 = 两组解

θ1 = atan2(y, x) − atan2(L2·sin θ2, L1 + L2·cos θ2)
```

**就这三行。** 六个自由度才需要 DH 参数和雅可比矩阵，平面两连杆用不着。

正解（验证用）：

```
x = L1·cos θ1 + L2·cos(θ1 + θ2)
y = L1·sin θ1 + L2·sin(θ1 + θ2)
```

**验证方法：正解 → 逆解 → 正解，闭环比对。** 14400 个姿态跑下来，最大往返误差 0.000121mm，说明公式和符号全对。这是装机械之前唯一能确认的事。

**`acos` 之前必须夹住输入：**

```c
c2 = clampf(c2, -1.0f, 1.0f);   // 浮点误差会让 cos 略微超 1，进 acos 就是 NaN
```

边界上（两臂刚好伸直）几乎每次都会超一点点，不夹住就得到一个 NaN 角度，后面全崩。

**两组解怎么选：** 等长臂时两组解是镜像对称，抓取效果一样。但舵机行程只覆盖一侧，所以实际只能用一组。舍掉一组只损失"多一条绕行路径"，不影响能不能抓到。

### 2. ★★★ 末端方位角 = 大臂角 + 半个小臂角，这条决定了工作区长什么样

**我一开始把"大臂舵机能转 ±82°"直接当成"末端方位角只有 ±82°"，这是错的。** 实际单圈能扫 164°，但扫出来的不是一片正扇形，是一片"扭过的扇形"。

**推导（等长臂 L1 = L2 = L）：**

```
正解：x = L[cos θ1 + cos(θ1+θ2)]
      y = L[sin θ1 + sin(θ1+θ2)]

和差化积：cos A + cos B = 2·cos((A+B)/2)·cos((A−B)/2)
          sin A + sin B = 2·sin((A+B)/2)·cos((A−B)/2)

代入 A = θ1、B = θ1+θ2：

  r = 2L·cos(θ2/2)          ← 半径只由小臂角决定，和大臂角无关
  φ = θ1 + θ2/2             ← ★ 末端方位角 = 大臂角 + 半个小臂角
```

**两条结论同时成立：**

1. **φ 的跨度 = θ1 的跨度 = 164°**（因为 θ2/2 只是平移，不改变宽度）
2. **但整个 164° 的区间被 θ2/2 推着走**，而 θ2 随半径变（近处大、远处小）

**实测数据：**

| r (mm) | θ2 (°) | φ 中心 (°) | φ 范围 (°) |
|---|---|---|---|
| 20 | 171.6 | 85.8 | 3.8 ～ 167.8 |
| 100 | 137.2 | 68.6 | 346.6 ～ 150.6 |
| 200 | 86.2 | 43.1 | 321.1 ～ 125.1 |
| 270 | 19.6 | 9.8 | 287.8 ～ 91.8 |

**每条弧跨度都是 164°，但中心从 85.8° 漂到 9.8°，漂了 76°。**

所以：

| 项目 | 真值 |
|---|---|
| 单半径方位覆盖 | **164°** |
| φ 中心漂移 | **76°**（内圈偏左，外圈偏前） |
| 全半径公共方位（r 120～260） | **118°**，φ ∈ [−18°, 100°] |
| 形状 | **斜扇环**，不是圆盘也不是正扇形 |

**164° 的来源：** 大臂舵机 `SERVO1_MIN_DEG=8 / SERVO1_MAX_DEG=172`，180° 行程两头各留 8° 安全余量。**这 8° 不能省**，顶到 0°/180° 的后果是嗡嗡响、发热、烧掉。

**★ 装配时要考虑 φ 的偏置。** 大臂中位对准 +X（`THETA1_HOME = 0`）时，工作区整体偏向 +Y（左侧），因为 θ2/2 恒为正。想让工作区居中，`THETA1_HOME` 要设成 −40° ～ −50°，或者把底座整体转个角度。

**中位选在哪，还决定能覆盖多大的半径：**

| 小臂中位 | θ2 可取值范围 | 对应半径 | 解的组数 |
|---|---|---|---|
| 90°（折成直角） | 0 ～ 180° | 20 ～ 274mm | **只有一组** |
| 0°（直臂） | −82 ～ +82° | 207 ～ 274mm | 两组 |

**所以小臂舵机必须装在"折 90°"的位置，不是"伸直"的位置。** 这是装配时就要定下来的，装错了半径范围直接砍掉三分之二。

### 3. ★★ 细分和电流是两个独立参数：一个管分辨率，一个管扭矩

驱动器上 6 个拨码，前三个管细分，后三个管电流，**互不影响**。

```
脉冲当量 = 丝杆导程 ÷ (200 × 细分)
         = 4mm ÷ 1600 = 0.0025mm/脉冲

转速 = 脉冲频率 ÷ (200 × 细分) × 60
     = 8000 ÷ 1600 × 60 = 300 RPM
```

**细分不是越高越好：**

| 细分 | 脉冲当量 | 20mm/s 所需频率 | 问题 |
|---|---|---|---|
| 8 | 0.0025mm | 8 kHz | 正常 |
| 16 | 0.00125mm | 16 kHz | 光耦和中断压力翻倍 |
| 32 | 0.000625mm | 32 kHz | 3.3V 驱动光耦开始丢脉冲 |

**判据：细分精度只需要做到机械精度的一半。** T8 丝杆的重复精度只有 0.02～0.05mm，把细分做到 0.0006mm 纯属浪费，代价是频率翻倍。

**电流决定扭矩，但和细分无关：**

```
驱动器设 1.0A → 电机出约 3.2 kg·cm
驱动器设 0.5A → 电机出约 1.6 kg·cm（和电流近似线性）
```

**电机型号里通常编码了参数。** 这只 `42SHDC1067Z` 的后四位 `1067` 就是 **1.0A / 6.7Ω**。查不到手册时，先看型号编码。

### 4. ★★ 舵机受力要分两笔账：转动扭矩和悬臂弯矩

很多人把"转得动"和"撑得住"混成一件事，其实是两个独立的力，量纲都不一样。

**第一笔：绕 Z 轴的转动扭矩（决定转不转得动）**

```
转动惯量 J = Σ m·r² ≈ 0.0205 kg·m²
0.2s 加速到 90°/s → α = 7.85 rad/s²
所需扭矩 = J × α = 0.161 N·m = 1.64 kg·cm
加摩擦算 3 kg·cm
```

**MG996R 有 9.4 kg·cm，3 倍余量，够。**

关键洞察：**SCARA 是水平构型，臂在水平面内摆动，重力垂直向下，转动时根本不用对抗重力。** 所以转动这一笔账特别轻松。

**第二笔：压在输出轴上的悬臂弯矩（决定会不会耷拉）**

```
各部件重量 × 到回转轴的距离：
  大臂      200g × 6.8cm  = 1.36 kg·cm
  小臂舵机   55g × 13.7cm = 0.75
  小臂      200g × 20.5cm = 4.10
  夹爪舵机   55g × 27.4cm = 1.51
  夹爪       80g × 27.4cm = 2.19
  ─────────────────────────────
  合计 ≈ 9.9 kg·cm
```

**9.9 kg·cm 压在 5mm 输出轴上，超载 2～3 倍。**

**表现（装好立刻能看出来）：** 臂在水平位下垂、舵机持续嗡嗡响、松手回不到原位。

**缓解手段：** 降压到 6V（扭矩 9.4→11，但对弯矩没用）、缩短臂长（弯矩按距离平方衰减）、减重。

**教训：算舵机选型时，弯矩和扭矩要分开算。** 只算扭矩会得出"3 倍余量很安全"的错误结论。

### 5. ★★ 3.3V 的 MCU 和 5V 的光耦打交道，进出两个方向都有坑

**方向一：MCU 驱动驱动器（输出）**

驱动器输入端是光耦 LED + 内部限流电阻。共阳接法下，MCU 输出高电平时两端压差是：

| 共阳接 | MCU 输出高时压差 | 后果 |
|---|---|---|
| **3.3V** | 3.3 − 3.3 = **0V** | 光耦完全关断 ✔ |
| 5V | 5 − 3.3 = **1.7V** | 光耦半导通，脉冲乱发 ✘ |

**所以 3.3V 单片机的共阳一定要接 3.3V，不能接 5V。** 接 5V 时电压"看起来对"，实际光耦一直微微导通，表现为电机乱走、方向乱跳，极难排查。

代价是灌电流只有 (3.3−1.2)/270 ≈ 7.8mA，比 5V 时小，所以**高速时要拉满测一遍**，低速能转不代表高速能转。

**方向二：编码器/传感器进 MCU（输入）**

NPN 集电极开路输出 = **开漏**：输出低时把线拉到 0V，输出高时**线是悬空的**。

```
不加上拉 → MCU 永远读不到高电平
上拉接 5V → 高电平 5V 直接灌进 3.3V 的 IO
上拉接 3.3V → 正确
```

标准接法（上拉放器件侧，不是 MCU 侧）：

```
器件输出 ──┬── 4.7kΩ ── 3.3V
           └── 1kΩ ──── MCU 引脚
```

上拉放 MCU 侧会出问题：器件拉低时，3.3V 经 4.7k + 1k 分压，MCU 脚只有 0.58V，虽然勉强算低电平但余量很小。上拉放器件侧，MCU 脚能干净地到 0V。

**串 1k 是保险**：万一器件其实是推挽输出（5V 推挽），1k 把灌进 MCU 的电流限到 1mA，不会烧。

### 6. ★ 24V 电源端子和信号端子挨在一起，接线前必须量电压

驱动器从上看 12 个端子：

```
ENA− / ENA+ / DIR− / DIR+ / PUL− / PUL+   ← 信号（上面 6 个）
B− / B+ / A− / A+                          ← 电机（中间 4 个）
GND / VCC                                  ← 24V（最下面 2 个）
```

**`VCC` 在最底下，`ENA−` 在最顶上。** 顺着数接错，24V 直接进 STM32，整块板报废。

**规矩：上电前用万用表量一遍**——VCC 对 GND 是 24V，PUL+ 对 GND 是 3.3V，都对了再接 MCU。

另外 `B−/B+/A−/A+` 是 **B 在上、A 在下**，不是习惯的 A 在上。两相接反电机会反转（不影响），单相反了会原地抖不转。

## 三、踩的坑

1. **买滑台只看行程和价格，没看滑块尺寸。** 到货才发现滑块只有 1cm 宽，带 300g 外伸 150mm 的机械臂超载两倍。进度不受影响，但精度和寿命要打折。
2. **没预留夹板空间就选了"传感器贴着滑块"的滑台。** 传感器和滑块间隙几乎为 0，导致"上下夹板"方案全部作废，被迫改成"附加触发体"。
3. **工作空间的描述错了两回。** 第一回在交接文档里写"工作半径 0～274mm"，把数学上限当成了实际范围，没考虑舵机行程。第二回纠正时又走了另一个极端，把"大臂舵机能转 ±82°"直接当成"末端方位角只有 ±82°"——实际单圈能扫 164°。错因是没意识到 θ1 和末端方位角 φ 不是一回事。

## 二、知识点

### 1. ★★★ ESP-IDF 工程分四层，别人的包里永远缺第三层

| 层 | 是什么 | 别人的包里 | 换机器要动吗 |
|---|---|---|---|
| 源码层 | `main/*.c`、`main/*.h`、`CMakeLists.txt` | 有 | 不用 |
| 芯片层 | `sdkconfig`（里面是 `CONFIG_IDF_TARGET`） | 有 | 换芯片要重配 |
| **本机层** | **`.vscode/`**（IDF 装在哪、串口号、target） | **通常没有** | **必换** |
| 产物层 | `build/` | 有时被打包进来 | **必删** |

`.vscode/` 不是工程的一部分，是"这台电脑的身份证"。ESP-IDF 插件靠它里面的 `idf.currentSetup` 判断"这是个 IDF 工程"，缺了就**不注入 include path**，C/C++ 满屏红线；同时 CMake Tools 插件会自己拿本机 mingw64 的 gcc 去 configure，多出一个错的 `build/`。

所以正确做法是：**每台电脑维护一份 `.vscode` 母版，所有工程共用，新工程直接复制**。只有三个字段可能变：`idf.currentSetup`（IDF 路径）、`idf.customExtraVars.IDF_TARGET`（芯片型号）、`idf.port`（串口号）。

`build/` 必须删的理由：里面的 `CMakeCache.txt` 和 `compile_commands.json` 全是别人机器的绝对路径。CMake 看到路径没变就认为"不用重新配置"，继续用错工具链。

### 2. ★★ I2C 只需要 4 个函数，读和写的区别就一句话

```
写： S | 地址+W | 寄存器号 | 数据 | P
读： S | 地址+W | 寄存器号 | Sr | 地址+R | 数据 | P
```

| 函数 | 干什么 |
|---|---|
| `i2c_new_master_bus()` | 铺一根线（配 SCL/SDA 引脚 + 时钟） |
| `i2c_master_bus_add_device()` | 往线上挂一台设备，登记地址，拿到 `dev` 句柄 |
| `i2c_master_transmit(dev, buf, len, to)` | 只发不收（写） |
| `i2c_master_transmit_receive(dev, &reg,1, data,1, to)` | 先发寄存器号再收数据（读） |

**总线是总线，设备是设备。** 建完总线只拿到总线句柄；挂完设备才拿到设备句柄。以后所有读写都用设备句柄，不再用总线句柄。

**一条总线可以挂多个从机，靠 7 位地址区分。** 这块板上：

- `PCA9557` = `0x19`，I2C 转 8 个 GPIO 的扩展芯片，管 `LCD_CS` / `PA_EN` / `DVP_PWDN` 这类开关脚
- `FT6336` = `0x38`，触摸控制 IC

PCA9557 就三个寄存器：`0x00` 输入（只读）、`0x01` 输出、`0x03` 配置（**写 1 = 输入，写 0 = 输出**，容易记反）。

**主机的真身是 ESP32 内部的 I2C 控制器外设**，不是 CPU 核心直接怼。所以配置时要指定 `i2c_port`（用 I2C0 还是 I2C1）。

### 3. ★★ 触摸屏：FT6336 和 gslX680 差的是"一整层内核驱动"

| | ESP32 / FT6336 | GEC6818 / gslX680 |
|---|---|---|
| 数据怎么来 | 自己的代码调 `i2c_master_transmit_receive()` 读寄存器 | `read()` 读 `/dev/input/event0` 的 `struct input_event` |
| 读什么 | `0x02` 触摸点数，`0x03~0x06` 四字节坐标 | `EV_ABS/ABS_X`、`EV_ABS/ABS_Y`、`EV_KEY/BTN_TOUCH` |
| 数据形态 | **一次拿到完整快照** `{state,x,y}` | **事件流**，一个动作拆成好几条 |
| 谁驱动 | 自己 `while(1)` 轮询 | LVGL 定时器回调 `read_cb`，被动被拉 |
| 芯片校验 | 读 4 个 ID 寄存器验明正身 | 不用管，内核验过了 |
| 输出 | 自定义 `tp_data_t` | `lv_indev_data_t`，直接喂 LVGL |

分层看就一句话：

```
GEC6818：芯片 → [内核驱动] → evdev 事件队列 → 你的 touch_input.c → LVGL
ESP32  ：芯片 → 你的 tp.c → 自定义结构体
```

**ESP32 上做的事，等于把"内核驱动 + evdev"两层的活自己干了。** 换算下来，`tp.c` 那 200 行里跟 LVGL 有关的只有最后几行，其余 150 行都在当驱动用。

接 LVGL 只差一个回调：

```c
static void tp_read_cb(lv_indev_t *indev, lv_indev_data_t *data)  // LVGL 每次刷新会调这个
{
    tp_data_t s;                                    // 装一次读到的快照
    tp_read_xy(&s);                                 // 调自己的驱动拿坐标
    data->point.x = s.x;                            // 填 X
    data->point.y = s.y;                            // 填 Y
    data->state = (s.state == TP_STATE_PRESS)       // 按下还是松开
                  ? LV_INDEV_STATE_PRESSED : LV_INDEV_STATE_RELEASED;
}
```

### 4. ★★★ PWM 的 `duty` 是"高电平占比"，亮度方向由 LED 极性决定

这是今天最容易搞混的一点，两层要分开算：

1. `duty` 是**高电平占整个周期的比例**（官方示例：13 位下 `duty = 4096` 就是 50%）
2. LED 亮不亮看**引脚是低电平还是高电平**（本板低电平点亮）

所以对这块板：

| duty（10 位 0～1023） | 引脚输出 | 灯 |
|---|---|---|
| `0` | 恒低 | **全亮** |
| `1023` | 恒高（实际约 99.9%） | **全灭** |

**STM32 那边反而是 CCR 越大越亮**，因为 `OCPolarity = LOW` 把"有效电平"定义成了低电平，`CCR` 越大低电平越长。两边数值含义相反，照抄代码会得到反方向的呼吸。

解法：ESP32 用 `ledc_channel_config_t` 里的 `.flags = { .output_invert = 1 }` 把输出反相，之后就是"数值大 = 引脚低 = 亮"，跟 STM32 的直觉一致。

### 5. ★★ LEDC 配置三步，第三步不能省

```c
// 1. 定时器：定频率和分辨率，可被多个通道共用
ledc_timer_config_t timer_cfg = {
    .speed_mode      = LEDC_LOW_SPEED_MODE,   // 低速模式
    .timer_num       = LEDC_TIMER_0,          // 定时器 0
    .duty_resolution = LEDC_TIMER_10_BIT,     // 10 位 → 占空比 0~1023
    .freq_hz         = 5000,                  // 5kHz
    .clk_cfg         = LEDC_AUTO_CLK,         // 时钟源自动选
};
ledc_timer_config(&timer_cfg);

// 2. 通道：绑定时器 + 绑定引脚
ledc_channel_config_t ch_cfg = {
    .speed_mode = LEDC_LOW_SPEED_MODE,        // 必须跟定时器一致
    .channel    = LEDC_CHANNEL_0,             // 通道 0
    .timer_sel  = LEDC_TIMER_0,               // 用哪个定时器（决定频率）
    .gpio_num   = GPIO_NUM_10,                // 输出引脚
    .duty       = 1023,                       // 初始占空比
    .hpoint     = 0,                          // 相位起点
    .flags      = { .output_invert = 1 },     // 输出反相
};
ledc_channel_config(&ch_cfg);                 // 配完就自动输出，没有单独的 Start

// 3. 改占空比：两句必须成对
ledc_set_duty(LEDC_LOW_SPEED_MODE, LEDC_CHANNEL_0, 500);  // 只写影子寄存器
ledc_update_duty(LEDC_LOW_SPEED_MODE, LEDC_CHANNEL_0);    // 这一句才推到引脚
```

**`ledc_update_duty()` 忘了写，现象是"代码在跑但灯一动不动"。** STM32 写 CCR 是立即生效的，ESP32 不是。

还有一个细节：10 位分辨率下最大只能写 `1023`，而 `1023/1024 ≈ 99.9%`，所以**永远到不了真正的 100%**，灯不会完全灭（或完全亮），差一丝。

### 6. ★ STM32 的 TIM 和 ESP32 的 LEDC 对照

| 维度 | STM32（TIM1） | ESP32（LEDC） |
|---|---|---|
| 外设性质 | 通用定时器，PWM 是它的一种模式 | 专用 PWM 外设 |
| 频率怎么定 | `Prescaler` + `Period` 两个数算出来 | 直接写 `freq_hz` |
| 分辨率 | 由 `Period` 隐含（999 → 10 位） | 显式声明 `duty_resolution` |
| 改占空比 | `__HAL_TIM_SET_COMPARE()`，立即生效 | `ledc_set_duty()` + `ledc_update_duty()` |
| 启动 | `HAL_TIM_PWM_Start()` | 通道配置完自动跑 |
| 引脚绑定 | CubeMX 选引脚 → 配复用 | 通道配置时直接写 `gpio_num` |
| 互补输出/死区 | 硬件自带（CH1/CH1N、BDTR） | 没有 |

RTOS 下两边还有两个差异：

1. **入口身份**：STM32 要 `main()` → `osKernelStart()`，业务代码必须放进任务；ESP32 的 `app_main()` **本身就是 FreeRTOS 任务**，可以直接写 `while(1)`。
2. **tick 频率会影响 `pdMS_TO_TICKS()`**：ESP-IDF 默认 `CONFIG_FREERTOS_HZ=100`，1 tick = 10ms，`pdMS_TO_TICKS(2)` 算出来是 **0**，`vTaskDelay(0)` 只是让出 CPU 不延时。要精确到毫秒级得把 tick 改成 1000，或者不用延时计时、改用 `esp_timer_get_time()` 读时间戳判断。

## 二、知识点

### 1. ★★★ `idf_component_register` 三个参数各管什么

```cmake
idf_component_register(SRCS "main.c" "led.c"
                       INCLUDE_DIRS "."
                       PRIV_REQUIRES esp_driver_gpio esp_timer)
```

| 参数 | 填什么 | 路径相对谁 |
|---|---|---|
| `SRCS` | **自己写的** `.c` 文件 | 组件目录（`main/`） |
| `INCLUDE_DIRS` | **自己写的**头文件所在目录 | 组件目录（`main/`） |
| `PRIV_REQUIRES` | **别人的**组件名，不是文件名 | —— |

口诀：**前两个说"我有什么"，后两个说"我要谁的"**。

`SRCS` 是白名单，不列进去的文件压根不参与编译，也不会出现在 `compile_commands.json` 里。ESP-IDF 没有"自动收集目录下所有 .c"这回事。

`SRC_DIRS` 能扫目录，但源码里写的是 `file(GLOB "${abs_dir}/*.c")`：**只扫一层不递归**，且不带 `CONFIGURE_DEPENDS`，新增文件后必须 `idf.py reconfigure` 才生效。所以文件少时老老实实列 `SRCS`。

`REQUIRES` 和 `PRIV_REQUIRES` 的区别：判据是**你的 `.h` 里 include 了谁**。只在 `.c` 里 include 的写 `PRIV_REQUIRES`；写在公开头文件里的写 `REQUIRES`（因为依赖你的人也得看得见）。`main` 是顶层组件没人依赖它，一律 `PRIV` 就够。

### 2. ★★★ `xxx.h: No such file` = 组件没声明，不是路径问题

ESP-IDF 里能不能 include 成功，只看**该文件的编译命令里有没有对应的 `-I` 目录**，跟文件在不在硬盘上无关。而 `-I` 目录是构建系统按 `PRIV_REQUIRES` 算出来的。

三步自查：

```bash
# 1. 这个头属于哪个组件
cd /e/a2_QianRuShi/ESP/v5.5.5/esp-idf/components
ls */include/esp_timer.h
# → esp_timer/include/esp_timer.h   → include 前面那层就是组件名

# 2. 看现在写了什么
cat main/CMakeLists.txt

# 3. 加上再 build（CMakeLists 变了会自动 reconfigure，不用删 build）
```

通配符只替换组件名那一层，`include/` 后面的路径要原样带上：`#include "driver/gpio.h"` 就查 `ls */include/driver/gpio.h`。

常用对照：

| 头文件 | 组件名 |
|---|---|
| `driver/gpio.h` | `esp_driver_gpio` |
| `driver/i2c_master.h` | `esp_driver_i2c`（5.x 老名字 `driver/i2c.h` 已删） |
| `driver/spi_master.h` | `esp_driver_spi` |
| `nvs_flash.h` | `nvs_flash` |
| `esp_timer.h` | `esp_timer` |
| `esp_log.h` / `freertos/*` | 公共依赖，**不用写** |

### 3. ★★★ ESP32 的 GPIO 中断是"查表"，STM32 是"向量表"

| | STM32 | ESP32 |
|---|---|---|
| 硬件中断源 | 每个引脚组一个（`EXTI15_10` 等） | **所有 GPIO 共用一个** |
| 入口绑定 | 编译期写死，链接器填向量表 | **运行期**查数组 `gpio_isr_func[]` |
| 怎么知道是哪个脚 | 自己在回调里比 `GPIO_Pin` | 驱动读状态寄存器拿位图 |
| 清中断标志 | 软件写 `EXTI->PR`（写 1 清零） | **驱动替你清** |
| 使能 | `EXTI->IMR` + `NVIC_EnableIRQ` | `gpio_intr_enable()` |

ESP32 的驱动里，`gpio_isr_func` 是一张**按引脚号索引的数组**，每项存 `fn` 和 `args`。中断来时读状态寄存器拿到位图，位号直接当数组下标取，所以虽然是"查表"但仍是 O(1)，没有遍历开销。

STM32 里中断标志**不清会死循环**：ISR 退出后 `EXTI->PR` 还是 1，NVIC 看到挂起标志立刻再次进同一个中断，程序卡死在中断里，主循环一行都不跑（"中断风暴"）。ESP32 没这个坑，驱动在你回调返回后统一清。

### 4. ★★★ "关 → 填 → 开" 只发生在注册阶段

`gpio_isr_handler_add()` 内部三步：

```c
gpio_intr_disable(gpio_num);                                 // 关这个脚的中断
gpio_isr_func[gpio_num].fn   = isr_handler;                  // 填函数地址
gpio_isr_func[gpio_num].args = args;                         // 填原样保存的参数
gpio_intr_enable_on_core(gpio_num, ...);                     // 开
```

**为什么必须先关**：填表是两条语句，中间可能被中断打断。如果那时中断来了，驱动会读到"`fn` 已经是我的函数、`args` 还是 NULL"的半成品，直接崩。

中断真正触发时**只查表不填表**，整个程序寿命里"填"只做一次。

`args` 存的意义：驱动只知道"0 号脚触发了"，不知道你管它叫 KEY1。把当初登记的参数原样传回去，两个键才能共用同一个回调、靠 `arg` 区分。

### 5. ★★ ISR 的三条铁律

1. **不能 `printf`**。ISR 借的是被打断任务的栈，没有任务控制块，而 `printf` 内部要拿锁、要动态分配——这些在中断上下文里没有意义甚至崩。
2. **只能用 `FromISR` 版 API**。`xQueueSendFromISR` 而不是 `xQueueSend`，因为前者不会阻塞。
3. **结尾要 `portYIELD_FROM_ISR(hp)`**。不写也能工作，但任务要等到下一个 tick 才被唤醒，默认 tick 100Hz 就是最多延迟 10ms。

`hp` 是**局部变量**，每次进中断都重新初始化为 `pdFALSE`，**不需要用完清零**。写成 `static` 才是错的——它会一直保留上次的 `pdTRUE`，导致每次中断都强制切任务。

`IRAM_ATTR` 的真正原因：ESP32 的代码默认在**外部 Flash**，靠 Cache 映射执行。写 Flash（NVS 保存、OTA）时 Cache 必须关闭，Flash 里的代码全都取不出来，此时来中断就崩。放 IRAM 等于给个安全屋。**但只有中断用 `ESP_INTR_FLAG_IRAM` 分配时才必须**；默认标志（`gpio_install_isr_service(0)`）时 Flash 操作期间中断本来就被屏蔽了，加不加都行，属于好习惯。

### 6. ★★ 事件驱动 vs 轮询

```c
// 轮询：每 500ms 主动问一次"按了吗"
vTaskDelay(pdMS_TO_TICKS(500));
if (gpio_get_level(KEY1_PIN) == 0) ...

// 事件驱动：按键那一刻才被叫醒
xQueueReceive(g_queue_key_handle, &key_state, portMAX_DELAY);
```

轮询的根本问题是**采样间隔决定漏检**——按住的时长小于 500ms 就完全抓不到。而按 500ms 以内采样，CPU 又全耗在空转上。

`portMAX_DELAY` 让任务在队列空时彻底挂起，一个指令都不执行，CPU 拿去跑别的任务。有数据时调度器唤醒它，把数据**拷贝**进缓冲区。

队列深度 5 意味着最多缓存 5 个事件，满了 `xQueueSendFromISR` 返回 `errQUEUE_FULL`，事件就丢了。

### 7. ★★ 消抖必须做在 ISR 里，时间戳必须 `static`

机械触点在闭合瞬间会弹跳，产生好几个下降沿。一次按键就能把深度 5 的队列灌满。

```c
static int64_t last_ms = 0;
int64_t now = esp_timer_get_time() / 1000;   // 微秒转毫秒
if (now - last_ms < 20) return;
last_ms = now;
```

`static` 是这里的关键：把变量放进 `.bss`，函数退出不销毁，下次进中断还是上次的值。不加就变成每次都是 0，消抖完全失效。

`esp_timer_get_time()` 返回上电以来的微秒数，它是 ISR 安全的（实现在 IRAM，只读硬件计数器）。

**两个键共用同一个 `last_ms` 会互相吞**：KEY1 触发后 20ms 内按 KEY2，KEY2 被当抖动丢掉。严格做法是按引脚分开存：`static int64_t s_last_ms[GPIO_NUM_MAX]`。

### 8. ★★ 对着原理图核对：GPIO0 是 BOOT 键，不是用户键

| 网络标号 | 芯片引脚 | 按键 | 外部上拉 |
|---|---|---|---|
| `IO0_BOOT` | 27（GPIO0） | SW2 | **R2 10kΩ → 3V3** |
| `IO11` | 20（GPIO11） | SW3 | **R111 10kΩ → 3V3** |
| `RESET` | EN | SW1 | —— |

板上就三颗键：复位、BOOT、用户键。**用户键是 GPIO11，GPIO0 是 BOOT 键。**

由此得三个结论：

1. `key.c` 里 `.pull_up_en = GPIO_PULLUP_DISABLE` 是**对的**。外部已经有 10k 上拉，再开内部上拉属于重复。
2. 下降沿触发也对：松开 = 3V3（高），按下 = GND（低）。
3. GPIO0 是 strapping 脚（启动模式选择），但**有 10k 上拉**，正常上电不按键就是高电平，能正常启动。只有上电/复位那一瞬间正好按着，才会进下载模式。所以风险没想象中大，但这颗键本来就设计成 BOOT 用，拿它做普通按键容易在调试时误触。

## 二、知识点

### 1. ★★★ 脉冲当量：从"导程"和"细分"一路算到"每毫米多少脉冲"

这条链路每一步都不能跳，跳一步后面全错。

```
丝杆导程 L = 4mm        （丝杆转一圈，螺母走多远）
步距角 1.8°             → 电机一圈 200 步
驱动器细分 1600 脉冲/转  → 实际 8 细分（200 × 8 = 1600）
每转位移 = 4mm
────────────────────────────────────
脉冲当量 = 4 ÷ 1600 = 0.0025mm/脉冲
```

反过来用：

```
走 10mm   → 4000 个脉冲
走 100mm  → 40000 个脉冲
```

**注意"螺距"和"导程"不是一回事。** 说明书上写"螺距 2，导程 4"——螺距是相邻两条螺纹的距离，导程是转一圈轴向走的距离。多线螺纹的导程 = 螺距 × 线数，这里是 2 线。**计算一律用导程。**

### 2. ★★★ "地"有三个，共地和接大地是两件事

| 名词 | 是什么 | 需不需要 |
|---|---|---|
| 大地（Earth / PE） | 埋在地里的那根线，220V 的保护地 | **适配器两脚插头就没有** |
| GND / 0V | 直流电源负极，电路的参考点 | **必须共** |
| 信号地 | 信号回流路径，本质就是 GND | 跟着 GND 走 |

**共地 = 把所有电路的直流负极连成一个点，跟接不接大地完全无关。**

为什么必须共地：信号是**电压差**。STM32 输出"高电平"是相对 STM32 的 GND 3.3V，驱动器读"高电平"是相对驱动器的 GND。两边 GND 不连，就没有共同参考点，驱动器读到的是随机值。

打个比方：两个人比身高，必须站在同一块地板上。这块地板是 GND，它不需要是地球。

**为什么两脚插头就够**：24V 是安全特低电压（SELV），适配器内部有隔离变压器，220V 侧和 24V 侧没有电气连接，输出侧是"浮地"。**浮地照样可以共地**，因为共的是各器件之间，不是对大地。

### 3. ★★★ 电容补不了堵转电流，只能补瞬态缺口

先算清楚电容到底能提供多少：

```
I = C × ΔV / t

2200μF，允许压降 0.5V，撑 1ms：
I = 2200×10⁻⁶ × 0.5 / 0.001 = 1.1A
```

**2200μF 在 1 毫秒内只能补 1.1A。** 而舵机堵转是 7.5A（三个 MG996R）。

真要补 7.5A 持续 5ms，需要：

```
C = I × t / ΔV = 7.5 × 0.005 / 0.5 = 0.075F = 75000μF
```

这么大的电容，上电瞬间充电电流会直接触发模块限流保护。

**所以电容的真实作用是这四条，不是"让模块带得动"：**

| 作用 | 说明 |
|---|---|
| 抑制纹波 | 开关电源输出有几十 mV 纹波 |
| 补偿线阻线感 | 舵机线 20cm 有 0.1Ω，7A 时压降 0.7V，就近的电容顶上 |
| 稳定反馈环路 | DC-DC 模块本身需要输出电容才不振荡 |
| 吸收换相尖峰 | 舵机内部 H 桥换向产生的高频尖峰 |

**真正解决供电的是"分路 + 时序"，不是电容：**

1. 双路模块分开带（每路 1～2 个舵机，负载降到 30%）
2. 软件错开动作（大臂转到位→停→小臂转→停→夹爪动，不要同时启动）
3. 夹爪动作加超时（夹住后一直堵转 2.5A，必须 500ms 后停止输出）

**电容要装在负载端，不是模块端** —— 它补的是线阻造成的压降，装在模块那头没意义。

### 4. ★★★ 槽配方滑块，绝不能配圆销

机械配合有一条基本规则：

| 配合 | 作用 |
|---|---|
| 圆孔配圆销 | **定位**（限制两个方向） |
| 长槽配方滑块 | **导向**（限制一个方向，允许另一个方向滑动） |
| **圆销配长槽** | **错误**，会滚 |

直码上是 6.5mm 宽的长槽。如果塞一个外径 6 的圆柱衬套进去：

- 横向只有 0.5mm 间隙（看着很好）
- **纵向能沿着槽滚 59mm**（废了）
- 而且垫片压圆柱端面是**切点接触**，不是面接触，3mm 冷轧钢反复受力会压出月牙凹坑

**正确做法：M3 螺丝直接穿过槽，用外径 10mm 的大垫片压住槽两侧的钢面。**

有人会担心"M3 螺丝在 6.5mm 槽里有 3.5mm 旷量"。但这里有个概念要分清：

| | 含义 |
|---|---|
| **可移动范围** | 螺丝松开时能在槽里滑多远 |
| **定位误差** | 锁紧后实际位置与期望位置的偏差 |

**松开时能滑 3.5mm 是"调节范围"，不是"误差"。** 锁紧后螺丝被约 200N 的摩擦力固定（M3 预紧力 500N × 摩擦系数 0.2 × 两侧），而臂的负载只有几牛，余量上百倍。

### 5. ★★ 步进驱动器的电源端必须并大电容

```
电机是感性负载
→ 每次换相，绕组电流方向反转
→ 电源线上产生尖峰，幅值可达供电电压的 2~3 倍（24V 系统能到 50~70V）
→ 没有电容吸收，驱动器 MOS 可能击穿

电机减速时，转子惯性带着电机发电
→ 能量倒灌回母线（"泵升电压"）
→ 母线电压被抬高
```

**所以在驱动器 VCC–GND 之间并 470μF/50V 电解电容，越靠近驱动器端子越好。**

耐压要按 24V 系统的 2 倍以上选，**50V 不是 16V**。

### 6. ★★ 地环路是怎么来的，怎么避免

错误接法：

```
适配器 → 驱动器 ─→ STM32 ─→ 模块 ─→ 适配器
         ↑________电流绕一圈________↓
```

电机换相的脉冲电流会在这个环路上流动，在地线上产生压降，叠加到信号上。

**症状：串口乱码、编码器丢脉冲、ADC 读数跳。**

正确做法：**星型接地**——所有 GND 从一个汇流点分出去，不要互相串联成环。洞洞板上用一条粗铜线当 GND 母线，所有器件的地都接到这条线，**只在一个点连到适配器的 24V−**。

### 7. ★★ ESP32 强在算力和无线，不强在实时控制

| | STM32F103 | ESP32 |
|---|---|---|
| 主频 | 72MHz | 240MHz 双核 |
| RAM | 20KB | 320～512KB |
| **脉冲抖动** | 定时器硬件输出，**< 1μs** | WiFi/BT 中断会打断，**可达几十 μs** |
| 无线 | 无 | 自带 |

**工业控制看"确定性"，不看"算力"。**

步进要发 40000 个脉冲走 100mm。脉冲间隔抖几十微秒就会丢步，表现是"偶尔走不准"，极难排查。

ESP32 也能发精确脉冲（用 RMT 外设，硬件不依赖 CPU），但那等于把无线功能关掉不用，只剩一个更贵的 MCU。

**架构上 PC 已经承担了视觉和语音，MCU 不需要联网，ESP32 的无线优势用不上。**

### 8. ★★ 舵机三线：中间那根永远是 VCC

| 颜色 | 功能 |
|---|---|
| 棕 / 黑 | GND |
| **红（中间）** | **VCC +5V** |
| 橙 / 黄 / 白 | 信号 PWM |

**"中间线是正极"是所有舵机的通用约定。**

但**插头顺序不一定一样**：有的是"信号-电源-地"，有的是"电源-信号-地"。接之前看线的颜色，别按排针位置硬插——信号线接到 5V 上，舵机瞬间烧。

另外 MG996R 工作电压 **4.8～6.6V**，接 12V 直接烧。24V 系统必须经降压模块转 5V。

### 9. ★★ "5A 降压模块"的 5A 是芯片能力，不是持续输出

XL4015 的 5A 是芯片手册的最大值，模块这么小的 PCB 没有散热，**持续能力大概只有 3A**。

判断一个模块能带多少，看三个东西：

1. 有没有散热片（有散热片的 3A 模块，可能比无散热片的 5A 模块更凉快）
2. 输出的电解电容容量（220μF 和 470μF 不是一个档次）
3. 卖家有没有写"建议持续 XX A"（肯写这句的通常比较实在）

**而且 DC-DC 只能降压不能升压**，24V 输入输出最高就是 24V。要给步进供 24V，只能从**模块的输入端**并联取，不能走输出。

---

## 三、踩的坑

1. **以为降压模块能"输出 24V 给步进"**。模块只能降不能升，24V 要从输入端并联取——多走一级转换纯属浪费，还多一份损耗。
2. **以为加大电容就能让 3A 模块带三个舵机**。算完才知道 2200μF 在 1ms 内只补 1.1A，7.5A 堵转根本补不了，真正起作用的是分路和错开时序。
3. **以为 ESP32 主频高就更适合做控制**。实时控制看的是抖动，不是算力，WiFi 中断反而让脉冲抖动变大。
4. **以为两脚的电源适配器"不能共地"**。共的是各器件之间的直流负极，不是接大地，隔离电源浮地照样能共。

## 二、知识点

### 1. ★★★ 有源蜂鸣器的音量下限，由工作电压决定，不由占空比决定

HNB09A05 的参数：`Driver Circuitry = 有源(内含驱动线路)`、`Voltage - Supply = 3V ~ 7V`。

```
4.8% 占空比（Pulse=6/125）   → 5V × 4.8%  = 0.24V   ← 差 12 倍
50%  占空比（Pulse=62/125）  → 5V × 50%   = 2.5V    ← 仍低于 3V 下限
NPN 低边驱动 Q2 的 Vce(sat) 再吃 0.6V → 蜂鸣器实际只拿到 4.4V
```

**结论：靠 PWM 调音量的可用区间只有 68%～100%，这个硬件上等于没有调音能力。**

要小声就串电阻或降到 3V3 供电，别指望压占空比。而且**"完全不响"和"声音小"是两种故障**，前者是电压不够起振，后者才是音量问题。

### 2. ★★★ STM32F1 在复用开漏（AF_OD）模式下，内部上拉是失效的

```c
GPIO_InitStruct.Mode = GPIO_Mode_AF_OD;
GPIO_InitStruct.Pull = GPIO_PULLUP;   // ← 这一行在 F1 上没有用
```

`Pull` 字段**只在输入模式下生效**。AF_OD 输出时引脚由外设驱动，内部上下拉电路不参与。

所以 I2C 的 SCL/SDA **只能靠外部上拉电阻**，软件救不了。拔掉 OLED 模块后 PB6/PB7 悬空实测 0V，就是这个缺陷的直接体现。

### 3. ★★★ I2C 总线悬空的连锁反应：从机状态机错位 → HAL_BUSY

```
排针接触一松 → 失去上拉 → PB6/PB7 悬空
  → 悬空的开漏线被人体电容 / 50Hz 工频拉低
  → SSD1306 收到乱码时钟+数据，内部状态机错位
  → 主机发 START 时检测到 SDA 低 → HAL_BUSY，连从机地址都发不出去
  → 之后所有传输立即失败 → 屏冻在旧画面
```

**实测铁证：手指碰一下 PB7（或测量时手碰到表笔金属头），屏立刻卡死。** 有上拉的话最多丢一帧，不会卡死 —— 差别就是总线上有没有那 0.7mA 在把它拉回高电平。

两个状态码指向不同硬件问题，别混：

| 返回码 | 含义 | 指向 |
|---|---|---|
| `st=2` HAL_BUSY | 总线被拉低 | 没上拉 / 短路 / 从机把线拽住 |
| `st=3` HAL_TIMEOUT | 地址发出去了没人应答 | 从机没供电 / 地址错 / 器件坏 |

### 4. ★★ 间歇性故障要用漏桶判定，不能用"连续 N 次失败"

原逻辑：

```c
if (失败) fail_count++;
else      fail_count = 0;        // ← 一成功就清零
if (fail_count >= 16) 判离线;
```

间歇性故障时，攒到第 15 次突然成功一次，计数清零，**永远攒不满 16**。表现是 `s_online` 一直为真，屏冻在 74 秒的画面却跑了四十多分钟。

改成漏桶：

```c
if (失败) err_score += 4;
else      err_score -= 1;        // 成功只减 1，不清零
if (err_score >= 16) 判离线;
```

**判据：能衰减、但不轻易归零的计数器，才认得出"大部分时候失败"这种状态。**

### 5. ★★★ 垂直轴丝杠会不会自己滑下去，取决于螺旋升角，不取决于电机

先分清两件事：

- **通电时**：步进电机有保持力矩（42 步进约 3.5 kg·cm），T8 导程 8mm 效率 0.6 → 推力约 16 kgf，扛得住整条臂。
- **断电时**：步进电机**没有保持力矩**，只剩 3～5% 的磁阻。这时能不能停住，纯看丝杠自锁。

自锁条件：**螺旋升角 λ < 摩擦角 φ**（钢-铜约 4～6°）。

```
λ = atan(导程 / (π × 中径))     T8 中径约 7mm
```

| T8 规格 | 导程 | λ | 自锁 |
|---|---|---|---|
| 1 线（螺距 2） | 2mm | 5.2° | 勉强自锁 |
| 2 线 | 4mm | 10.3° | 不自锁 |
| 4 线 | 8mm | 20° | 完全不自锁 |

工业上垂直轴用滚珠丝杠也不自锁，标准做法是**抱闸电机或配重块**。DIY 最便宜的办法是一根拉簧做配重（5 元），顺便减小电机负载。

### 6. ★★★ 机械臂构型决定逆运动学难度，差三个量级

| 构型 | 逆运动学 | 需要的数学 |
|---|---|---|
| **SCARA**（水平二连杆+升降） | 余弦定理求肘角，atan2 求肩角，两解取一 | **高中三角函数** |
| 圆柱坐标（旋转+直线伸缩） | 三轴完全解耦，各算各的 | 加减乘除 |
| 6 轴关节型 | DH 参数 + 齐次变换矩阵 + 雅可比 + 多解筛选 | 线性代数、矩阵 |

SCARA 的全部公式：

```
r = sqrt(x² + y²)
cos(θ2) = (r² - L1² - L2²) / (2·L1·L2)      → θ2 = ±acos(...)  两解
θ1 = atan2(y, x) - atan2(L2·sin θ2, L1 + L2·cos θ2)
```

**"画圆"不是单独写的算法**，是给定圆周上一串点、逐点代入上面公式的自然结果。

选构型时这条比"看起来简不简单"重要得多 —— 6 轴的机械看着差不多，数学门槛高一个数量级。

### 7. ★★ SCARA 构型下重力不产生关节转矩，但会产生径向负载

臂在**水平面**内旋转时，重力方向与舵机输出轴平行，**不产生绕轴的力矩**：

```
臂总重约 185g，重心半径 150mm
转动惯量 I ≈ 0.0042 kg·m²
加速时需要扭矩 ≈ 0.04 kg·cm
```

MG996R 有 9.4 kg·cm，余量三个数量级。这也是它跟 MeArm 的本质区别 —— MeArm 的臂是竖着举起来的，重力全压在舵机转矩上，2.2 kg·cm 的 MG90S 连 50g 都费劲。

**但径向负载是另一回事**：臂重垂直压在输出轴上，全靠舵机内部轴套扛，跑久了会松。工业做法是关节用轴承承重、电机只输出扭矩；DIY 短期可以直接扛，但要知道精度衰减是从这儿来的。

### 8. ★★ 舵机 180° 和 360° 不是"范围大小"的区别

| | 180° 角度舵机 | 360° 连续旋转舵机 |
|---|---|---|
| 1500μs | 停在 90° | **停止不动** |
| 2000μs | 转到 135° | **正转，速度与偏差成正比** |
| 输入含义 | **目标角度** | **转速 + 方向** |

360° 拆掉了角度反馈电位器，只知道"转多快"，不知道"转到哪"。**凡是要定位的关节，必须 180°。**

另外 180° 舵机在 0°/180° 附近会顶到机械限位，堵转电流 2.5A，几分钟就烧。软件限到 10°～170°，超范围直接拒绝执行。

## 二、知识点

### 1. ★★★ `osKernelStart()` 之前不许有任何阻塞或死循环

CubeMX 保留 `USER CODE BEGIN 2` 区，老工程那句 `app_main();` 留在原地。而 `app_main()` 内部是 `while(1)`，永远不返回：

```c
MX_FREERTOS_Init();
osKernelStart();     // ← 永远执行不到
```

**后果不是报错，是"板子照常跑裸机逻辑，你完全看不出 RTOS 没启动"。**

这是移植最容易踩的一脚，因为所有外设初始化都正常，串口也正常打印，只有调度器没起来。

**铁律：`main()` 里 `osKernelStart()` 之前只允许配外设，不许有任何业务逻辑。**

### 2. ★★★ `delay_ms` 改 `vTaskDelay`，一行解决 12 秒调度器停摆

```c
void delay_ms(int nms) { HAL_Delay(nms); }              // 改前
void delay_ms(int nms) { vTaskDelay(pdMS_TO_TICKS(nms)); }  // 改后
```

`HAL_Delay()` 是"读 uwTick 死等到够数"，**全程占着 CPU 不让出**。而 `esp_mqtt_init()` 里有 6 个 `delay_ms(2000)`，合计 12 秒。

改之前的串口是**完全静默 12 秒**（LoRa 那 6 帧全丢）；改之后两个任务交错输出：

```
[21:29:10.836] [init] 7/10 connect_server     ← MQTT 在连服务器
[21:29:11.304] [lora] #9  type=1 v1=252 v2=590   ← LoRa 同时收数据
[21:29:13.003] [init] 8/10 entry_transparent
[21:29:13.309] [lora] #10 type=1 v1=251 v2=589
```

**只改底层一个函数，上层几十处调用全部自动生效。**这比逐个替换调用点可靠得多。

### 3. ★★★ 中断 → 信号量 → 任务，替掉轮询

```c
// 裸机：等的时候 CPU 原地空转
while (!rx_done && !rx_timeout) {
    if (HAL_GetTick() - start > 60) break;
    HAL_Delay(1);
}

// RTOS：等的时候任务挂起，CPU 让给别人
xSemaphoreTake(g_lora_rx_sem, pdMS_TO_TICKS(60));
```

**驱动写成双模式最划算**：信号量为 NULL 时自动退回轮询，这样同一份 `llcc68_p2p.c` 在裸机工程和 RTOS 工程都能用，不用维护两份。

两个细节：
- 中断里 `xSemaphoreGiveFromISR(sem, &woken)` 之后必须 `portYIELD_FROM_ISR(woken)`，否则要等下一个 tick 才切任务
- `Take` 之前先清一遍残留（`while (xSemaphoreTake(sem, 0) == pdTRUE) {}`），否则上一轮的 give 会让这次立刻返回，表现为"收得特别快但全是垃圾数据"

### 4. ★★★ 能在中断里调 FreeRTOS API 的优先级，必须 ≥ `configMAX_SYSCALL_INTERRUPT_PRIORITY`

CubeMX 给 EXTI15_10 配的是 **3**，而 `configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY` 是 **5**。

STM32 的 NVIC 是**数值越小优先级越高**，所以 3 比 5 更"高"，属于 FreeRTOS 管不着的层级。在里面调 `xSemaphoreGiveFromISR` 会命中 `vPortValidateInterruptPriority()` 的断言。

**现象是"一收到 LoRa 就死机"**，而且不会告诉你是优先级的问题。

改法：`HAL_NVIC_SetPriority(EXTI15_10_IRQn, 6, 0);` 写在 `MX_FREERTOS_Init()` 里，别改 `Core/Src/gpio.c`（Generate 会冲掉）。

### 5. ★★ 队列的两个参数决定语义，别乱配

| 用途 | 深度 | API | 理由 |
|---|---|---|---|
| 环境数据（LoRa → MQTT） | **1** | `xQueueOverwrite` | 上报只要最新值，旧的覆盖掉，慢的一方不会积压 |
| 控制指令（MQTT → LoRa） | **4** | `xQueueSend` | 连点几下不能丢 |

深度 1 + `Overwrite` 是"永远保留最新"的标准写法；深度 1 + `Send` 会变成"满了就丢新数据"，语义正好相反。

### 6. ★★ 两个触发源控制同一个执行器，必须先用标志合成再执行

蜂鸣器有两个触发源：光照太暗、巴法云下发 `on`。

**错误写法**（两边各自调 `BEEP_Alarm`）：

```c
if (太暗)     BEEP_Alarm(1);
if (变亮了)   BEEP_Alarm(0);
if (远端 on)  BEEP_Alarm(1);
```

MQTT 刚让它响，200ms 后光照判断"不够暗"立刻把它关掉，**互相打架**。

**正确写法**：各自只改自己的标志，在固定节拍里统一合成。

```c
static uint8_t beep_by_light, beep_by_remote;

每 20ms：BEEP_Alarm(beep_by_light || beep_by_remote);
```

这条对任何"多来源控制一个设备"的场景都成立（比如以后的电机、继电器）。

### 7. ★★ 没有串口时的调试手段：让对端回一帧 ACK

终端板的 CH340 接触不良，看不到它的打印，"指令发到了没"完全抓瞎。

解法：**让终端板收到控制帧后立刻回一帧 ACK**，借中控板的串口打出来。

```c
// 终端板
frame_build(frame, TYPE_ACK, CMD_BEEP, beep_by_remote, s_led_state);
llcc68_lora_send(&llcc68_ctx, frame, FRAME_LEN, 1000);
```

```
[lora] *** ACK from terminal: cmd=0x03 val=1
```

`val=1` 这一条就把"指令到了、进对了分支、变量置对了"全部证明掉，**问题范围立刻从"整条链路"缩到"PWM 或硬件"**。

**这是"链路分段验证"思路的具体实现**：哪一段看不到，就让它的对端帮你把结果带出来。

### 8. ★★ J-Link ARM-OB 的速度，两块板不一样

| 板 | 可用速度 | 现象 |
|---|---|---|
| 中控板 | 400kHz | 正常 |
| 终端板 | **100kHz** | 400kHz 报 `Verification of RAMCode failed` |

`RAMCode` 是 J-Link 下载算法（跑在目标 RAM 里），写进去读回来不一致就是速度太快。**看到这个错误先降速，别怀疑接线。**

这块 J-Link 是 2012 年固件的克隆 OB，对速度很挑。

### 9. ★ 阻塞式接收会把"20ms 节拍"拖成 1 秒

终端板主循环：

```c
while (1) {
    20ms 节拍块           // 想每 20ms 跑一次
    ...
    receive_data(1000);   // 但这里阻塞 1000ms
}
```

节拍块实际每 1 秒才执行一次。**凡是在主循环里塞"高频节拍"的，先检查循环里有没有阻塞调用。**

修法：把接收超时降到 20ms，让循环真正转起来（代价是每圈多几次 `receive_mode` 的 SPI 配置开销）。

### 10. ★ 有源蜂鸣器的 PWM 占空比不能太低

8kHz × 4.8% = 每个周期只通电 **6 微秒**。

有源蜂鸣器的机械响应时间是几十微秒量级，**6us 根本来不及让它动**。表现是"完全不响"，而不是"声音小"。

**降音量要靠占空比，但下限大约在 20～30%**，再低就起不了振。真要更小声，串电阻比压占空比可靠。

## 三、RTOS 概念速查（附本项目实际用法）

下面这张表按"通用概念 / 本项目用了没"对照着记。**只看概念容易飘，标上实际状态才知道自己真正掌握了什么。**

| 概念 | 本质 | 本项目实际状态 |
|---|---|---|
| **Task** | 拥有独立栈的无限循环函数 | ✅ 4 个任务。没有进程隔离，所以全局变量是共享的 |
| **NVIC 优先级** | 中断的抢占等级，数值越小越高 | ⚠️ EXTI15_10 从 CubeMX 的 3 **改成 6**。必须 ≥ `configMAX_SYSCALL_INTERRUPT_PRIORITY`(5) |
| **EXTI** | 外部中断，感知突发事件 | ✅ DIO1(PB10) 用上升沿。⚠️ **PB12 按键中断里还有 `delay_nms(15)` 空转，RTOS 下要删** |
| **DMA** | 硬件搬运数据，不占 CPU | ✅ 终端板 ADC1 用它搬 `adc1_value[]`，**连续模式，没开 DMA 中断**（用不上信号量） |
| **二值信号量** | 0/1 标志，做同步通知 | ✅ `g_lora_rx_sem`。中断 give、任务 take，替代了 `while(!rx_done)` 轮询 |
| **队列** | 任务间传数据，自带同步 | ✅ 两个，方向相反：`env_queue`（深度1+Overwrite）和 `cmd_queue`（深度4+Send） |
| **互斥量 Mutex** | 带所有权的二值信号量，支持优先级继承 | ❌ **一个都没用**。`configUSE_MUTEXES=1` 只是开了编译开关 |
| **SPI** | 4 线高速总线（SCK/MOSI/MISO/CS） | ✅ 驱动 LLCC68。**只有 `loraTask` 用，单任务独占所以不需要锁** |
| **I2C** | 2 线低速总线（SCL/SDA），开漏+上拉 | ✅ 驱动 OLED。**只有 `oledTask` 用，也不需要锁** |
| **UART** | 点对点串口 | ✅ 中控板 USART2 接 ESP12-F。⚠️ 它是 `HAL_UARTEx_ReceiveToIdle_IT` 空闲中断收整包，**不是 DMA 方式** |
| **CS 片选** | 告诉 SPI 从机"在跟你说话" | ⚠️ LLCC68 的 NSS 在 `llcc68_hal.c` 里手动拉。**将来如果多个任务用 SPI，拉 CS 和发数据必须是一个原子段，在锁里面做** |
| **delay_us()** | 忙等待，占着 CPU 不让出 | ⚠️ 终端板 DHT22 还在用，而它**借 SysTick 当定时器**。RTOS 下要么换 DWT，要么用 `vTaskSuspendAll` 包住 |
| **vTaskDelay()** | 挂起任务，让出 CPU | ✅ `osDelay` 全是它。**关键收益：`esp_mqtt_init()` 那 12 秒不再卡死 LoRa 收数** |
| **portYIELD_FROM_ISR** | 中断里触发立即切换 | ✅ `DIO1_EXTI_Callback` 里调了。不调的话要等下一个 tick 才切任务，延迟 1ms |

**一句话总结这张表**：真正在用的只有 **Task、信号量、队列、vTaskDelay、EXTI→信号量** 这五样；Mutex、DMA 中断、事件组、任务通知都还没碰。**"学过"和"用过"是两件事，别混。**

### 本项目实际的完整数据流

```
                     ┌──────────── 中断层（只做"短平快"）────────────┐
  终端板发帧 ──空中──> DIO1(PB10) 上升沿 → EXTI15_10_IRQn
                     → HAL_GPIO_EXTI_Callback()
                     → DIO1_EXTI_Callback()   读 IRQ 状态+清除
                     → rx_done = true
                     → xSemaphoreGiveFromISR(g_lora_rx_sem)
                     → portYIELD_FROM_ISR()
                     └───────────────────┬───────────────────────────┘
                                         │ 唤醒
                     ┌───────────────────▼───────────────────────────┐
                     │ loraTask（AboveNormal / 1KB）                  │
                     │ 1. receive_mode(0)     进连续接收              │
                     │ 2. receive_data(50)    → xSemaphoreTake(50ms)  │
                     │ 3. 四查：长度/帧头/设备ID/校验和               │
                     │ 4. 更新 g_disp 快照（给 OLED 用）              │
                     │ 5. env_queue ← xQueueOverwrite(温度湿度)       │
                     │ 6. cmd_queue → 取指令，搭车发控制帧             │
                     └───────┬───────────────────────┬───────────────┘
                             │ env_queue(深度1)      ▲ cmd_queue(深度4)
                             ▼                       │
                     ┌───────────────────────────────┴───────────────┐
                     │ mqttTask（Normal / 1.5KB）                     │
                     │ 1. xQueueReceive(env) → esp_mqtt_set_env()     │
                     │ 2. esp_mqtt_poll()：收指令/心跳/10秒上报        │
                     │ 3. esp_mqtt_take_cmd/beep → cmd_queue          │
                     │ 4. osDelay(20)    ← 主动交出 CPU               │
                     └───────────────────────────────────────────────┘

                     ┌───────────────────────────────────────────────┐
                     │ oledTask（BelowNormal / 1KB）                  │
                     │ 拷 g_disp 快照 → 刷 4 行 → osDelay(1000)      │
                     └───────────────────────────────────────────────┘

   SysTick（FreeRTOS 独占）每 1ms 一跳 → 决定谁上 CPU、谁去睡觉
   TIM2（HAL 时基）每 1ms 一次     → HAL_GetTick() 靠它递增
```

**和通用架构图的区别，正是本项目最该记住的地方**：

1. **没有 Mutex** —— 每个外设只有一个任务碰，用不着锁。将来加第二个 SPI 设备才需要。
2. **没有 DMA 中断** —— ADC 连续转换，任务随时读最新值，比"搬完发信号量"更简单。
3. **有两条独立队列，方向相反** —— 这是双板架构决定的：环境数据往上传（只要最新），控制指令往下传（不能丢）。
4. **两个 1ms 时基分开** —— SysTick 归 FreeRTOS，TIM2 归 HAL。混用一个就是死锁。

## 四、踩的坑

1. **`app_main()` 挡在 `osKernelStart()` 前面**，RTOS 压根没启动，而所有外设看起来都正常。这个坑不报错、不报警，只能靠"任务里加心跳打印"发现。
2. **任务启动那两行打印只出现一次**，串口抓晚了就错过，差点误判成"任务没创建"。判据：看 `heap_free` 掉了多少 —— 掉了约 1200 字节就说明任务和信号量都建成功了。
3. **通过 bash 传给 `python -c` 的字符串会被两层转义**，`printf("...\r\n")` 里的 `\r\n` 变成真实换行，字符串字面量跨行，编译报 `missing closing quote`。以后这种改动用脚本文件，别用 `-c`。
4. **CubeMX 生成的是 `Template.uvprojx`，不是覆盖 `Terminal.uvprojx`**。两个 `.ioc` 的 ProjectName 都是 `Template`，所以每次 Generate 都新生成一个工程文件，原来的分组一个都不继承。

## 五、遗留

1. **蜂鸣器不响**（明天第一件事）。已排除：MQTT 链路、LoRa 下行（有 ACK）、TIM4 时钟和 PB9 复用配置、占空比过低。待验证：GPIO 直推能不能响、蜂鸣器是有源还是无源/三脚（**三脚是低电平触发，和现在的代码极性相反**）。
2. **终端板节拍被 1 秒阻塞拖慢**，蜂鸣器节奏会是"响 1 秒停 1 秒"，不是要求的 200/300ms。
3. **OLED 字库曾被链接器裁掉**（`RO-data` 只有 352 字节），现在 OLED 任务已经用上了，下次编译要留意 RO-data 应该回升到 15KB 左右。
4. **调试打印要收拾**：`esp_mqtt.c` 里那句 `[MQTT] rx topic=[..] payload=[..]` 是诊断用的，稳定后删掉。
5. **终端板还没移植 RTOS**，按计划压后，先解决蜂鸣器硬件。
6. **中控板按键中断里的 `delay_nms(15)` 还留着**：`ISR_callback.c` 的 `HAL_GPIO_EXTI_Callback()` 里，`GPIO_Pin == GPIO_PIN_12` 分支空转 15ms 做"软件去抖"。PB12 和 LoRa 的 DIO1(PB10) 同属 `EXTI15_10_IRQn`，按一下键就把 LoRa 中断堵住 15ms —— 正好可能错过终端板那一帧。RTOS 下的正确做法：中断里只置标志发信号量，去抖交给任务用 `vTaskDelay` 做。
